# Email-template variables as chips

Companion to CLAUDE.md § Forms — Template variable fields and § Rich text editing. One topic that used to have two homes: the chips are super_editor inline placeholders, so the field rules and the editor rules belong together. The main file carries one line per rule; this doc carries the evidence.

## Which variables a template supports is a property of the server engine

**Which variables a template supports is a property of the server engine, not of a list.** `HtmlEngine` renders invoice / quote / credit / reminder / recurring emails, `VendorHtmlEngine` purchase orders, `PaymentEmailEngine` payments — but `payment_failed` goes through `HtmlEngine` (plus `$payment_error`), `statement` gets `HtmlEngine` values plus `$start_date` / `$end_date` from `ClientService`, and `custom1-3` go out with any document, so they never warn. `lib/domain/email_template_variables.dart` (imports nothing) holds the scopes, the picker groups and, per catalogued token, the set of engines that define it; "in scope" is computed from that set, never from which group happens to list a token (`HtmlEngine` defines `$vendor.name` although no invoice group offers it). `test/domain/email_template_variables_test.dart` re-extracts the `$data['$…']` keys from the three PHP engines when the server checkout is present and reports **skipped**, never passed, when it isn't — the `totals_parity_test` contract — and asserts every token of every server default template is in scope, which is what caught the statement template's `$start_date`. The old card's `$client_address1` existed in no engine. A catalogued token the scope's engine lacks warns amber "Not available"; an uncatalogued one stays plain text in Templates & Reminders, which has no way to ask the server.

## A single-line field can't hold chips and be edited as text

**A single-line field can't hold chips and be edited as text,** because a `WidgetSpan` standing in for a 13-character token breaks `EditableText`'s 1:1 text↔layout offset map. So `TemplateVariableFieldShell` has two modes: at rest a `Text.rich` of chips inside an `InputDecorator` built exactly as `TextField` builds its own; tap the text and the owner's untouched `TextField` swaps in (tokens tinted by `TemplateVariableTextController`, offsets 1:1, the IME's composing underline left alone), caret at the tapped character. Three rules. **Blur is focus leaving the whole shell**, not the text field — Tabbing into its own suffix button must not swap the view and unmount the button that just took focus. **The owner wires the supplied tap-outside handler** (`dismissPickerOnTapOutside`): on touch an outside tap never unfocuses a field, and the user would be stuck staring at raw tokens. **Edits made through a chip are programmatic** and don't fire `onChanged`; they arrive through `onEdited`. An inherited value (`interactive: false`) is inert and unfocusable — the `IgnorePointer` in `OverridableField` doesn't stop Tab.

## The default template is shown, never silently saved

**The default template is shown, never silently saved.** Most companies never customise a template, so an empty subject and body are the common case. At company scope both fields render the statics default (muted, with a "Default" badge / caption); chip edits and typing work on a copy, and the value stays `''` until a real edit — text equal to the default writes `''` again, and "Reset to default" writes `''`. That matters beyond tidiness: the server localises an *empty* template per client at send time, and a saved one is fixed text in one language. The statics key isn't always the template id (`staticTemplateKeyFor`: `payment_partial` → `partial_payment`); credit and custom templates have none.

## Values come from the server, exactly, or not at all

**Values come from the server, exactly, or not at all.** `/api/v1/templates` returns rendered text but no variable map; it does, though, substitute a *subject* with plain `strtr` — no markdown, no escaping — leaving unknown tokens literal. So `resolveTemplateVariables` sends a subject of the tokens behind `[[in<nonce>:i]]` markers (no `$` in them, so `strtr` can't match one) with a body of `'.'` (Laravel turns `''` into null and the engine would load the default body), and reads each value back out; an echoed token is "Not recognized". It is a free function over `render`, not a `TemplatesApi` method — four tests `implements` that class — and it **throws when unbound**, because an unbound render substitutes another record's values (#31); the composer only builds a `TemplateVariableValuesController` when `emailPreviewBinding` is bound. One probe on open covers the whole catalog; later only new tokens are asked about; every failure is silent and a permanent one stops probing. On a phone the composer also shows the rendered subject under the field, since the preview is a tab away. The Send Email body is no longer pre-filled with the template (usually literal HTML): it starts empty ("Use default"), and **Customize** loads the template for editing. Scheduling after an edit asks first — the server's scheduler ignores subject/body overrides (BACKEND.md).

## Template variables are inline placeholders the markdown never sees

**Template variables are inline placeholders the markdown never sees.** With `templateVariables:` set (the Templates & Reminders body — invoiceninja/flutter#139), a recognised `$token` is a super_editor inline placeholder (`TemplateVariablePlaceholder`, one atomic character to the caret, selection and backspace) rendered as a chip through `Stylesheet.inlineWidgetBuilders` (`markdown_template_variables.dart`). The pinned serializer has no placeholder hook — a placeholder serializes as a literal U+FFFC — so chips are created *after* deserializing (`tokenizeTemplateVariables`) and turned back into their tokens before **every** serialize (`_serialize()`, the only serialize call in the file). Five things are load-bearing. **The round trip must be byte-identical**, or an untouched field emits a spurious change: attribution markers are remapped through an offset map rather than stitched, and `markdown_template_variables_test.dart` pins a corpus that includes the server's default bodies after `markdownFromLegacyHtml`. **Only a uniformly formatted token becomes a chip**: the server substitutes *before* it parses markdown, so `**$client**.name` is `$client` plus a literal `.name` — a chip there would change what the email says; inline code and tables stay raw too. **The chip builder must claim every placeholder of its type**, known or not — super_editor adds nothing to the span for an unclaimed one and the layout's offsets then drift from the document's. **Taps never reach a chip widget**: inline widgets sit under an `IgnorePointer`, so the editor routes them through a `ContentTapDelegate` (built fresh per `Editor` — SuperEditor disposes delegates when its editor changes) and the tap-to-edit reader, itself under `SliverIgnorePointer`, hit-tests the host's tap against `SuperReader(documentLayoutKey:)`; for the same reason body chips have no hover, no ripple and no semantics of their own (the frame carries a `Semantics` value summarising them). **Reactions order**: every reaction's `react` gets the same change list and a request issued in `react` runs at once, so the typed-token conversion reaction is appended **last** (`installTemplateVariableReactions`) — shrinking the text before `LinkifyReaction` ran would leave it on stale offsets. Opening the picker is a route, which blurs the editor and clears its selection, so the target is captured first and the caret restored after. Copy/paste of a chip drops it (super_editor copies a placeholder as U+FFFC, which serialize discards) — accepted. `defaultValue:` renders the server's default template when the value is empty and emits nothing until a real edit; a document edited back to exactly the default emits `''`, and one emptied outright shows the default again — at once at rest, and on blur while editing, from a **post-frame** callback: SuperEditor's own blur handler runs after ours and executes a `ClearSelectionRequest` against the composer a reseed would already have disposed. The caption under it sits in a wrapper that stays mounted for as long as a default exists — wrapping on the showing-default flag itself re-parented the frame at the first keystroke into the default and remounted the live editor under the caret, which `markdown_text_field_template_variables_test.dart` catches by asserting the `SuperEditor` state survives. A super_editor bump must re-run `markdown_template_variables_test.dart`. Logged in `docs/upstream-workarounds.md` § 9.

## Every markdown field guards `$variables` from linkify

**Every markdown field guards `$variables` from linkify.** super_editor's `LinkifyReaction` matches loose URLs over the whole space-delimited word, so typing `Dear $client.name, ` (`.name`, `.city`, `.date` are TLD-shaped) produced `[$client.name,](https://$client.name,)` — and the server, which also substitutes variables in terms, notes and footers (`PdfBuilder.php`), then replaced the token in both halves and rendered broken link markup. `TemplateVariableLinkScrubReaction` runs directly after `LinkifyReaction` on every `MarkdownTextField` and removes a link whose URL is `https://` + its own text when that text holds a variable; `healTemplateVariableLinks` applies the same predicate on seed, *before* the baseline, so content saved while the bug was live is cleaned on the next real edit without a spurious emit. A real URL still links. `docs/upstream-workarounds.md` § 10.
