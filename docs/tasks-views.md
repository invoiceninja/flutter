# Tasks layout views

Companion to CLAUDE.md § Tasks layout view. The main file carries the `?view=` / `nav_state` precedence rule and the rule for each behaviour; this doc carries the evidence — why the URL is an override rather than the carrier, what the lock exists for, and why the kanban board has no create FAB.

## The `view` key is overloaded, so `full` must parse to null

**The `view` key is overloaded, so `'full'` must parse to null.** `MasterDetailLayout` writes `?view=full` for its full-width pane flag (`_toggleFullScreenInUrl`, plus the auto-promote redirect a frame after an editor opens) and the tasks list is rebuilt from that same `GoRouterState` — so every open editor hands the parser `'full'`. Null means "the URL expressed no opinion"; mapping it to `list` would claim the URL had chosen the list. Every *other* reader of `queryParameters['view']` in `lib/` compares against `'full'`, so the overload stays contained to one line. This is also why the mode is **not** carried on the pane URL instead: `_toggleFullScreenInUrl` would clobber it going in and strip it coming out.

## The fallback is suppressed when the screen can only be the list

**The fallback is suppressed whenever the screen can only be the plain list** (`locked`), and each arm exists for something that fails silently. **A pane is open** — only `EntityListScreenScaffold` writes `MasterDetailNavController.update`, and the pane reads it for J/K row-stepping and for `EntityDetailScaffold`'s synchronous first-frame seed, so a board behind the pane kills both and opens the detail on a spinner; `_SelectedIdScope` is inert there too, and `TaskCalendarScreen.initState` does network I/O (`loadStatus` + the events fetch), so a remembered calendar would fire a connection-status request on **every record opened**. Locking keeps everything behind the pane identical to what shipped — the mode only has to survive the trip *out*. **A `ListFilterIntent` rode in** on the route's `extra` (a dashboard task card) — only `GenericListViewModel` consumes it, so a board would swallow the drill-down. **Embedded, or scoped to a client / project** — the board and calendar take no such argument and would drop the filter.

## The toggle emits no `?view=` — a view switch is not a history step

**The toggle emits no `?view=` at all — a view switch is not a history step.** `TasksViewToggle._go` writes `Services.tasksView` and navigates to a bare `/tasks`. It has to be that way round: `isUpNavigation` compares paths only, so `/tasks` and `/tasks?view=kanban` are separate history entries, and pressing Android back onto the bare one re-renders the board from the preference — the press changes nothing on screen and reads as a broken back. Every other list-view control in the app (filters, sort, status tabs) already lives in `nav_state` and creates no entry; this now matches, and the URL stays a pure override for the paths that genuinely carry one. The cost is that the `go` is a **no-op whenever the URL is already `/tasks`** — `GoRouterDelegate.setNewRoutePath` returns early on an unchanged `RouteMatchList`, so `NavStatePersister` and `NavHistoryController` see nothing either — which is exactly why the `ValueListenableBuilder` in § `_RememberedTasksView` is the second writer below is the entire repaint path and must not be made conditional. `_go`'s early return needs **both** halves (`next == active` AND the stored value matching): `active` is what the screen renders, and a locked screen renders List even for a Kanban user, so tapping List there must still be able to set it.

## `_RememberedTasksView` is the second writer, and its builder is unconditional

**`_RememberedTasksView` is the second writer, it writes post-frame, and its `ValueListenableBuilder` is unconditional.** The toggle writes the user's own choice; this mirror covers every URL-driven path — the calendar day-cell's `?view=daily&date=…`, the post-OAuth `/tasks?view=calendar`, a restored `nav_state` route, back/forward — so the preference cannot drift from a URL that does name a layout. Post-frame because `ValueNotifier.notifyListeners` must never fire inside the parent's build phase. **Do not wrap the builder in an `if (locked) return …`**, however tempting: `locked` carries `hasPane`, which flips on every pane open and close, so the widget at the list's slot would alternate between `ValueListenableBuilder` and `EntityListScreenScaffold`, `Widget.canUpdate` would fail on the runtimeType change, and the list would be unmounted and re-inflated. The wide branch of `MasterDetailLayout` keeps that element alive on purpose (`Positioned.fill(Offstage(…))` is Stack child 0 in both pane states), so the symptom is a desktop list that resets its scroll, rebuilds its ViewModel back to page 1 and drops multi-select every time a row is clicked — and a re-seeded `MasterDetailNavController` that can no longer resolve the row the pane just opened. Narrow remounts anyway, so it is invisible where it is easiest to test. `EntityListScreenScaffold._statusTabs` is **not** a precedent for branching here: that guard wraps an optional *sibling* in a `Column`. `test/lint/tasks_view_wiring_test.dart` fails the build on the early return.

## `stripTransientQuery`'s carve-out for a non-`full` view must stay

**`stripTransientQuery`'s carve-out for a non-`full` `view` must stay** even though the toggle no longer produces one: the calendar day-cell link and the post-OAuth landing still do, and stripping it would drop the layout from a restored route for exactly those. (It is **not** what keeps Android back working — the toggle emitting no `?view=` is.) Three known gaps, deliberately not fixed here: applying a Tasks **saved view** while a board is showing does nothing visible (its filters land in `nav_state.filters_json`, which only `TaskListViewModel` hydrates), `/tasks?client_id=…` still loses its filter through a pane round trip, and a dashboard card's `ListFilterIntent` lock lasts only as long as the route entry that carried the `extra`, so opening one of the drilled-into tasks and closing the pane unlocks the screen and a remembered board replaces the filtered list (the filters survive in the VM and `nav_state`, and every task card ships `{}` filters today, so nothing is actually lost yet) — the general cure for that is a "sticky list query" concept in the entity-agnostic navigation helpers, which is a much wider change than a bug fix wants.

## The kanban board is the one Tasks view with no create FAB

**The kanban board is the one Tasks view with no create FAB, and the gate that makes that safe is not the one it looks like.** Daily / weekly / calendar each hardcode an identical `FloatingActionButton`; kanban had a fourth copy, and it was the redundant one — every column ends in a `+ New Task` that seeds *that column's* `status_id`, while the FAB seeded nothing. `emptyTask()` is `statusId: ''` and `watchAllByStatus` groups strictly on that key, so a FAB-created task **whose status the user left blank** — the form has a picker, but nothing defaults it — sits in no column until the server's `TaskRepository::setDefaultStatus` assigns the first status on the round trip, i.e. never, offline. On a phone `endFloat` also parked it on top of the footer of whichever column was scrolled to the right edge. That was invoiceninja/flutter#135, and React had already settled it: `Kanban.tsx` has no page-level create control at all, only a per-column `+` gated on `hasPermission('create_task')`. **The trap is what that footer was gated on.** `KanbanBoard` passes `canEdit && !vm.filtersActive`, which is right for **drag** — a reorder computed from a filtered, partial set would drop the hidden tasks from a status's persisted order, which is why `commitReorder` re-checks it — but the footer was riding along, so applying any Client / Project / Assignee filter took away the board's *only* remaining create path. `canCreate` is now a separate parameter carrying `create_task`, and it is deliberately filter-independent: a quick-add writes one task's `status_id` and rewrites no order. The token matters as much as the split — `edit ⇒ view` and `delete ⇒ edit` are the **only** cross-verb implications `can()` makes (it also expands `<verb>_all`, and admin / owner short-circuits the lot), so an edit-only user genuinely cannot create, and a create-only one previously had the FAB and no footer. Two things are deliberately left alone: the `statuses.isEmpty` empty state keeps its `New task status` CTA and offers no task-create at all (with no columns there is nothing to create *into*, and the other four layouts are one tap away on the same AppBar), and the daily / weekly / calendar FABs stay, because **a FAB may only be dropped where the substitute is the same verb** — which is the rule to carry forward, not "kanban has another button". Daily and weekly are specifically not a precedent: each already shows a `+` FAB *and* an always-visible `Log time` button on both widths (`task_daily_header.dart`, `task_weekly_screen.dart`), and `TaskDailyActions.logTime` really does create — it ends in the same `goEntityCreateFullWidth('/tasks')` — but it pre-fills a 30-minute `TimeEntry` and is labelled as logging time, so removing their FAB would make a plain new task unreachable from a timesheet view. Calendar's only other create is convert-this-event (`convert_event_to_task_sheet.dart`), which needs a connected calendar and an event to convert. `test/lint/tasks_view_wiring_test.dart` scans for a returning FAB — stripping `//` first, or it trips on the comment in `kanban_screen.dart` that explains the absence — and for the two gates staying apart; `kanban_column_test.dart` pins the widget in both directions, since every failure here is silent: the wrong gate simply draws one widget fewer.
