# Why a translated string renders wrong

Companion to CLAUDE.md § Localization. CLAUDE.md keeps the workflow (Transifex
zip → importer → bundled JSON) and one rule per trap; this doc carries the
mechanism behind each — what shipped, why no lint saw it, and the test that
now pins it.

## The upstream PHP is HTML-escaped — the importer decodes entities

**The upstream PHP is HTML-escaped — the importer decodes entities, don't bypass it.** Transifex ships `&#39;`, `&quot;`, `&gt;`, `&amp;`, `&eacute;` inside translated strings, and Flutter's `Text` has no HTML layer to undo them, so whatever lands in the JSON is literally what the user reads: Italian Settings showed `Colore dell&#39;accento`, French `Cl&eacute; d&#39;acc&egrave;s`. 504 strings across 7 locales shipped that way, invisible to the team because **English has zero entities**. `TransifexPhpParser.parse` now runs values through `decodeHtmlEntities` (`lib/l10n/transifex_php_parser.dart`, mirrored in the importer's own inline copy — keep them in sync). That function is the app's single entity decoder, not an l10n-private one — `lib/utils/notes_html.dart` imports it for the read-only notes surfaces — so don't narrow it to the importer's needs. It is deliberately a **single pass** so `&amp;#39;` stays the literal text `&#39;` rather than double-decoding to an apostrophe, and it leaves unrecognized entities, bare `&`, and markup tags (`<p>`, `<br>`) alone. `test/l10n/no_html_entities_test.dart` fails the build if an escaped string reaches `assets/i18n/`.

## Serbian ships in Latin script — the importer transliterates its Cyrillic

**`sr` is `sr-Latn` (`kSupportedLocales`, so Material's own strings match), and the importer runs every `sr` value through `serbianCyrillicToLatin` (`tools/transifex_importer/lib/serbian_latin.dart`) before the English filter.** Transifex's `sr` file mixes the two scripts: 2,426 of 6,065 values in `sr.json` were Cyrillic, so a Serbian sidebar read "Klijenti, Računi … Продавци" (`vendors`), and `purchase_orders` / `transactions` likewise. The conversion is letter for letter (the alphabets map one to one); only Љ / Њ / Џ become two letters, title case at a word start (Ljubav) and all caps inside a caps word (LJUBAV) — decided by the next letter, or the previous one at a word end. Everything else — `:placeholders`, `$variables`, URLs, HTML, Latin text — is ASCII or already Latin and passes through. A non-Serbian Cyrillic letter is left as is and the importer prints a warning.

Applied once to the bundle in October 2026 (the `_app_pending_sr.json` overlay was already all Latin). 138 of the converted values then read exactly as the English — mostly the English source letter-mapped into Cyrillic rather than translated (`backup` was `Бацкуп`, `cart` `Царт`, `json` `ЈСОН`), which had slipped past the identical-to-English filter — and were dropped, as the importer now drops them; the lookup reads the same English text. `test/l10n/serbian_latin_test.dart` tests the transliteration (the importer is a zero-dependency CLI with no test runner, so CI runs it from the root suite) and fails if either Serbian file holds Cyrillic again.

## `_app_pending.json` can only add a key, never override one

**`_app_pending.json` can only *add* a key, never override one.** Lookup order is active locale (with its `_app_pending_<locale>.json` laid in, below) → `en.json` → pending → raw key, so a pending entry whose key already has a non-blank `en.json` value is dead and never renders. 41 such entries had accumulated — one of them (`fees_sample`) left the gateway fee preview naming the *total* as the fee. `no_unsubstituted_placeholders_test` now fails the build on a shadowed entry; give deliberate rewordings a distinct name (`*_label` / `*_short` / `*_detailed`).

## App-local strings are translated per locale in `_app_pending_<locale>.json`

**App-local strings are translated per locale in `_app_pending_<locale>.json`, laid over the locale's bundle wherever it has no real translation (blank, or Transifex's English copy) — so an entry outlives its `_app_pending.json` line and goes only when a real translation lands.** Transifex can't translate a key it doesn't have, so before Oct 2026 every one of the ~1,600 app-local strings read English in all eight non-English locales. Each non-English locale in `kSupportedLocales` may carry `assets/i18n/_app_pending_<locale>.json` (flat key → string); the delegate loads it beside the locale bundle and merges it in once (`Localization._withLocalePending`; none for `en*`, a missing file is simply empty, and a missing *locale* bundle still gets it), so the per-lookup chain is unchanged. The merge replaces an entry that is absent, blank **or equal to the `en.json` value** — the last because Transifex exports an untranslated key as its English source (`zh_CN.json` carries 5,245 such copies), so a plain "locale bundle first" order would hand the user English the moment a key reached Transifex in English only. A real Transifex translation still wins. The importer now drops those copies at import (any value identical to the zip's own English), so the comparison only matters for a bundle imported before that change or one newer than `en.json`. The lifecycle is therefore: a key is added to `_app_pending.json` (translations optional — a missing one reads English); when Transifex ships the English, the `_app_pending.json` line is deleted (`no_unsubstituted_placeholders_test` insists) and the overlay entries **stay**; when the locale's bundle carries a real translation, that locale's entry is deleted. `test/l10n/app_pending_translations_test.dart` fails the build on an entry whose English is in neither file, a blank value, an entry the locale bundle really translates, a `:placeholder` set that differs from the English, and a State filter chip (`entity_state_filter`) reading the same as `status` — the collision that key exists to avoid, which the first machine pass reintroduced in es / it / zh_CN. A translation of English that Transifex later reworded is not caught. These files are machine-translated against each locale's Transifex vocabulary; Transifex remains the source of truth.

## A placeholder name that prefixes another needs no care

**A placeholder name that prefixes another needs no care — because `lookup` sorts longest-first.** `":time in :timezone"` substituted in map-insertion order rewrites the second token to `"<value>zone"`, which then never matches: rendered garbage, not a missing string, so no `tr()` lint sees it, and which token wins depends on the caller's literal map order. `Localization.lookup` therefore replaces the longest name first (the single-param hot path returns before the sort). Five bundled keys have this shape — `activity_10`/`_39`/`_40`/`_41` (`:payment` + `:payment_amount`) and `entity_number_placeholder` (`:entity` + `:entity_number`); the activity templates dodge it only because `activity_description.dart` tokenizes with a regex instead of coming through `lookup`.

## Never render a string carrying a `:placeholder` without filling it

**Never render a string carrying a `:placeholder` without filling it.** Many Transifex keys ship in two flavours: a parameterised one for when the app knows the value (`add_to_invoice` = "Add to invoice :invoice") and a plain verb for when it doesn't (`action_add_to_invoice` = "Add To Invoice"). Pointing a menu label at the former leaks the raw token (invoiceninja/flutter#35). Fix one, in this order: **(1) pass the params** — usually possible and always keeps the translation (`copyToClipboard` fills `:value` this way, with a `label:` when the payload is a blob); **(2) point at a placeholder-free Transifex sibling** (`action_add_to_invoice`, `invoice_sent_notification_label`, `min_amount`); **(3) last resort, add a distinctly-named app-local key** — that key has no Transifex translation, so until someone adds it to the locale overlays (next section) every non-English user reads English, and it's only right when the bundle has no clean variant (`view_expense_label`, `download_documents_label`). **Don't blank the token and `.trim()`**: German and Japanese put `:invoice` mid-string, so that leaves a double space. A translator can cause the same leak from the other side by renaming a token (`fi` shipped `copied_to_clipboard` as "Copied :arvo", and about 25 locales had `days_left` as `:day s`), so the importer drops any translation carrying a placeholder its English lacks, and `test/l10n/supported_locales_test.dart` checks every bundle for it. `test/lint/no_unsubstituted_placeholders_test.dart` fails the build on a leak it can see; keys reached through a variable, a const list, or a positional arg are invisible to it, so a renderer that looks up keys from a structure needs the invariant asserted in that structure's own test (`settings_search_catalog_test` does this).

## The company's Custom Labels are the one override

**`Localization.lookup` reads the active company's Custom Labels first, then the locale, English and pending bundles** (invoiceninja/flutter#84). Settings → Localization → Custom Labels writes `company.settings.translations`. The server applies it to every PDF, email and portal page, and React to every string (`useCompanyTranslations`). This app used to read it at the line-item headers alone, so a company that called a quote an "Estimate" saw "Quote" everywhere else.

- **The path.** `CompanyLabelOverrides` (`lib/app/company_label_overrides.dart`) watches the active company's Drift row, so a save, a Sync, a `/refresh` and a company switch all reach it. It is cleared at the moment of a switch rather than when the new row arrives. `CompanyLabelsScope`, an `InheritedNotifier` wrapping everything `MaterialApp.builder` returns, carries it. `Localization.of` layers it over the bundle instance (`withOverrides`), memoized on the pair, so a frame shares one instance and a locale switch never serves the old language. The delegate is untouched: reloading it would re-decode the locale's whole JSON for a map of a few labels.
- **Company only, and only in the company's language.** No client or group cascade; the app's strings are not about one client. While the language the app *shows* (`Services.appLocale`) differs from the company's own (`settings.language_id` through the statics, English when unset), the map is withheld, so German labels never land inside English sentences. The comparison is with what is shown, not with the device setting. A company whose language ships no UI strings runs the app in English with no override at all, and its labels are words of its own language. React applies them whatever the language; this was a product decision. The Custom Labels screen says so (`withheldForLanguage`). Statics that fail to load leave the language unknown, and the labels then apply unchecked rather than stay stale.
- **Blank and non-string values are dropped** (`companyLabelOverrides`). The editor seeds a new row with `''`, and some accounts store a nested object under a key.
- **One exact key.** Overriding `invoice` does not change `invoices` or `new_invoice`, as in React. The Custom Labels screen says so and offers the related keys the bundle has.
- **What must not see an override reads `lookupBundled` / `context.trBundled`:** the Custom Labels screen's own row labels and add dropdown (it would otherwise label a row with the user's wording), and `builtInTaskStatusKey`, which matches a stored status name against the bundled word. `englishOf` stays bundle-only, so settings search still matches the English word.
- **Without a scope nothing changes**, which is every test that pumps a bare `MaterialApp`. `wrapWithShell` installs one, as `main.dart` does.
