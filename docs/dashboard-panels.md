# Dashboard panels

Companion to CLAUDE.md § Dashboard panels. The main file carries the registry shape — how a panel is declared, ordered and hidden — and the rule for each behaviour; this doc carries the evidence, almost all of it from the task-calendar panel, the first Drift-backed one.

## The task-calendar panel, and the eleven things that hold it up

**The task-calendar panel (invoiceninja/flutter#137) is the first Drift-backed one, and almost everything load-bearing about it is invisible at the call site.** It shows a month as a 7×6 grid tinted and bar-filled by the hours booked on each day, so a user on the phone can see whether they are free before agreeing to a date. Eleven things matter. **It must keep itself alive** (`AutomaticKeepAliveClientMixin`): both dashboard bodies are lazily-collected `ListView`s and the panel is appended *last*, so it starts off-screen, and a plain `StatefulWidget` there is garbage-collected past the cache extent — taking its view model, its Drift subscription, the month the user paged to and the fetch latch with it, so every scroll back would reset the month and re-request. Every other dashboard card is stateless, so nothing else in the feature guards this; `task_calendar_card_test.dart` pins it by scrolling a tall list and checking the month survived, and that case genuinely fails without the mixin. **Nothing under the card may be a `LayoutBuilder`** — `_MultiColumnGrid` wraps every wide-grid row in `IntrinsicHeight`, which throws on an intrinsic query against one in debug and silently answers 0 in release; `Center` is genuinely inert under an intrinsic query; `ConstrainedBox` — which is what the `kMiniCalendarMaxWidth` cap uses — is **safe but not transparent**, since `RenderConstrainedBox` forwards the *incoming* width to its child unclamped, so the body is measured at the full column width and laid out at the cap. Nothing under it may change height with width (the caption is `maxLines: 1` for exactly that reason). That cap is **not** a wide-desktop nicety: the bottom grid stays one column from 600 px to 1199 (it only splits at 1200), so without it a 768 px tablet pane renders seven ~110-165 px columns against a ~38 px row — a month grid stretched into a banner. **The cell tint rides on the cell's own `Material`**, never a `DecoratedBox` under the `InkWell`: ink features paint *before* the child subtree, so an opaque fill below the ancestor Material swallows the splash — the same mechanism that makes `Ink` banned. (The shipped `_DayCell` in `date_range_picker_button.dart` shows both halves: its edge branch uses a local `Material`, its range band a bare `ColoredBox` that eats its own ripple.) **The tint is `Color.alphaBlend(<statusToken>.withAlpha(α), tokens.surface)`, not the `*Soft` token** — `surface` is user-overridable (`CustomToken` is `{background, surface, ink, border}`), so a fixed pale-green would sit on an arbitrary background and strand `ink`; blending into the live surface keeps every cell near it, `_deriveAccentSoft`'s idiom. The hues are `paid` → `sent` → `overdue`, deliberately the **status** tokens: none is in `CustomToken` and every preset keeps the hue family, so no override can invert the scale — unlike `accent`, whose second stock swatch clamps to near-black in light mode. **The bar is not redundant with the tint**: the tint is three buckets while load is continuous, so 5 h and 7 h are both "limited" but visibly different, and the bar's *length* is what keeps the signal alive under red-green colour blindness (colour is never the only cue). **Out-of-month days dim their NUMBER only** — the tint and bar stay at full strength, the reverse of `TaskCalendarDayCell`'s whole-cell `Opacity`, because the panel exists to answer "can you do the 2nd?" and the 2nd lands in the spill row; dimming the one signal it is for would be exactly backwards. **`Semantics(excludeSemantics: true)` must re-declare `onTap`** or the cell becomes a button a screen reader can announce but not activate, and its label speaks **decimal hours with a unit** rather than `formatDuration`'s `H:MM`, which in a *calendar* is heard as a clock time — the same ambiguity that keeps hours out of the cell itself. The `Tooltip` is gated on `!Env.isTouchPrimary`: it is a `StatefulWidget` owning an `OverlayEntry`, and 42 of them on the app's landing screen is a real cost for something touch can only reach by a long-press nobody will try. **It is gated on `can('view_task')`, unlike its six siblings** — they render server-fed data the API has already permission-scoped, so an empty card honestly means "nothing to show", while this one reads the *local* tasks table and a user without the permission has none in Drift, so an ungated grid would paint every day unbooked: a positive claim of availability rather than an absence of data (`RunningTimerPill` gates on the same key for the same reason). **`Today` renders only off the current month**, its slot reserved, since always-on it does nothing on the month the panel opens to. And the panel's one accepted cost is that `watchAllActive` — an unLIMITed `select(tasks)` that JSON-decodes every active task's payload per emission — now runs on the route the app opens onto; it cannot move into SQL because a task's day and durations live only inside `payload`, and the real fix is a `calculated_start_date` column on the Drift table (which would also close the device-vs-company timezone gap and unblock sorting by date), deliberately out of scope on a shipped app.

## Per-day load buckets per time entry, not per task

**Per-day load is one rule in one leaf, and it buckets per time ENTRY.** `lib/domain/tasks/task_day_load.dart` owns `kFullDayLoad` (8 h), `taskLoadByDay`, `dayLoadBucket` and `dayLoadFraction`. `tasksByDay` answers a different question — which day a task *starts* — and drops every later day it was worked on, so a task with entries on Monday and Wednesday would colour only Monday; the per-entry rule is the one `TaskWeeklyViewModel.secondsFor` already applies, and `task_day_load_test.dart` asserts `taskLoadByDay` and `secondsFor` agree day for day, which is what stops the panel and the timesheet disagreeing about the same Tuesday. Consequences: an entry lands **entirely on its start day** (a 20:00→04:00 session, or a timer still running from yesterday, counts wholly on the first day — imperfect for availability, but diverging from the timesheet would be worse); `now` is a required parameter so a running entry is measured against an injectable clock; the result is a snapshot at the caller's last notify, **not a ticker**, because re-laying out 42 cells at 1 Hz to move a 3 px bar is not worth the frames; and `dayLoadBucket` compares whole `Duration`s rather than a ratio, so the 4 h and 8 h boundaries cannot land on a float edge. Fixtures use the local `DateTime(...)` constructor and one `.toLocal()`-derived UTC case — check with `TZ=UTC flutter test`.

## The month window is fetched by the view model, month-aligned

**The month window is fetched from the server, by the view model, and it is month-aligned for a reason.** `TaskCalendarViewModel.ensureMonthLoaded` pages `repo.ensurePageLoaded` with `extraFilters: {'date_range': {'calculated_start_date,<from>,<to>'}}` — a **one-element** set, since `ensurePageLoadedTemplate` serialises a filter's values with `join(',')` and a second element would corrupt a 3-part value into a 4-part one. It lives on the VM rather than on either screen so the Tasks calendar and the dashboard panel get it *structurally*, with neither call site having to remember. The window is `firstOfMonth − kTaskMonthLookbackDays` to `firstOfMonth + 41`, **never grid-aligned**: `calendarFirstDayOfWeek` resolves the company setting *or the device locale* and both hosts correct the seeded `firstDayOfWeek` on their first frame, so a grid-aligned window would shift under `setFirstDayOfWeek` and fire a second request on every calendar open outside a Sunday-first locale — `task_calendar_month_fetch_test.dart` pins exactly that. **The trailing bound is `+41` from the FIRST of the month, and the arithmetic is the part to get right**: `monthGridDays` is always 42 cells from a start that is never later than the 1st, so `firstOfMonth + 41` covers the grid whatever the week start, with slack equal to the leading-blank count. A margin measured from the month *end* instead has to be **14** (a 28-day February whose 1st falls on the week start spills exactly that far) — the `+6` this shipped with left part of the rendered grid unfetched in **383 of the 588** month × week-start combinations, and those cells then paint "free" off whatever the local cache held, which is the one claim the panel must never make by accident. The 90-day lookback is a mitigation, not a proof: the server's `calculated_start_date` is harvested from `time_log[0]` — the **first** entry, not the earliest — and shifted by the *company's* utc offset, so a task opened in August and still being logged against in September is invisible to a naive September window, and no width fixes that in general. The fetch is bounded at 5 pages and **never throws**: `CompanySwitchedException` and `NetworkException` log at `fine`, everything else at `warning`, every arm releasing the latch. The window maths and the two latch checks sit in `ensureMonthLoaded` and cannot throw (pure `Date` arithmetic); the `try` begins at the page sweep inside `_runWindow`, and its catch is deliberately **bare rather than `on Exception`** — nothing awaits the constructor's future, so an escape becomes an unhandled async error, and the repository doubles in the sibling suites raise `UnimplementedError`, which is an `Error`. **Completed windows and in-flight ones are tracked separately, and collapsing them re-introduces a race.** `_loadedWindows` is what has finished; `_inFlightWindows` maps a window key to the sweep running for it, registered before `ensureMonthLoaded` returns — no other caller can run between the lookup and the claim — so two month taps join one walk. `invalidateLoadedWindow` (the dashboard's pull-to-refresh hook) clears only the first: clearing a live claim would let a refresh landing mid-sweep start a second concurrent walk of the identical window, and the first walk's failure arm would then release the key the second was holding, freeing a third. The loop also **re-checks `_disposed` after every page** — `dispose` cancels the Drift subscription but cannot interrupt a `for`, and on a company switch the next page would otherwise go out under the *new* company's token for the *old* company's window, only to be discarded when it arrived. **A successful sweep notifies; a failed one does not.** Leaning on "the upsert re-emits through the watch" is wrong for the case that matters: `upsertAllPreservingDirty` early-returns on an empty batch, so a `{"data": []}` response writes nothing, drift raises no table update, and the stream stays silent — which is precisely a new account or an empty month, the one state the "nothing booked" caption exists for. The failure arms stay silent because nothing observable changed there, and a best-effort top-up that fails must remain invisible. Three costs are accepted rather than fixed: a cold start now adds up to five task requests to the boot fan-out on the default post-login route; the latch is per-instance, so the dashboard card and the Tasks calendar screen each fetch the same window while both are mounted (a shared cache would need a logout fan-out to be leak-safe), and holding the month arrow queues one bounded sweep per month with no supersession. One more silent degradation worth knowing: the server falls back to `date` for a column it does not recognise, and `tasks` has no `date` column either, so an old self-hosted install without `calculated_start_date` gets **no filter at all** rather than an error — harmless, since that is what `refreshAll` fetches anyway, but undetectable client-side.

## `hasLoaded` is not enough to claim availability

**`hasLoaded` is not enough to claim availability, and the gate for that claim is not `Opacity`.** A Drift watch emits on subscribe, so `hasLoaded` flips within a frame of construction — before the window fetch that fills the grid's far edges resolves. The confident sentence ("Nothing booked this month") therefore waits on `hasLoaded && !isLoadingWindow`, while the dimming waits only on `hasLoaded` (dimming for every month change's round trip would flicker). And the dimming itself is paint-only: without the `ExcludeSemantics` + `IgnorePointer` beside it, an un-loaded grid still announces "<date>, Free" for all 42 cells to a screen reader and still accepts taps into a day it has no data for — the positive claim of availability the `view_task` gate exists to prevent, made out loud. The caption's predicate is also over the **visible grid** and on the **duration, not the key**: `taskLoadByDay` inserts a key for a zero-length entry too, so a month whose only rows are `start == end` would otherwise suppress the caption over a blank grid.

## The today marker takes `onAccent`, never `accentInk`

**The "today" marker takes `onAccent`, never `accentInk`.** `accentInk` is the *text-on-surface* accent, derived by shifting `accent`'s lightness precisely because `accent` fails as ink — pairing the two gives about **2:1** in either brightness, and every other call site correctly pairs `accentInk` with `accentSoft`. `onAccent` (`design_tokens.dart`, modelled on `onOverdue`) computes the accent's relative luminance and returns whichever of white / near-black wins, so it follows a user-overridden accent: 4.34:1 on the stock blue — its ceiling, no foreground clears 4.5 against that hue — and 5.5:1 on the green swatch, where white would be 3.3. The full-size `task_calendar_day_cell.dart` had the same 2:1 pairing and is fixed with it.

## A new panel goes at its canonical rank

**`DashboardViewModel._hydrate` places a missing kind at its rank in `panelKinds`, not at the end.** The rule it replaced — "append, never splice" — was self-fulfilling: the hydrator appended, so front-loading a constant would have shown a panel first on a fresh install and last on every existing one, and the advice was therefore to declare it last. What made that costly is that `setFilter` calls `_schedulePersist()`, so **anyone who has ever changed the dashboard date range has a persisted `panels` array** — i.e. nearly everyone — and a new panel's declared slot was unreachable for all of them. The Invoices & Quotes panel is a strip of counts meant to be *glanced at*, and on a phone the trailing block already starts ~1150 px down, past the hero, the quick actions, the past-due card, the chart and the activity feed; appended, it would have shipped where the issue's reporter says a feature "may as well not exist". The rule has to be stated precisely, because two plausible readings are wrong. **Walk `panelKinds` in ascending canonical order; insert each missing kind immediately after the last already-placed kind of smaller rank, or at position 0 if there is none.** Anchoring on the *predecessor* rather than "before the first kind of greater rank" is what keeps a new kind below `past_due` in a save where the user dragged `past_due` down — `dashboard_view_model_test`'s hydrate fixture is exactly that arrangement, and the other reading hoists the panel to the very top. Never `loaded.insert(canonicalIndex, …)`: on a reordered save it shoves unrelated panels around, and it `RangeError`s whenever the saved list is shorter than the index — which `_hydrate`'s `catch` would swallow into a log line while silently discarding the user's whole arrangement. Ascending order matters too, or several missing kinds land in arbitrary relative positions. One property worth asserting because it is easy to lose: a save that *was* the old default now hydrates to the *new* default, so `panelsAreDefault` stays true and the manage dialog's Reset stays enabled — under the append rule it went false for every existing user the day a panel shipped. `reorderPanels`, `reorderTrailingPanels`, `togglePanelVisibility` and `resetPanels` all re-derive from `panelPrefs` or `panelKinds` on every call, so an extra kind at index 1 is transparent to their index maths.

## The Invoices & Quotes panel, and why its per-entity ids are explicit

**The consolidated panel (invoiceninja/flutter#155) is a *view* over the invoice and quote badge catalogs, and the one thing that cannot be inferred is which mode id each entity contributes to a tab.** `lib/domain/dashboard/billing_status_tabs.dart` owns the union: a `BillingStatusTab` carries the borrowed `SidebarBadgeMode` for its label and tone plus a **separate, nullable `invoiceModeId` and `quoteModeId`**, and null means "this entity does not participate". That verbosity is the whole design, because **both DAO seams fail *open*, not closed.** `badgeModeListFilter` returns null for a mode a DAO does not recognise and `watchPage` then skips its WHERE; `watchBadgeCount` does `if (extra != null) q.where(extra)` and otherwise counts **every active row** — not zero. So handing the quote-only `approved` to the invoice side would list and count every invoice in the company, and it type-checks, renders, highlights and looks entirely plausible. Of the seven tabs only `All` and `Draft` are mixed; invoices have no `sent`/`approved`/`rejected`/`expired` mode and quotes have no `unpaid`. The **order is derived, not invented**: filtered to each entity, `kBillingPipelineTabOrder` reproduces that entity's own `kListStatusTabs` order — invoices read `draft, unpaid` (their strip minus the deliberately-omitted `overdue`, which "Needs your attention" already covers) and quotes read `draft, sent, approved, rejected, expired` — so the panel can never disagree with the list its footer link lands on, and `billing_status_tabs_test` pins that in both directions plus the reverse union, which is what catches a mode added to a list catalog later that never reaches the panel. `unpaid` sits second rather than last because it is not a lifecycle *stage* (draft → sent are stages, approved/rejected/expired are terminal outcomes of a sent quote), so lifecycle order is silent about a cross-cutting money state and parking it last would cost the strip's most actionable number the most travel. A mixed tab borrows the **invoice** side's mode for its label and tone while its badge sums both populations, which is benign only because `draft` is spelled identically in both catalogs — asserted, not assumed. Three more things are load-bearing and invisible at the call site: the card needs `AutomaticKeepAliveClientMixin` (both bodies are lazily-collected `ListView`s, and it is now the *first* trailing panel on mobile, closer to the cache extent than the task calendar ever was); `narrow` is a parameter rather than a `LayoutBuilder`, because the wide grid wraps each row in `IntrinsicHeight`; and it is gated on `view_invoice` / `view_quote`, unlike its six server-fed siblings, for the same reason the task calendar is gated on `view_task` — it reads the local tables, so an ungated strip would paint seven confident zeroes as a positive claim.

## A strip of counts is payload, so it wraps

**`EntityListStatusTabs` has two layouts, and which one is right depends on whether its items carry state.** Above an entity list the strip is chrome over rows that render either way, so a tab scrolled off the edge costs a swipe: it scrolls, with the gated edge fades. Inside this panel the strip *is* the feature — its items carry the counts the whole issue asks for — so an item pushed off the edge hides **state**, which is the same argument `docs/pane-width-and-overflow.md` records for the Tasks filter chips ("a chip pushed off the edge hides an active filter") rather than the one it records for a tab strip. Seven tabs measure ~615 px against a ~334 px phone card *and* a ~570 px card in the desktop two-column band, so scrolled, four counts — including the red `Expired` — sit behind a gradient on a card the user already scrolled ~1150 px to reach. `wrap: true` shows all seven for ~44 px of card height (a third run in German or at a large text scale). It needs no breakpoint: a `Wrap` self-measures, and it is safe under the wide grid's `IntrinsicHeight` because `RenderWrap` answers intrinsics via `getDryLayout` — it is not a `LayoutBuilder`. **Selection has to change with the layout.** The 2 px bottom border takes its meaning from sitting on the strip's own rule; on the first run of a wrapped strip it floats mid-surface and reads as a stray line, so wrapped tabs use an `accentSoft` fill at `InRadii.r2` — the treatment `SidebarNavItem` already uses for this same vocabulary (a label plus a `SidebarBadge`, no rule beneath), and the one `SidebarBadge.active` exists to retune its palette against. The failure direction is then the right one for a density complaint: the strip degrades by **growing**, never by hiding. Two things landed with it that apply to every host: `_StatusTabButton` now declares `SemanticsRole.tab` + `selected` under a `MergeSemantics`, so a screen reader says "Draft, 12, selected" instead of reading seven pairs of unrelated nodes — the role is gated on `onTap != null` because it *asserts* a tap action and the strip stays laid out but untappable during multi-select.

## A tabbed card is the one place the generic empty string is right

**Every other dashboard card names what it has none of — `no_invoices_due_soon`, `no_payments_yet` — and the Invoices & Quotes panel deliberately does not.** The house rule exists because a single-purpose card's title is the only context an empty body has, so "No records found" there leaves the reader to work out what was being counted. A tabbed panel has the answer on screen: the selected tab is highlighted directly above the empty area, so the generic string reads in context, and six per-tab strings would restate a label the user is already looking at. (`_app_pending.json` can only *add* keys, never override one, so a per-tab set is also unusually hard to walk back.) The exception stops exactly there: **`Rejected` keeps its own two-line hedge**, because that tab is local-only until BACKEND.md § F1 ships and an empty body there genuinely does not mean the company has none — which is the case the honesty rule was written for. `BillingStatusTab.isLocalOnly` selects it, and it is a property of the **tab** rather than something the widget derives: asking `statusTabServerFilters` directly answers null for `All` too — whose `kBadgeModeTotal` simply has no `ListStatusTabSpec` — so a derivation at the call site labelled an ordinary unnarrowed server page "not synced yet" on any single-module company, which is the bug this shape closes.

## Most recent needs a tie-break, and epoch 0 leads

**`date` is date-only, so "the five most recent" is decided by the tie-break, and both obvious tie-breaks are wrong.** Every document a company issued today ties on `date`, and `watchPage`'s backstop is `OrderingTerm(expression: e.id)` — a hashid, **ascending, regardless of `sortAscending`** — so the panel's top five would have been an arbitrary, effectively-oldest five. `tieBreakField` (+ `tieBreakAscending`) is the fix, and four properties are load-bearing. It **appends** rather than replacing: rows can tie on both keys (a bulk import shares a date and a whole-second `created_at`), and without the final `id` the order is non-deterministic, so `distinctRows()` can flap between emissions and the cross-entity merge stops being reproducible. It carries **its own direction**, since the `id` backstop's is fixed. It is validated **eagerly** — drift invokes the `orderBy` generators inside `orderBy()`, so an unmapped field throws `ArgumentError` at the `watchPage` call site rather than inside a stream nobody has listened to yet. And **`created_at == 0` must sort FIRST, not last**: the column is `withDefault(0)` and `<Entity>EditViewModel` stamps epoch 0 on a local create, so a plain `created_at DESC` puts the invoice the user just made offline at the *bottom*, where a five-row window drops it entirely. The expression maps 0 to the max signed 64-bit value; `NULLIF(created_at, 0)` is the idiomatic-looking version and is **wrong**, because SQLite ranks NULL below every value and under DESC those rows sort last — the same bug by a prettier route. The Dart-side merge (`compareRows`) restates the identical total order, since merging two individually-correct top-Ns and truncating is only the overall top-N when both halves agree; `billing_recent_order_test` pins the SQL half and `billing_pipeline_merge_test` the Dart half, and each has a case that fails without the epoch-0 rule. One consequence of the panel being Drift-backed: its per-tab top-up passes `ignoreCursor: true` on **every** call, including the unnarrowed ones, because an unnarrowed fetch is not a "narrowed fetch" and `shouldReadCursor` would otherwise send the `updated_at >=` watermark and return a delta rather than a true first page — which would leave the local-only `Rejected` tab with no mechanism at all to pull rejected quotes into the cache.
