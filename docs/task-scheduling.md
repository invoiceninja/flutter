# Task scheduling — booked blocks and starting the timer

Companion to CLAUDE.md § Tasks layout view (the booked-block rule). A task carries no stored start time, so scheduling one means seeding a future `time_log` entry — which makes "start the timer" a decision rather than an append. Pinned by `test/lint/task_start_rules_test.dart`.

## A booked block and a finished session are the same four wire slots

**A booked block and a finished session are the same four wire slots, so "start the timer" is a decision, not an append.** A task carries no stored start *time*: scheduling one means seeding a **future `time_log` entry** (`line_item_task_seed.dart` for a quote line — invoiceninja/flutter#88 — and `calendar_event_seed.dart` for a converted event), which is also what puts it on the calendar / daily / weekly / dashboard-panel grids, since `TaskDay.day` is the local date of the earliest start. `lib/domain/tasks/task_schedule.dart` is the one place that tells a *booking* from *worked time*, every start path routes through its `planTaskStart`, and `Task`'s `scheduleStateAt` / `workedTime` / `bookedTime` / `lateByAt` are the only way UI should ask — they bind the two fields the rules need, and passing a bare `timeLog` silently drops the anchor everything below turns on. Eleven things are load-bearing. **The server rejects two of the three logs a naive append produces**, and `Request::checkTimeLog` (`app/Http/Requests/Request.php`) is the whole contract: an inverted entry, an overlap, and — the non-obvious one — **a zero-end entry followed by anything once sorted by start**. So Resume at 09:30 on a block booked 09:00–11:00 overlaps, and Start at 09:00 on one booked 14:00–16:00 is running-not-last: both 422, both leave a dead outbox row, and **a running timer therefore cannot coexist with an unfinished booking at all**, which is why claiming is the only legal way to start such a task and why two unfinished bookings are refused outright. `planTaskStart` validates its own output against that port and downgrades to `blocked` rather than trusting the reasoning — the first thing that caught was a *worked* block spanning `now`, where appending lands a running entry inside it. **The third case is worse because it succeeds.** Once a booking's window has passed, appending IS legal, so there is no 422 and no banner — the log just keeps a block nobody worked, and `Task.billableDuration` counted it onto the invoice. Hence `TaskScheduleState.late`, and hence `billableDuration` and `loggedDuration` **both** delegating to `workedDuration`: a booking contributes nothing to either, and `loggedDuration` counting it was what made one booked task read `09:00` on a phone and `2:00` on a desktop, and an unstarted job read `Duration 2:00 / Estimated 2:00` — "done". `taskInvoiceNotes`, `ProjectProgressCard.buildCumulativeSeries` and `TaskWeeklyViewModel.secondsFor` skip a booking for the same reason. **`stop > now` is NOT the booking test, and getting that wrong is the sharpest trap here.** It cannot tell a plan from work that simply ends later today — and the app manufactures the second kind by default: `weekly_merge.dart` synthesizes every weekly-grid cell at local **09:00**, so "8" typed into today's column is `09:00–17:00`, and `TaskRepository::roundTimeLog` reaches the same shape server-side by rounding an entry's end *up* when `task_round_to_nearest > 1`. Treated as bookings, both billed **zero**, listed under Upcoming, refused every further edit to that cell, and — worst — were *claimed*, which rewrites the block's start to `now` and destroys the logged work. So `_isBooking` takes `start > now` as unambiguous and requires the task's **`due_date` anchor** for the straddling case; the app writes `due_date` whenever it books and nothing else does. `late` is narrower still (one entry, on the due date, **matching `estimated_duration`**) because a false positive there offers to discard real work — which is also why claiming it prompts, and why the prompt names the duration it will replace. **There is nowhere to mark an entry "planned"**: both task requests cap an entry at four elements and `TaskMeta` is a closed one-field DTO, so the plan lives in `tasks.due_date` (DATE — **no** time-of-day) and `tasks.estimated_duration` (seconds), which both scheduling sheets write beside the block. **That pairing is what makes claiming non-destructive** — the promised duration and day survive, the promised clock time does not, and that loss is permanent and accepted. **Sorting happens at the DOMAIN boundary** — `Task.fromApi`, `_apiToCompanion`, and `TaskRepository.save`/`create` — never inside `TimeEntry.encodeLog`: `_domainToCompanion` writes the `is_running` column from the in-memory list's `.last` and the `payload` from `toApiJson`, and `_fromRow` rebuilds out of that payload, so a sort in the encoder desyncs them and `watchRunning` counts a timer `stopRunningTimer` then refuses to stop. `sortTimeLog` drops a null start (a wire `0`), which means `timeLogProblem` judges the log **as it will be sent**; it also tie-breaks on the original index, because `List.sort` is unstable where the server's `usort` is stable. **Four start paths, not two** — the repository primitive (inline toggles + bulk), the ⋮ menu's Start and Resume, and the edit screen's own draft-level button — and `Resume` may only appear where there is worked time to resume. **Feedback is captured before the first await**: claiming removes the row from the Upcoming tab's own query and swaps the shell pill's body out, so the widget that started the timer is unmounted *by its own write* — reading `context` afterwards dropped the toast and its Undo. Undo restores `time_log` + `status_id` through a targeted primitive, never a whole-record `save`, which would revert any field a sync landed meanwhile. The status move to **In progress** lives in `TaskActions`, not the repository (`builtInTaskStatusKey` is a `lib/ui` symbol and `layering_test` forbids reaching it from `lib/data`), so bulk never moves a status. **Bulk admits exactly what `startTimer` writes without a prompt** (`append` and `claim`) — note `EntityListScreenScaffold` always passes `ids`, so `applyBulkAction`'s skipped count is zero regardless and an ineligible row is dropped from the selection silently. And the **`upcoming` tab means *booked ahead***: its SQL reads the last entry's **start** (`$[#-1][0] > now`), not its stop, which is what dragged today's timesheet rows in; the nested `CASE` is structural rather than defensive, since the server sends `time_log: ''` for an empty log and SQLite does not guarantee short-circuiting inside one condition. A live or late booking is deliberately *not* in that tab — it surfaces on its row and, for a live one, on the shell pill. `test/lint/task_start_rules_test.dart` pins the paths, the Resume gates, the slot swap and the single Start glyph (#153: `stop_circle_outlined` has no un-circled sibling, so the pair settles circled).
