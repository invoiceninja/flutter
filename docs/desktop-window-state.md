# Desktop window state

Each desktop runner persists window size, position, and fullscreen across launches via the host OS's native preference store. No Dart or Flutter package involvement — the goal is one short native function per platform, idiomatic to that platform's APIs. **N/A on web** — the browser owns the window chrome; there is nothing to persist.

> **Linux status:** the runner ships (`linux/`, distributed as a Snap — see `docs/setup.md`) and the **hidden title bar is done** (§ Desktop hidden title bar). Window-STATE **persistence is still not done** — the `setup_window_state_persistence()` / `GKeyFile` references below are the plan, not the current state.
>
> **Windows status:** the runner ships (MSIX / Microsoft Store) and **both halves are done** — window-state persistence (below) and the frameless title bar (§ Desktop hidden title bar).

**Contract** — every desktop runner does the same three things:
1. Read saved state at window-construction time, before the window is shown.
2. Write on every geometry change (move / resize) and on every fullscreen transition completion.
3. Fall back to the platform-native default frame on first launch (the values declared in the platform's window template — XIB on macOS, manifest / template on Windows, default size call on Linux).

**macOS** — `macos/Runner/MainFlutterWindow.swift` → `setUpWindowStatePersistence()`. Frame via `NSWindow.setFrameAutosaveName` (NSUserDefaults key `NSWindow Frame InvoiceNinjaMainWindow`, derived by AppKit); fullscreen bool via `NSWindowDelegate.windowDidEnter/ExitFullScreen` → NSUserDefaults key `ninja.window.isFullscreen`. `isRestorable = false` to keep AppKit's autosave as the only mechanism (otherwise Cocoa state restoration would override it after `awakeFromNib`).

**Windows** *(done)* — `windows/runner/win32_window.cpp` → `SavePlacement()` / `RestorePlacement()` (private members of `Win32Window`; the window lifecycle lives there, not in `flutter_window.cpp`). Raw `WINDOWPLACEMENT` (normal-rect + maximized in one struct) as `REG_BINARY` under `HKCU\Software\InvoiceNinja\Window\Placement`. **Save** on `WM_EXITSIZEMOVE` (end of an interactive drag — debounces the per-tick `WM_SIZE`/`WM_MOVE` spam), on non-interactive `WM_SIZE` `SIZE_MAXIMIZED`/`SIZE_RESTORED` (caption-button maximize emits no exit-size-move), and on `WM_DESTROY` (last chance, hwnd still valid). Saves are armed only after restore ran — the `WM_SIZE` fired inside `CreateWindow` would otherwise clobber the stored value before it was read. **Restore** in `Create()` before `OnCreate()` — restore-before-show, so the Flutter surface is created at its final size (no startup resize flicker; the `setFrameAutosaveName` parity point). Off-screen guard: `MonitorFromRect` + `IntersectRect` against the nearest monitor's work area; no intersection → template defaults. Minimized-at-exit normalizes to a normal restore; a maximized exit re-applies via `Show()`'s `SW_SHOWMAXIMIZED`. The `Fullscreen` DWORD is still deferred, but the reason has changed: the frameless work has landed, so an F11 mechanism is now *reachable* (cache the placement + style, clear `WS_OVERLAPPEDWINDOW`, `SetWindowPos` to `rcMonitor` with `SWP_FRAMECHANGED`). It is simply not built — there is no F11 binding anywhere in `lib/`, `WindowChrome.fullscreen` is macOS-shaped, and `SavePlacement` would first have to learn not to persist a fullscreen rect as the normal one. Tracked separately, not blocked.

**Linux** *(when added)* — `linux/runner/my_application.cc` → `setup_window_state_persistence()`. Connect `configure-event` (geometry) and `window-state-event` (fullscreen / maximize); persist to `<g_get_user_config_dir()>/invoice_ninja/window-state.ini` via `GKeyFile` — resolve the directory through the API, never a literal `~/.config/...`, because snap confinement remaps `$HOME` into the snap's own tree. Note `gtk_window_move` is a no-op on Wayland, so position can only ever be restored on X11. Restore in `activate` via `gtk_window_set_default_size` + `gtk_window_move` + `gtk_window_fullscreen` as appropriate.

## Desktop hidden title bar

Every desktop platform hides the OS title bar and integrates the window controls into the app chrome. The goal is the same everywhere; the **implementation diverges** because macOS keeps its real controls while Windows/Linux do not (see the divergence note below). macOS is wired today; Windows/Linux follow this contract when their runners are added.

**Shared Flutter layer** (platform-agnostic):
- `Env.isDesktop` (`lib/app/env.dart`) — the single "is this desktop" gate.
- `NativeWindow` (`lib/app/native_window.dart`) — bridge over the `invoice_ninja/native_window` method channel, mirroring the `native_window_theme` bridge; no-op off desktop. Method set: `startDrag`, `doubleClick`, `minimize`, `toggleMaximize`, `close`, `setContentSize`, `setWindowButtonsHidden`, `windowChrome`. It also listens the *other* way: `listenForNativeEvents()` (called once from `main.dart` before `runApp`) installs the handler for the runner's `windowChromeChanged` push and then seeds `NativeWindow.chrome`, a `ValueNotifier<WindowChrome>` the caption strip watches. `WindowChrome` carries `fullscreen`, `captionHeight`, `buttonsCenterY` and `buttonsTrailingX` in points from the window's **top-left**; its defaults are the classic 28 / 14 / 70, so any platform that never reports behaves as it did before the measurement existed.
- `WindowCaptionStrip` (`lib/ui/features/shell/widgets/window_caption_strip.dart`) — the draggable caption strip at the top of the sidebar (and narrow-layout column). Its optional `trailingBuilder` hosts app chrome *inside* the caption row, aligned to the trailing edge; `WindowCaptionStrip.hostsCaptionRow()` is the one predicate a caller gates that on (content handed to a platform with no caption row asserts rather than silently vanishing). It is a **builder, not a widget**, because the strip owns the measured band and hands the height down — a caller sizing itself from its own constant is the split brain that misaligned the arrows once already.
- `WindowFrame` (`lib/ui/features/shell/widgets/window_frame.dart`) — the **full-width app-painted title bar** on the frameless Windows/Linux runners, wrapped around the whole routed app in `main.dart` (a passthrough everywhere else). Its leading segment mirrors the sidebar rail's width and colour and carries the **app mark and wordmark** — a frameless window otherwise loses the icon and name the OS caption used to show. The nav arrows sit just past that segment's divider, at the same 10-px inset on its other side: squeezing both the wordmark and the pair into 232 px overflows once the wordmark grows at a large text scale. `WindowControls` sits trailing; everything between is drag region.

  **Everything decorative in the band must be wrapped in `IgnorePointer`, and that is not defensive.** `RenderDecoratedBox.hitTestSelf` returns `decoration.hitTest(...)` — true anywhere inside a plain rectangle — and `RenderParagraph` hit-tests itself so it can dispatch `TextSpan` recognizers. A `Stack` stops at the first child that hits, so an unwrapped segment or wordmark silently swallows every press over it: the rail-coloured stretch of the title bar stops dragging the window, and a drag test that probes the middle of the band never notices. Both are pinned by `window_frame_test.dart`.

  **Fullscreen:** Windows has no F11 mechanism, so maximized is the only case and the runner reports `fullscreen: false`. A window manager can fullscreen the Linux window, and the band deliberately stays visible there — it is the only window chrome left, so hiding it could strand someone who does not know their WM's keybinding.
- `WindowControls` (`window_controls.dart`) — the drawn min/max/close cluster, 46×32 per button. Not needed on macOS, which keeps its real traffic lights.
- The three platform predicates and `kAppTitleBarHeight` live in `native_window.dart` — a leaf both `in_sidebar.dart` and `window_frame.dart` already sit below, so neither has to import the other.

**Channel method set** — `startDrag` (begin a native move-drag), `doubleClick` (title-bar double-click action), `minimize`, `toggleMaximize`, `close`, `showSystemMenu` (**no arguments** — Windows only; the band is client area once the frame is custom, so a right-click never arrives as `WM_NCRBUTTONUP` and has to be routed from Dart. It deliberately carries no coordinates: Flutter's `globalPosition` is logical and client-relative while `TrackPopupMenu` wants physical screen pixels, and both errors nearly vanish on a maximized window at 100% scale — i.e. exactly where anyone would first try it. The runner reads `GetCursorPos()`, the right anchor by construction. Linux returns `NotImplemented`, which `NativeWindow._invoke` swallows, because GDK's own `gdk_window_show_window_menu` needs a live `GdkEvent` a channel call does not have), `windowChrome` (Dart -> native, returns the measured chrome payload below), plus the Debug Panel screenshot tools: `setContentSize` (resize the content area to `{width, height}` logical points preserving the visual top-left, exiting fullscreen first if needed; returns the achieved `{width, height}` so Dart can detect clamping — AppKit constrains the frame to the visible display, so a screenshot size larger than the screen clamps and surfaces via the returned size, which the Debug Panel warns on) and `setWindowButtonsHidden` (`{hidden}` — toggle the native window buttons; **deliberately never persisted**, so every launch starts with visible buttons). macOS implements `startDrag` + `doubleClick` + `windowChrome` + the two screenshot methods (its native buttons cover the rest). Windows and Linux implement the whole set, with two deliberate differences: `setWindowButtonsHidden` is a **no-op that returns success** (the cluster is Flutter's own, so hiding it is a Dart-side concern — returning `NotImplemented` would log an error on every Debug Panel toggle), and `setContentSize` does **not** clamp the way AppKit does. `SetWindowPos` is not screen-constrained, so an over-large screenshot size actually applies on Windows; `gtk_window_resize` is a request the WM must ack, so Linux reports the requested size back. The Debug Panel's clamp warning is therefore macOS-only in practice — that asymmetry is intended.

**Native -> Dart pushes** — `windowChromeChanged`, carrying `{fullscreen, maximized, active, captionHeight, buttonsCenterY, buttonsTrailingX}`, sent by macOS from `windowDidEnterFullScreen` / `windowDidExitFullScreen` and after `setWindowButtonsHidden`; by Windows from `WM_SIZE` (maximize/restore), `WM_ACTIVATE`, `WM_DPICHANGED` and the settings/display changes; and by Linux from `window-state-event`.

Three field rules the runners must honour, each silent if broken. **`maximized` and `active` are pushed, never inferred** — Aero Snap, a title-bar double-click and Win+Up all change maximized state without going through Dart, so a bool toggled beside `toggleMaximize()` desyncs on the first snap. **`active` is the one flag defaulting to `true`**, so `WindowChrome.fromMap` cannot parse it with the `== true` shape the others use — an absent key would report every window as unfocused and permanently dim the drawn glyphs. And **Windows/Linux must send `buttonsTrailingX: 0` explicitly**: `fromMap` falls back to the macOS default of 70 when the *key is absent* and only preserves a zero that was actually sent.

**The frameless runners do NOT report a caption height.** `captionHeight` measures a real OS titlebar the app must fit inside; once Windows and Linux are frameless there is none left to measure, so the band is `kAppTitleBarHeight` (32) in Dart. Reporting it would also make the first frame lay out at one height and the second at another — a visible jump on every cold start, worst on `/login`. The `windowChrome` pull is **not** redundant with it: `setUpWindowStatePersistence()` runs before the channel is even created, and its restore-fullscreen `toggleFullScreen` fires the delegate on a later main-queue turn — possibly before Dart installs a handler — so a launch straight into fullscreen has no push to catch. `listenForNativeEvents()` installs the handler first, then pulls, so nothing lands in the gap. An unknown method name is ignored rather than thrown back, so a newer runner can't break an older app.

**Why the chrome is measured and never hardcoded.** `windowChromeMetrics()` reads `contentView.bounds.height - contentLayoutRect.height` for the band and unions the three `standardWindowButton` frames for the buttons, flipping AppKit's bottom-left origin to Flutter's top-left. That is not ceremony — **macOS 26 redesigned the window controls**, and a constant that was right for a decade silently went wrong:

| `windowChromeMetrics()` reports | macOS 26.4.1 | 10.15 – macOS 15 |
|---|---|---|
| `captionHeight` (titlebar) | **32 pt** | 28 pt |
| `buttonsCenterY` | **16 pt** | 14 pt |
| `buttonsTrailingX` (frame union) | **69 pt** | ~66–70 pt |

The macOS 26 column is what AppKit actually returned on a real window, not an estimate. Screenshot measurement of the same window shows why it moved: the visible buttons grew from 12 pt to 14 pt and their spacing from 20 pt to 23 pt.

With `MACOSX_DEPLOYMENT_TARGET = 10.15` the app ships to both columns, so **no single constant is correct** — a hardcoded 28 put the sidebar's nav arrows 2 pt above the buttons on macOS 26, and hardcoding 32 would put them 2 pt below on everything older. The strip therefore centres its content on the reported `buttonsCenterY` rather than on the middle of the band: AppKit centres the buttons in the titlebar on every release to date, but that assumption is the one that broke, so the alignment target travels explicitly. `window_caption_strip_test.dart` pins both columns of the table.

**macOS** *(done)* — the "full-size content" look: no title-bar strip, the FlutterView fills the window, and the **real** traffic-light buttons float over its top-left (the top of the sidebar). `MainFlutterWindow.swift` → `configureHiddenTitleBar()` sets `titleVisibility = .hidden`, `titlebarAppearsTransparent`, `titlebarSeparatorStyle = .none` (macOS 11+), `styleMask.insert(.fullSizeContentView)`. The window stays `.titled` so the system buttons exist and keep their automatic active/inactive graying; `self.title` is retained for Mission Control / the Window menu. `WindowCaptionStrip` reserves the measured `captionHeight` (see the table below) and calls `startDrag` → `NSWindow.performDrag(with:)` and `doubleClick` → the user's configured action. The dead space to the buttons' right is not wasted: the sidebar's expanded persistent rail passes `NavHistoryButtons` as the strip's `trailing`, so the back/forward arrows sit at the rail's trailing edge on the buttons' own centre line instead of costing a row of their own below. (The strip hands the pair its height through `trailingBuilder`, and `NavHistoryButtons.height` applies it as a *pinned* `fixedSize`, not a floor. Left to its own sizing it measures 32, which grows the band and lands it below the buttons it should be level with; `visualDensity: compact` does not shrink it, so don't assume it will. The collapsed 64-px rail and the mobile drawer keep the arrows in their own row — the rail is narrower than the traffic-light span itself, and the drawer has no strip.) The 28-px reservation and the drag handle both drop when no real buttons are floating there — fullscreen (they move to the auto-hiding menu bar) or the Debug Panel's `setWindowButtonsHidden` — leaving a bare strip collapsed to zero and a hosted row shrunk to its content, with no jump in where the arrows live. Traffic-light glyph + inactive-gray color follow the themed `NSAppearance` set in `apply(_:)`. No drawn controls — `minimize`/`toggleMaximize`/`close` are unused here.

**Windows** *(done)* — `win32_window.cpp` keeps `WS_OVERLAPPEDWINDOW` **exactly as it was** and handles `WM_NCCALCSIZE` by letting `DefWindowProc` compute the standard frame and then restoring only `rgrc[0].top`. Keeping the styles is the whole trick: Aero Snap, the minimize animation, the DWM shadow, Win11 rounded corners, Alt+Space and the taskbar thumbnail all key off them rather than off who painted the caption — and because `AdjustWindowRectEx` is unchanged, the persisted `WINDOWPLACEMENT` **needs no migration** (a stored window rect still means what it meant; upgrading users keep their geometry and gain the band's height as content). Left/right/bottom keep the default proc's insets, which *are* the invisible resize border, so three edges stay natively hit-tested for free.

Four things that are silent if dropped:
- **A maximized window's rect is the work area grown by the frame**, so the top ~8 px of the Flutter surface renders off-screen unless the client top is inset by `SM_CYSIZEFRAME + SM_CXPADDEDBORDER` (`ApplyMaximizedInsets`).
- **A maximized frameless window covers an auto-hide taskbar** and makes it unreachable — probe `ABM_GETSTATE` then `ABM_GETAUTOHIDEBAREX` (monitor-aware; the older `ABM_GETAUTOHIDEBAR` only ever answers for the primary monitor) per edge and leave 1 px. `WM_SETTINGCHANGE` / `WM_DISPLAYCHANGE` force a `SWP_FRAMECHANGED` recompute, or toggling auto-hide while already maximized leaves the stale inset.
- **`DefWindowProc` does not consult `WM_NCCALCSIZE`** — it still reports `HTCAPTION` / `HTMINBUTTON` over the reclaimed strip, so without `WM_NCHITTEST` the top of the Flutter surface is dead to the mouse and drags the window on every click.
- **`startDrag` must `PostMessage(WM_SYSCOMMAND, SC_MOVE | HTCAPTION, …)` with the real cursor position**, not `SendMessage(WM_NCLBUTTONDOWN, …)`. The cursor position is what makes dragging a maximized window down restore it *under* the cursor. `PostMessage` is what keeps the OS move loop out of the embedder's task-runner callback — `SendMessage` spins that loop with a platform task still on the stack, so a Dart→platform call arriving mid-drag runs *inside* the drag (`BeginDrag` can re-enter itself) and the channel reply is withheld for the whole gesture. Posting also leaves the OS owning the down/up pairing, so there is no swallowed button-up to synthesize back to the Flutter child.
- **Focus comes from `WM_ACTIVATE`'s own `wparam`, never from `GetActiveWindow()`.** The handler calls `SetFocus(child_content_)`, which is documented to activate the window receiving focus (or its parent) — so sampling afterwards reads a *deactivation* back as active, and because the chrome push dedupes, that wrong value latches until an unrelated `WM_SIZE`. The drawn glyphs would never dim, which is the one state the flag exists to show. `SetFocus` therefore also runs only when actually activating.

`DwmExtendFrameIntoClientArea` is **not** needed: that recipe exists for the other branch (returning 0 with `rgrc[0]` untouched), and keeping the L/R/B frame means DWM still shadows the window. `DWMWA_CAPTION_COLOR` / `DWMWA_TEXT_COLOR` are now structurally dead (there is no caption), so `titleHex` is ignored on Windows permanently; `DWMWA_BORDER_COLOR` is deliberately *not* called either, because the default border goes accent-coloured on focus and grey when not — a focus affordance the app cannot reproduce. **Snap Layouts** (the Win11 flyout on hovering maximize) is a deliberate deferral: it needs `HTMAXBUTTON`, which hands the OS all mouse input over that region, forcing hover from `WM_NCMOUSEMOVE`, clicks from `WM_NCLBUTTONDOWN`, and the button's rect to be published from Dart on every layout. Win+Z, drag-to-edge and Win+arrow all still work. A **kill switch** (`IN_DISABLE_CUSTOM_FRAME=1`, or a `CustomFrame` DWORD of 0 beside the placement value) restores the stock caption without a new build — worth having because a frameless window whose Flutter chrome fails to render has no close button at all.

**Linux** *(done)* — `my_application.cc` replaces the `GtkHeaderBar` with **an empty, zero-height widget passed to `gtk_window_set_titlebar`** — deliberately **not** `gtk_window_set_decorated(FALSE)`. They are not two spellings of the same thing: `set_titlebar` is what turns client-side decorations *on*, which keeps the drop shadow, rounded corners, `_GTK_FRAME_EXTENTS`, the automatic `.maximized`/`.tiled` handling and, decisively, **GTK's own resize handles**. `set_decorated(FALSE)` leaves `client_decorated` false, so GTK's edge hit-testing short-circuits and there is *no mouse resize at all* until eight edges (and their cursors) are reimplemented over Flutter's pointer stream — and on Wayland it is worse, since no server-side decorations exist to fall back to, leaving the window neither movable nor resizable. How much CSD buys depends on the compositor, and it is worth being precise rather than optimistic: `set_titlebar` first evaluates `gtk_window_supports_client_shadow()`, which requires an RGBA visual **and** `gdk_screen_is_composited()`. With a compositor you get wide invisible handles on all four edges, a drop shadow and rounded corners. Without one (i3, openbox, VNC, some remote-desktop sessions) GTK falls back to `.solid-csd`: square corners, no shadow, and a resize border on the order of a single pixel. A small application-priority CSS provider flattens the `.titlebar` node, or a theme can still allocate it a minimum height. It must run **before `gtk_widget_realize`** (set_titlebar on a realized window unrealizes it).

This also collapses the old GNOME-vs-other-WM `use_header_bar` branch, which now decides nothing — delete the `GdkScreen*` locals **and** the `<gdk/gdkx.h>` include together, since `linux/CMakeLists.txt` sets `-Werror`.

Two non-obvious rules: **`startDrag` needs a cached grab serial.** Channel calls dispatch *outside* `gtk_main_do_event`, so `gtk_get_current_event()` returns `NULL`; X11 usually tolerates a zero timestamp but **Wayland's `xdg_toplevel.move` requires a real serial and the compositor may simply drop the request** — the band silently would not drag on GNOME Wayland. `gdk_event_handler_set` caches the last `GDK_BUTTON_PRESS` (it is process-global and singular; no current plugin uses it). And **every flag in the `window-state-event` handler must be read out of `event->new_window_state`, never off the window**: the signal is `G_SIGNAL_RUN_LAST`, so a handler installed with `g_signal_connect` runs *before* `GtkWindow`'s class closure — and that class closure is what assigns `priv->maximized`. `gtk_window_is_maximized()` there returns the **previous** value on every maximize, restore and snap, which is exactly the desync the pushed field exists to prevent. (The `windowChrome` *pull* path has no such constraint and reads the window directly.) The handler must also **`return FALSE`** — returning `TRUE` stops propagation, and GTK's own CSD handler needs that event to apply the `.maximized` class and drop the shadow when tiled, i.e. to perform the very update this handler declines to read. `maximized` itself ignores the tiled bit — a half-snapped GNOME window is `GDK_WINDOW_STATE_TILED` and must not offer "restore" — but `TILED` stays in the *change* mask, because a snap moves focus without moving maximized.

Window-state persistence is still **not** done here. When it is: use `g_get_user_config_dir()`, **not** a literal `~/.config/...` — under snap confinement `$HOME` is remapped into the snap's own tree. Note also that `gtk_window_move` is a no-op on Wayland, so it can only ever be "size + maximized everywhere, position on X11 only".

**Divergence note** — macOS keeps the *genuine* system buttons (so active/inactive graying, accessibility, and the system menu are free); Windows/Linux become frameless, which deletes the native buttons, so the app must **draw its own** (top-right) and handle window resize itself.

**Do not "finish" this by widening `WindowCaptionStrip`.** An earlier version of this checklist said to *drop the `SizedBox.shrink` early-return in `WindowCaptionStrip`* for Windows and Linux. **That is now wrong and would ship a double bar**: those platforms get the full-width `WindowFrame` above the router instead, and the narrow layout still mounts the strip (`scaffold_with_nav.dart`), so widening it puts a second band inside the first. The strip stays macOS-only; its own `hostsCaptionRow is true only where the title bar is hidden` test doubles as the guard, alongside `test/lint/window_chrome_wiring_test.dart`.

**Why the bar is full-width rather than mirroring macOS.** The original sketch floated the drawn controls top-right *over the content*. Every entity list, every detail screen and the wide dashboard already draw their own actions there, so the window buttons would land on top of them and each screen would need a bespoke inset. A full-width band pushes every screen down instead — and it has to wrap the **router**, not the shell, because `/login`, `/lock`, `/setup`, `/signup`, `/too-old`, the calendar callback and go_router's `errorBuilder` screen all render outside `ScaffoldWithNav`; a frameless window with chrome only inside the shell would be unmovable and unclosable on all seven.
