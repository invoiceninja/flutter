# The list search field

Companion to CLAUDE.md § List state filter. That section owns what the lifecycle filter may *hold*; this doc owns the box that edits every filter — `TokenSearchField` and its popup (`lib/ui/core/list/search/`): where the popup lands, what a key press does, what Enter is allowed to commit, and why the list header grows around it. CLAUDE.md is at its size cap, so these rules are indexed from `docs/README.md` rather than from a bullet there.

Everything below shipped broken first and was found by reading, because **nothing pumped the wide field** — `token_search_field_test.dart` covered the parser and the chip and said so. `test/ui/core/list/search/_token_search_harness.dart` is the harness that now does; § Testing the field says what it has to get right.

## The popup is placed in the layout pass, from the input

**The suggestion menu is positioned by `OverlayPortal.overlayChildLayoutBuilder`, and the portal wraps the *input*, not the whole box.** The report was "the popup often appears too far over", and it was four bugs with one root. The menu was positioned inside a plain `overlayChildBuilder`, which runs in the **build** phase, from `RenderBox.localToGlobal` and `RenderEditable.getLocalRectForCaret` — i.e. from the *previous* frame's layout. Measured against that code with the harness, on a 700 px box:

| Flow | Menu left edge | Should be |
|---|---|---|
| Re-open on existing text (`acme corporation`, click at its end) | 550 | 287.5 |
| Edit a chip (`name:acme` written in the same frame) | 715 | 569 |
| Backspace away a chip with the menu open | 639 | 457.5 |

The first is an anchor bug (it hung from the **caret**, so a text-width right of the token), the second is the stale frame, the third is an anchor captured once and never refreshed.

`overlayChildLayoutBuilder` runs its builder during **layout**, with the portal child's rect already in the hosting Overlay's coordinates (`info.childPaintTransform`). That also deletes the hand conversion from global coordinates that existed because the list's Overlay starts at the sidebar's width, not at 0. Two things are load-bearing. **The portal must wrap the thing being measured.** The SDK guarantees the child's own rect and every ancestor's are final when the callback runs; it does not promise the child's interior. The search box is an ancestor of the input, so reading it alongside is safe — reading the input from a portal around the *box* is not. **The callback does geometry only.** No `setState`, no `OverlayPortalController.show()/hide()` (both assert there), no notifier writes; the cached anchor fields are plain assignments. The menu subtree is built once per `_buildWide` and handed in, so a re-run caused by the box moving (a resize, a page scrolling under an embedded list) repositions it without rebuilding it. The portal carries a `GlobalKey` because it is a child of a `Wrap` whose earlier children — the chips — come and go; without one its State, and the open menu, would be torn down on every chip.

The comment this replaced said `CompositedTransformFollower` had been rejected because it broke `TapRegion` hit-testing. `TapRegion` decides inside/outside from the hit-test path and never calls `globalToLocal`; a `Positioned` in the layout builder gives the menu a real offset, which is all it needs.

## The placement rule is one pure function

**`placeFilterMenu` (`filter_menu_placement.dart`) is the whole rule, with no widgets in it.** The menu's row *content* starts at the anchor (so the painted edge is `kMenuRowInsetLeft` before it); it never leaves the search box horizontally when the box is at least as wide as the menu, and falls back to the Overlay's extent when it is not; RTL mirrors, hanging the menu's *end* from the token start; height is capped to the room above the soft keyboard. It flips above the anchor only when below has room for fewer than about three rows and above has more — and the side is **latched for as long as the menu is open**, or a rising keyboard flips it mid-aim. The keyboard overlap is measured against the Overlay's own bottom edge in global coordinates, not read off `MediaQuery.viewInsets` at the field: a `Scaffold` between the two may or may not have consumed the inset, and only the ones *above* the Overlay shrank it. The per-chip segment popups use the same function with `containInField: false`; they used to clamp on the left only.

## The anchor holds while a multi-select list is being ticked

**x is re-captured when the menu opens and when the applied chips change, and held while a `checkboxMultiSelect` list is open.** Typing never moves the start of the token, so there is nothing to chase — but ticking a row widens that key's chip, which pushes the input right, and a menu that followed would slide out from under the pointer mid-click. y is held too from a tick made by tap or click until the next key press (`_pointerTicking`) and follows the box otherwise. That flag is set where the tick is handled, which knows what made it — not read off `FilterSuggestionController.movedByKeyboard`, which is true for every fresh list until a mouse *moves* and so reads "keyboard" for every touch tap. The chip anchor (a pinned picker opened from a chip) is cleared whenever the pin clears; it used to outlive it and leave the filter list under the old chip.

## Focused text is the search, and a matched key is not

**One predicate decides "the user is building a filter": `TokenSearchController.parseInput().matchedKey != null`.** It is pin-aware, and it replaced `text.contains(':')`, which was wrong in both directions: `INV:001` contains a colon and is a search, while text typed into a pinned Status picker contains none and is not — it used to live-search the list behind the picker, and stayed applied after a tick and a click away. Three more consequences. **Emptying the box clears the search**; the live commit used to be gated on non-empty text, so backspacing a term away left the list filtered by its last letter. **`setSearch` cancels its debounce before its no-op return** (and `clearAllFilters`, a restored snapshot and a deep link cancel it too): typing `status:` at normal speed left `statu` armed, and it fired a quarter-second later under the open value list. And **a click that starts a filter clears the search explicitly** (`_dropBoxText`) rather than through the text listener — on desktop a text field unfocuses on any tap outside itself, a menu row included, and the listener only writes the search for a focused field.

**A typed prefix resolves only to a key the picker would offer** (`typeableKeys`: available and not locked). `client:` typed on a client's own Invoices tab used to add a second client beside the parent scope and empty the list; a hidden custom column applied a filter with no chip.

## Enter commits a row only if the rows are for this text

**Published rows carry a stamp of the input they were built for, and `commit(expecting:)` refuses a mismatch.** Rows are published in a post-frame callback, so for one frame they belong to the previous text. A barcode scanner, or a paste followed at once by Enter, lands the key in that frame: Enter ran "Search for acm" under a box reading `acme`. On a mismatch the typed path commits what is actually in the box.

The stamp guards the *input*; a second guard covers the *data*. When the query changes, the value list's stream is swapped, and `StreamBuilder` keeps handing its builder the previous stream's rows until the new one emits — a frame for an in-memory list, as long as the query takes for a Drift-backed one. Those rows stay on screen (blanking the list per keystroke would flicker) but each emission is tagged with the key and query it answers (`_Suggestions`), and rows for an earlier query are published under a stamp that matches nothing: typing `zeta` into a Client list and pressing Enter before the new list arrived used to apply the first client of the old one. Rows left over from a different *key* are not shown at all. And a list whose typed value is not a value yet publishes **no** rows — an action that runs and does nothing still counts as "committed".

The typed path is one method for both hosts, `TokenSearchController.commitTyped`. The phone sheet had none, so `name:acme` + Search there searched for the literal text `name:acme`. The same goes for what a pick *means*: `pickKey`, `editChip`, `pickOp` and `dropBoxText` live on the controller. The field and the sheet each carried a copy and drifted three times — custom fields pinned in one, `directApplyValue` honoured in one, the typed text dropped in one — so the hosts now keep only what is theirs: anchors, the overlay, navigation.

## A pick-only key never takes typed text

**`FilterKey.acceptsTypedValue` is false for every key whose values are ids or enum names.** `client:acme` + Enter with no matching row — or Enter that beat the list's first emission — used to apply `client_id=acme`: a chip reading `client acme` over an empty list. Now the input and the menu stay. The same flag decides how a key opens (`opensViaPin`): a pick-only key and a custom field open through the pin, with no `<id>:` written into the box. One predicate for wide and sheet; they had each carried a copy and drifted.

## A typed value goes through the key's normalizer

**`FilterKey.normalizeTypedValue` returns the canonical wire value or null to refuse.** Three bugs lived in the gap. `balance:<500` + Enter committed `> 500`, because the operator rows always pre-selected row 0 — they now pre-select the comparator that was typed (it is part of the row keys, so typing one re-keys the list). `balance:abc` was accepted and sent as `gt:abc`; amounts now follow `parseDecimal`'s separator rule under the company's decimal convention, but parsed *strictly* — `parseDecimal` answers zero for what it cannot read (it is built for form fields, where blank is zero), so `1.2.3` would have become `> 0`. And a typed date could not be committed at all: Enter picked the comparator row, then the "back" row, in a loop. A date that `DateColumnFilterKey.parseTypedDate` accepts now shows one-step rows that read the way the chip will (`is on or after 14 May 2026`). The pre-selected row is the comparator typed in front of the date, else the one picked from the list before typing, else the key's default — and the picked one is held in `_ValueListState`, because typing swaps the preset widget for the typed-date widget and a choice kept in the swapped-out State went with it (pick "is before", type the date, Enter applied "is on or after"). Text that is not a date says so and gives Enter nothing to commit; it used to walk the highlight through a comparator and then "1 hour ago".

**A pasted value passes the same gate** (`applyPastedQuery`, the clipboard-free half of `handlePaste`). It used to go straight to `addValue`, so pasting `client:acme balance:abc` applied both. A typed-value key normalizes it; a pick-only key takes it only when it names one of the key's own values exactly, resolved through the synchronous `quickValueSuggestions` (`is:archived`, `status:paid`). Whatever is refused stays in the box as text.

`parseTypedDate` deliberately accepts less than `parseDateInput`. That function also reads `20`, `+1` and `0514` as dates — right for a date field committed on blur, wrong halfway through typing `2026-05-14`, where Enter would commit "the 20th". Here a date needs a digit either side of a separator, or a word. `today` and `yesterday` become rolling `rel:d0` / `rel:d1` tokens so a saved view keeps meaning "today"; a window-only key has no rolling form and gets the absolute date. `May 14, 2026` contains a comma and is a single date, so a single date is tried **before** the comma is read as a window.

## A chip's body edits, and only ✕ removes

**Tapping a chip never removes its value.** For a multi-value key the tap used to remove the value first and then open the picker, so Escape or a click away deleted the filter — against the chip's own contract (`docs/pane-width-and-overflow.md`). The value now stays applied: the controller remembers the chip being edited (`beginEdit`), and a pick swaps it through `FilterKey.replaceValue`, one write for the set-backed keys. A multi-select or custom-field chip opens its list with the applied values ticked instead.

Two presentation rules ride along. **The label keeps its case** — it was lowercased for a `key:value` look, which gives `kunde` and `ust-idnr.` in German and mangles a company's own custom-field label. **An aggregate chip names two values and counts the rest** (`Status Draft, Paid +1`, full list in the tooltip): three labels in one chip is what pushed the input onto a second line.

## Multi-select rows toggle, and "Only" replaces

**The whole row ticks or unticks and the menu stays open; a trailing "Only" picks one value and closes.** The row used to be split invisibly — the 20 px checkbox added, the label replaced the selection and closed — so clicking "Paid" with Draft and Sent ticked silently dropped both, and a near-miss on the checkbox wiped the selection. "Only" shows on the highlighted row, and on every row on touch, where there is no hover to reveal it. After a tick made with Enter the typed query is cleared so the full list is back for the next one; a tap or click leaves it, so the list does not reshuffle under the finger working down it. Which it was is asked of the commit (`FilterSuggestionController.committingByKeyboard`, true only while `commit()` runs a row).

## The first view leads with the suggested filters

**With nothing typed the picker shows `Suggested` — the keys marked `FilterKey.isPrimary` — and then `All filters`, A→Z.** It used to be one flat A→Z list with no hints: on Clients, State — the filter the placeholder advertises — was row 12 of 15, and eight rows fit. Primary is a flag on the key (State, the per-entity Status, Client, the document's `date`, a client's Name), not "the first N in registry order": that order also drives chip order and the cross-key value matches, and it is not a ranking — Invoices registers Tags before Status. The headers appear only when both groups have rows, so a settings list with State alone stays a bare row. While typing, keys whose label, id or alias *starts* with the query lead the ones that merely contain it (`rankFilterKeys`); a flat A→Z of every substring match put `Custom…` ahead of `State` for someone typing `st`.

On a pointer platform each row also shows what to type to reach it without the menu (`status:`), and a footer shows the keys — the command palette's caps and words. Neither on touch, and no type-hint for a custom field, whose id is exactly what its configured label exists to hide. The value list's header is a "‹" back to the picker: the only way back that needs no hardware key, since a soft keyboard sends no event for Backspace on an empty input. A list still waiting on its first emission says "Loading" rather than "No matches", and an idle list cut to `FilterKey.idleSuggestionCap` says so in a trailing row.

## The keyboard: Escape in two stages, Tab accepts, Backspace arms

- **Escape** closes the menu first and leaves the box second. One press did both, so every filter built from the keyboard cost another `/`. Android back still does both at once: back cancels.
- **Tab** accepts the highlighted row when something is typed; otherwise, and for Shift+Tab, it closes the menu and lets focus move on. The menu's visibility is deliberately not tied to focus, so a Tab that simply moved on left it open with nothing able to close it. "Accepts" means something was actually committed: a typed value the key refuses keeps the input for Enter, but a Tab that did the same was swallowed on every press, so a refusal closes the menu and lets Tab through (`_Commit`).
- **↓** opens a closed menu. `/` focuses the box without opening anything.
- **Backspace** in an empty box arms the last chip (accent border); a second press removes it — the whole *chip*, so an aggregate `Status Draft, Paid +1` goes in one, not one value at a time under a highlight that said the chip would. A key *repeat* never reaches a chip — that is someone holding the key to clear their text.
- **Arrow keys repeat.** A held ↓ used to fall through to the text field and walk the caret.
- A mouse click on a multi-select row refocuses the input; the click had unfocused it and left the open menu with no keyboard at all.

## Hover moves the highlight only when the pointer moves

**Rows listen to `MouseRegion.onHover`, not `onEnter`.** `onEnter` also fires when a row *appears* under a pointer that is not moving — the menu opening beneath a cursor parked below the box. That row took the highlight and Enter committed it instead of "Search for …". A keyboard move scrolls its row into view (through the nearest scrollable only — an embedded list's field sits inside the record page's own scroll view); a far jump in a lazily-built list is scrolled from the index by `_MenuScroll`.

## The header grows because `preferredSize` is a ceiling

**`EntityListAppBar` shrink-wraps, and `preferredSize` is how tall it *may* get.** `Scaffold` wraps its app bar in `ConstrainedBox(maxHeight: preferredSize + inset)` and places the body under the height the bar actually reports, in the same layout pass; Material's `AppBar` only ever looked fixed because it expands to fill that ceiling. So nothing is measured and no frame lags. The header used to be an `AppBar` with a fixed `toolbarHeight`, which gave the search row 45 px however many chips it held. Measured before the change: on desktop a wrapped input sat at y 47–79 in a 69 px bar — painted over the first rows of the table and, being outside the bar, not clickable — and on a touch platform a *single* chip (17–67, its ✕ padded to 40 px square) already overran its box.

Both header modes are one widget with both halves mounted (`IndexedStack`, which sizes to the taller child). That is what keeps the row under the pointer still when it is ticked: the selection chrome is as tall as the normal chrome it covers, wrapped chips included, by construction rather than by two classes agreeing on a number. The hidden half is excluded from focus, pointers and semantics. Past the ceiling (`maxExtentFor`: under half the available height) the box scrolls its chips instead of clamping; that scroll view is `hitTestBehavior: deferToChild` with the scrollbar off, because either would swallow clicks on the blank part of the box. For the ceiling to be reached at all the box needs a *bounded* height: in the narrow header the search row is a `Flexible` child of the header's `Column` (a non-flex child is laid out unbounded, and overflowed the bar instead of scrolling), aligned with `Align(heightFactor: 1)` rather than `Container(alignment:)`, which under a bounded height expands to fill it.

## One line is `InSizes.headerRow` on every platform

**The search box floors to `InSizes.headerRow` (the band less its padding), and everything beside it sits in a `HeaderRowSlot` of that height.** The row is top-aligned, so without the slots the "New" button slid down the header each time a chip wrapped. Three sizing traps, all on touch, all hidden until the fixed-height bar stopped clamping them: the theme pads an icon button's *layout* box to 48 px; the input was 40 px (a pointer platform's compact density takes 8 off the decorator, touch does not); and a chip's ✕ was 40 px square. Inside the box they now take their height from the line and keep a finger's width — the axis `docs/touch-targets.md` reclaims. `FilterTokenChip(compact:)` is that switch; the phone sheet has the room and leaves it off. The focus ring thickens by shadow, not border width: a wider border grew the box by a pixel on every focus, which a header that sizes to the box would pass to the whole list.

`searchWide` is `(wide || globalNav) && !Breakpoints.isPhone`: a landscape phone clears the 600 px test and has about 190 px above its keyboard, so it gets the summary row and the full-screen sheet like a portrait one.

## Testing the field

**Assert on global rects, in a host with a second Overlay.** The shell hosts a list in a branch Navigator whose Overlay starts 232 px in; a test that hosts the field in the root Overlay cannot see a lost origin. The harness reproduces that, uses a real view model (the bugs are in how the field and the VM talk), and never calls `pumpAndSettle` — an open popup re-lays-out every frame. Every test ends with a pump long enough for the VM's debounced `nav_state` write, which is a Timer. Seed filters *after* the first pump. And `flutter test` defaults to Android: pin `TargetPlatformVariant` or the key hints, the 40 px rows and hover are all absent.
