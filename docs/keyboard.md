# The keyboard layer

Companion to CLAUDE.md § Design system (v2) (the keyboard rules). Shortcut discoverability, the focus invariant the whole keyboard layer hangs off, the `G`-leader table, and how a key is drawn in a cap. The failure mode most of this exists for is silent: the tree still builds, nothing throws, and the app simply answers no keystroke.

## Keyboard-shortcut discoverability

**Keyboard-shortcut discoverability.** `KeyCap` (`lib/ui/core/widgets/key_cap.dart`) is the shared keycap chip; `platformModifierLabel()` (`lib/ui/core/utils/platform_modifier.dart`) gives `⌘`/`Ctrl`. Holding the platform modifier reveals a bottom-center hint bar (`ShortcutHintOverlay`, mounted beside `ToastHost` in `main.dart`) listing the modifier shortcuts registered for the current screen. Register context shortcuts by wrapping a body in `ShortcutHintScope(hints: [ShortcutHint(keys: [...], labelKey: '...')], child: ...)` — the shell registers the globals (⌘K/⌘//⌘B/⌘,), `entity_edit_scaffold` adds ⌘S, `billing_doc_edit_fab` adds ⌘N. Hovering a button can surface its shortcut via `ShortcutTooltip(label:, keys:)` (used on the list New button, company switcher, and sidebar leader rows). Note `ShortcutTooltip` uses `Tooltip.richMessage`, so it isn't matched by `find.byTooltip('<message>')` — don't add it to a button whose tests locate it that way; keep a plain `tooltip:` there. New screens with a context modifier shortcut should add a `ShortcutHintScope`.

## The whole keyboard layer hangs off one focus node

**The whole keyboard layer hangs off one focus node, and every framework recovery path drops it somewhere that node cannot see.** Flutter dispatches a key event only from `FocusManager.primaryFocus` *upward* — `_handleKeyMessage` returns `false` outright when it is null, then walks `[primaryFocus, ...primaryFocus.ancestors]`, ancestors and never descendants. Everything this app binds lives **inside** `ScaffoldWithNav`: the global `Shortcuts` map, the `G` leader `Focus`, and every list / pane / edit `Shortcuts` below them. So the instant primary focus lands at or **above** the shell, all of it is skipped at once — ⌘K, ⌘/, ⌘B, ⌘,, `?`, `/`, ⌘←/→, the chords and every bare-key screen shortcut, together — and on macOS the keystroke then falls through to `[super keyDown:]` → `NSResponder.noResponderFor:` → **NSBeep**, which is the only outward sign. `Focus(autofocus: true)` cannot recover: `_FocusState` applies autofocus exactly once (`_didAutofocus`) and `_Autofocus.applyIfValid` additionally requires the enclosing scope to have no focused child. Four ordinary paths reach the dead state and none of them come back — a focused node being **disposed** (`_markDetached` nulls `_primaryFocus`, then `applyFocusChangesIfNeeded` falls back to `rootScope`, whose `ancestors` is empty; closing a detail pane disposes `_PaneRoot`'s own autofocus node); **`FocusNode.unfocus()`**, whose default `UnfocusDisposition.scope` clears the scope's remembered children and parks focus *on the scope itself* — both edit-save paths call it to flush an unblurred field, and navigating away then disposes that scope; a route **popped off the root navigator**, where `_ModalScopeState`'s `setFirstFocus` resolves to the shell page's own `FocusScopeNode` once its remembered `focusedChild` is gone; and **app-lifecycle suspend**, which parks focus on `rootScope` and restores `_suspendedNode` on resume only if that node is still alive. `FocusOwnerKeeper` (`lib/ui/core/widgets/focus_owner_keeper.dart`) restores the invariant, and four things about it are load-bearing. **The predicate is ancestry, never `primaryFocus == rootScope`** — the root-scope spelling looks right and misses the commonest case, since case 3 lands on a scope that is not the root but is still above everything that handles keys; `!primaryFocus.ancestors.contains(node)` covers root scope, the shell page's scope and a detached node (empty `ancestors`) in one expression. **It stands down while the app is not `resumed`**, or it would beat the framework's own suspend/restore and blur whatever the user was typing in when they switched away. **A test for that clause has to stage the park by hand.** `FocusManager` registers its lifecycle listener everywhere but `android` and `iOS` (`_respondToLifecycleChange`, flutter#148475) and `flutter test` always reports `android` (`_platform_io.dart` rewrites it whenever `FLUTTER_TEST` is set), so `handleAppLifecycleStateChanged(inactive)` moves no focus at all in a widget test — and `debugDefaultTargetPlatformOverride` cannot reach it either, because that decision is made in the constructor of a `FocusManager` the test binding builds during the *previous* test's `postTest`. Drive the suspend and then park focus yourself (`rootScope.requestScopeFocus()`), and let the sibling test that reclaims from the identical park carry the two-sidedness; asserting on the framework's own suspend instead is asserting on something that never happens, which is how the lifecycle case in `focus_owner_keeper_test.dart` shipped red. **It stands down while a route above the shell is current** (`ModalRoute.of(context)?.isCurrent`, the idiom `_createEntity` already uses), because a dialog, the command palette and the company picker legitimately own focus up there — and reading that in `didChangeDependencies` is also what wakes the keeper when one of them closes. And it re-checks **post-frame, one pending check at a time**, because focus moves in bursts: a route push lifts it above the shell and drops it back inside the same frame, and acting on the intermediate state would fight the framework. There is no loop risk — a `requestFocus` that cannot land fires no `FocusManager` notification, so nothing re-arms. The second half of the same defect is *below* the shell: `StatefulShellRoute.indexedStack` keeps every visited branch mounted behind an `Offstage`, which does **not** move focus, so after a branch switch primary focus can still sit in the branch the user left — and dispatch being leaf-first, that branch's `Shortcuts` are consulted first, so a bare `N` / `E` / arrow is serviced by a screen nobody can see, while a focused invisible search field keeps `isTextInputFocused()` latched true and stands *every* `GuardedShortcutAction` in the app down. Hence the keeper's `branchIndex` trigger + `focusIsInHiddenBranch` test (which walks the *inactive* branches' `NavigatorState.focusNode`s — asked positively, because 'not in the active branch' also catches the shell's own chrome, where a tabbed-to sidebar row lives), and hence `TokenSearchField` claiming `SearchFocusRegistry` in `didChangeDependencies` under `TickerMode.valuesOf(context).enabled` rather than in `initState` — the same one-slot-registry gate, and the same finding (#40), as `ShortcutHintScope`. `test/lint/focus_owner_wiring_test.dart` pins the wiring by source scan, because the real shell cannot be pumped and a lost keeper is otherwise invisible: the tree still builds, nothing throws, and the whole suite stays green while the app answers no keystroke at all. **The same hole ran one level down, inside every entity list, and had been there since the shortcuts shipped.** `Shortcuts` mounts a `Focus(canRequestFocus: false, skipTraversal: true)`, so it is only ever *walked past* — it needs something below it holding primary focus, and `EntityListScreenScaffold` had nothing: on a freshly opened list, primary focus sat on the shell node or the branch route's scope, both **ancestors** of the list's own `Shortcuts`. So `N` (new record), `↑`/`↓` (step the selected row) and every entity's `selectionShortcuts` letter (Tasks' `S`) fired only after the user had clicked or tabbed into the list — which nobody does before pressing `N`. `_PaneRoot` has carried such a node since it shipped, which is the whole reason the pane's `Esc`/`F`/`J`/`K` do work; the list never had one. **`Focus(autofocus: true)` is not the fix, and was tried first** — it is applied once and only while the enclosing scope has no focused child, so it is silently dropped on a hot reload, on a list rebuilt under a route that already existed, and any time focus has already been somewhere; and it can never re-fire after a pane closes and takes the focused node with it. The list therefore gets its own `FocusOwnerKeeper` over a retained `_bodyFocus`, and **its three gates each prevent a fight rather than an edge case**: `embedded` (a detail screen mounts several list tabs at once and the host owns the page), `TickerMode.valuesOf(context).enabled` (go_router keeps every visited branch mounted, so without it the hidden branch's list and the visible one would both claim, forever — the `ShortcutHintScope` gate again), and `paneIsOpenForList` (the pane is a **sibling** of this node, not a descendant, so an open pane reads as escaped focus and the list would steal its `Esc`/`J`/`K`). That last one is a **non-subscribing** read (`router.dart`'s `_SelectedIdScope._peek`, via `getInheritedWidgetOfExactType`) and is passed as the keeper's `canClaim` callback rather than as build state, because subscribing would rebuild the whole list scaffold on every row click — the cost the `settingsBackTargetFor` comment in the same file already warns about — and it does not need to: the check is only ever reached from a `FocusManager` notification, and closing a pane always moves focus. Two keepers never fight for the same focus, because a nested one claiming its own node necessarily satisfies every keeper above it. **A new screen that registers a `Shortcuts` map owes itself a focus owner** — the map is not wrong, it is simply never consulted, and nothing about the call site looks it.

## The `G`-leader table has one copy, and it is not in the shell

**The `G`-leader table has one copy, and it is not in the shell.** `G` then a letter jumps to a branch; the letters live in `lib/domain/leader_shortcuts.dart` (`kLeaderTargets`, a leaf over `EntityType` + `FixedBranchKind`), because there are **three** consumers and each drifts silently in its own direction: the shell resolves the pressed second key, `in_sidebar` draws each row's `G`-then-x tooltip, and the `?` dialog is the only place any of it is documented. A shortcut with no sidebar hint and no dialog row is one nobody can discover; a hint with no shell case is a documented shortcut that does nothing. Adding a destination is one entry — `test/lint/leader_shortcuts_wiring_test.dart` fails the build on a hand-rolled switch coming back, and `test/domain/leader_shortcuts_test.dart` pins uniqueness, the single-uppercase-letter shape (the shell matches on `LogicalKeyboardKey.keyLabel`, which keeps the match on the *logical* key and so carries across layouts), and that `G` is not itself a target. Letters are the destination's first letter where free and otherwise one from inside the word (`J` = pro**j**ects, `Y` = pa**y**ments, `O` = purchase **o**rders, `B` = **b**ank transactions); **Credits and the recurring pair are deliberately unbound**, because every letter in "credits" is already taken and a letter the name does not contain can only be looked up, never remembered. Free: F H K L M N U W X Z. Two things a new entry must not assume: the jump is refused for a module the company has switched off *and* — the one fixed branch with a permission of its own — for Reports without `view_reports`, which `_goBranch` checks because the sidebar omits that row entirely rather than disabling it (the Pro lock beside it is only a hint; the row still navigates). And the second key is only special while the leader is armed, so binding a letter here never makes it un-typeable anywhere.

## A chord is one cap per glyph, never a concatenated label

**A chord is one cap per glyph, never a concatenated label.** `KeyCapRow` (`key_cap.dart`) is the unit — `KeyCapRow(keys: [platformModifierLabel(), '/'], label: context.tr('navigate'))` renders `[⌘][/] Navigate` — and it backs every hint surface: the hold-modifier bar, the palette's field chip and footer, the `?` dialog's key column, and both settings shortcut screens. A single `KeyCap(label: '⌘/')` reads as one key and paints `Ctrl/` with no gap on Windows and Linux (invoiceninja/flutter#103); `test/lint/keyboard_hints_use_keycaps_test.dart` fails the build on that shape and on two arrow glyphs in one literal. **Whitespace is the only separator** — no middots, no `+`: use `platformHistoryModifierGlyphs()`, not `platformHistoryModifierLabel()`, wherever the result becomes caps. `label` is an **already-localized string, not a key**, so `key_cap.dart` stays a leaf (`flutter/material` + `design_tokens.dart`) and each caller does its own `context.tr`; `dense: true` fits a narrow fixed-width popover. Two traps: `keys` means "the keys in this hint", not strictly a chord — the palette footer's `['↑', '↓']` is *either* arrow while the chip's `['⌘', '/']` is *both*, and where the difference must show (the `?` dialog) the caller renders one row per alternative joined by `tr('or')`, so **flattening an alternatives row into one chord silently turns "press either" into "press both"**; and a hint must never advertise a dead key — the palette gates its `↑↓`/`Enter` runs on `_recentMode || _results.isNotEmpty`, because a keycap makes a claim that grey 11-px text got away with mumbling.

## Inside a cap a key gets its printed name

**Inside a cap a key gets its printed name** — `Esc`, `Enter`, `Backspace` — with symbols only where the physical cap is one (`↑ ↓ ← → ⌘ ⇧`). That is what `KeyBinding._glyphForLogicalKey` emits for a rebind (it falls through to `LogicalKeyboardKey.keyLabel`), so a hand-written cap must match or one key gets two names across surfaces. The bare `↵` in `PrimaryDialogAction` / `FilterSuggestionMenu` is a **different tier** — an inline "press this" beside the control, never in a cap. Relatedly, **the bundled JetBrains Mono has no `↵`**: its `cmap` carries `↑ ↓ ← → ⌘ ⇧ ·` but not U+21B5, `⏎`, `↩`, `⌤`, `⎋` or `⌫`, so `KeyCap` carries `fontFamilyFallback: [kSansFontFamily]` — without it a symbol cap drops to Menlo / Segoe UI Symbol / Noto, a different face and metrics beside the cap next to it, and **no widget test can see it** (`flutter test` substitutes its own font). Check a new cap glyph against the bundled `cmap`. `KeyCapRow` also wraps in `MergeSemantics`, since `KeyCap` announces one screen-reader stop per cap (with an untranslated `'Key: '` prefix — a known gap); that merge is inert wherever the surface already sits in `ExcludeSemantics`, as `ShortcutHintOverlay` and the `re_editor` popover do.
