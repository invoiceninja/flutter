# Overflow menus and popups

Companion to CLAUDE.md § Design system (v2) (the overflow-menu rules) and § Forms — Searchable pickers (the dismissal rules). Which glyph an overflow menu wears, and how a surface that is not a route gets closed. A `MenuAnchor` panel and a `RawAutocomplete` options popover are both overlays rather than routes, so neither gets Android's back for free and neither closes on an outside tap on native touch. They are documented together because the picker rule literally reads "a picker popover is not a route **either**".

## A `MenuAnchor` is not a route, so Android back has to be wired by hand

**A `MenuAnchor` is not a route, so Android's back has to be wired by hand — use `BackDismissibleMenuAnchor`** (`lib/ui/core/widgets/back_dismissible_menu_anchor.dart`). Every `⋮` menu in the app is a `MenuAnchor`: the list row's (`EntityActionsPopupButton`), all three on the detail header (`entity_detail_actions_row.dart`), Reports' date-preset and Export menus, and the debug screenshot-size picker. `MenuAnchor` binds Escape (`DismissMenuAction`) and Flutter wraps its panel in a `TapRegion` that closes on an outside tap, so on a desktop — where this is reviewed — it looks finished. But `menu_anchor.dart` and `raw_menu_anchor.dart` contain **no** `PopScope`, `BackButtonListener` or `NavigatorPopHandler` at all, while `PopupMenuButton`, which these replaced, is a `_PopupMenuRoute extends PopupRoute` that back closes for free. So the swap kept its outside-tap semantics — `entity_actions_popup_button.dart`'s comment says "Match the old PopupMenuButton" about exactly that — and silently dropped its back semantics: on Android, opening a row's `⋮` and pressing back **navigated off the list** instead of closing the menu. **A `PopScope` cannot fix it**, which is the non-obvious part: `ModalRoute.onPopInvokedWithResult` notifies *every* registered `PopEntry`, so a `canPop: false` entry beside the menu would stop nothing — `SystemBackGate`'s entry is on the same route and its handler would still run `NavHistoryController.back()`. The fix has to sit **above** route popping, and that is a `ChildBackButtonDispatcher`: `Router` consults its children before it calls `popRoute()` at all. It is registered imperatively and only while the menu is open — `BackButtonListener` would otherwise put one dispatcher per visible list *row* in the parent's child list (it registers in `didChangeDependencies`, and `Router.of` takes a dependency), and mounting it conditionally instead changes the tree depth around `MenuAnchor`, re-inflating its element and disposing the very menu the listener exists to close. `test/lint/menu_anchor_back_dismiss_test.dart` fails the build on a bare `MenuAnchor` in `lib/`, and pins the wrapper's own contract too; the behaviour needs a real `Router` plus an Android back event to observe, so nothing about a new call site looks wrong at the call site.

## On native touch nothing closes the options popover but a pick

**On native touch nothing closes the options popover but a pick — so every `RawAutocomplete` field sets `onTapOutside`.** Three SDK facts conspire. `_canShowOptionsView` is `hasFocus && options.isNotEmpty`, so the overlay closes only on a `_select`, on a `DismissIntent` (Escape — a hardware keyboard) or on **focus loss**. `_EditableTextTapOutsideAction` deliberately does *not* unfocus for a `PointerDeviceKind.touch` event on android/iOS/fuchsia unless `kIsWeb` — a soft keyboard must not close on a stray tap. And a list with anything in it has no way out: `_optionsFor` never returns empty (it falls back to `_idleOptions()` for a pristine or empty query, and an empty `items` takes the disabled-placeholder branch), and the tax cell prepends a "none" row. The create-bearing pickers *can* go empty — `TagPickerField._canCreate` is false for an empty query, `_ProductCell` appends its create row only for a non-empty one — and that does unmount the overlay, but it is not a dismissal anyone can aim for. Net: on a phone or tablet there was **no dismissal path at all** — the popover stayed up until the user picked something or closed the whole screen (invoiceninja/flutter#130), and that was every picker in the app, not just the Activity filter it was reported against. It is one line per field view — `onTapOutside: dismissPickerOnTapOutside(focusNode)` (`lib/ui/core/widgets/picker_dismissal.dart`) — and it is safe **because** `RawAutocomplete` wraps both the field and the options overlay in `TextFieldTapRegion` (same default `groupId: EditableText`) and a tap-region group acts as one region, so a tap on an option row, the popover footer or a selection handle counts as *inside* and never fires it. The proof isn't the source, it's the product: on desktop a mouse-down outside already unfocuses, so if the overlay sat outside the group, clicking an option on desktop could never have worked. `TapRegion` is also route-aware (it nulls `onTapOutside` while `ModalRoute.isCurrentOf` is false), so a picker behind an open dialog — `ClientPickerField` mid-create — is left alone. Off native touch it reproduces the SDK default exactly, so desktop and mobile web are unchanged. Three consequences. It fires on pointer **down**, so a scroll or drag that *starts* outside also dismisses — right, since the popover is anchored to a field that is about to move. The ✕ sits **inside** that same tap region, so it needs its own `unfocus()`, and only when the text is `_isPristine`: clearing a committed value is a *commit* (the same shape as tapping the committed row, which already closes and unfocuses), while clearing a half-typed query means "erase and let me retype", so focus and the keyboard stay. Without that, `clear()` is a text change, the idle list comes back non-empty over a still-focused field, and the SDK **opens** the popover — plus it strands a stale `_options` computed before `setState` nulled `_committed`, so a soft-keyboard Done then re-selects the value just cleared. And on a **keyboard-less** picker (`_suppressKeyboard`, ≤ 6 options on touch — `showCursor: false`, no caret to place) a tap on the field itself toggles the list shut, because there the field *is* the dropdown button and it is often the only part of the screen the popover doesn't cover; a typable field keeps its tap for the caret — and that tap needs **`onTapAlwaysCalled: _suppressKeyboard`** beside it, because `TextField.onTap` arrives through `TextSelectionGestureDetectorBuilder`, whose `_handleTapUp` calls it only on the FIRST tap of a series, so an impatient second tap inside `kDoubleTapTimeout` is swallowed whole and the toggle is intermittent. **The scope is wider than the popover, deliberately**: `onTapOutside` is wired whenever the field has focus, and `_select` closes the overlay *without* unfocusing, so on touch these fields now drop the keyboard on any outside gesture — a scroll started right after a pick included. Kept because desktop already behaves that way; narrowing it would need a visibility flag in two hosts that have none plus a re-implementation of the SDK's platform matrix. `test/lint/picker_popover_wiring_test.dart` pins the hook — and `OptionsViewOpenDirection.mostSpace`, which the tax cell alone had never set — on every `RawAutocomplete` in `lib/`, counting the type-inferred `RawAutocomplete(` too. The tap-region-group argument is pinned by the **SDK source**, not by a test: a widget test cannot see it, because removing the overlay takes a frame and `tester.tap` pumps none between pointer-down and pointer-up, so even an unfocus firing on an option tap leaves the row mounted long enough to complete. That was checked by experiment after an earlier draft of this paragraph claimed the opposite.

## Android back is the other dismissal, and needs its own wrapper

**Android's back is the other dismissal, and a picker popover is not a route either — wrap it in `BackDismissiblePickerOverlay`** (`picker_dismissal.dart`). The rule above (§ On native touch nothing closes the options popover but a pick) gave the popover a way out for a *tap*; this is the gesture an Android user reaches for first, and `RawAutocomplete` handles it even less well — `autocomplete.dart` (and `editable_text.dart`) contain **no** `PopScope`, `BackButtonListener` or `NavigatorPopHandler` at all. So back fell through to `SystemBackGate` and ran `NavHistoryController.back()`, leaving the screen — **or exited the app**, since that gate calls `SystemNavigator.pop()` when `canGoBack` is false and the app restores exactly where the user left off, so a session relaunched onto `/tasks` had no history behind it. That was invoiceninja/flutter#134, reported against the Tasks filter bar's Assigned User picker but true of all five hosts. It looked intermittent because it tracks the option count: `_suppressKeyboard` sets `TextInputType.none`, which suppresses `showSoftInput`, so at ≤ 6 options there is no Android IME to swallow the press and it lands on the first try; above that the IME eats one and it takes two. Six things are load-bearing. **A `PopScope` cannot fix it** — `ModalRoute.onPopInvokedWithResult` notifies *every* registered `PopEntry`, and `SystemBackGate`'s resolves to the same shell page route, so it would still navigate; the fix has to sit above route popping, which is what a `ChildBackButtonDispatcher` is. **The wrapper mounts inside `optionsViewBuilder`, never around the field**: `RawAutocomplete` builds its overlay child only while the options show, so *mounted == open* by construction and no host needs a visibility flag (`TagPickerField` and `_TaxCell` have none) — and the containment errs the safe way, since `_buildOptionsView` returns `SizedBox.shrink()` **without invoking the builder at all** when the field's paint transform is degenerate. **It must be `unfocus()`, not `DismissIntent`**, and that is a live bug rather than a preference: `RawAutocomplete` registers `_hideOptions` in an `Actions` wrapping only the *field* branch of the portal, while the overlay child is a **sibling** element under `_OverlayPortalElement`, so walking up from the popover skips it and finds `ModalRoute`'s dismiss action instead — back would pop the route. It would also strand the three hosts that *do* keep an `_optionsVisible` flag, because `EscapeObserver` watches the Escape **key** and a back-triggered intent fires none, leaving `_reopenOptions` to eat the next tap on the field. **`Router.maybeOf`, never `Router.of`** — Flutter's own `BackButtonListener` asserts and then bangs, and eleven picker tests pump a bare `MaterialApp` with no `Router`; `maybeOf` degrades to plain popover behaviour instead. **The claim runs inside a *layout* callback** (`OverlayPortal.overlayChildLayoutBuilder` wraps the builder in an `AbstractLayoutBuilder`), which is safe only because it is pure set mutation on both sides and `addCallback` here is the **child's**, never `RootBackButtonDispatcher.addCallback` — the one override that would mutate `WidgetsBinding`'s observer list. And **one callback per child dispatcher**: `_CallbackHookProvider.invokeCallback` calls `_callbacks.single()`, which throws, is caught, is reported, and then silently answers `defaultValue` for ever — so the `_child != null` guard is behaviour, not tidiness. Two designs not to re-propose: a global "a picker is open" flag consulted by `SystemBackGate` cannot tell "field focused" from "popover open" (`_select` closes the overlay *without* unfocusing, so it would eat back after every pick) and never runs for a dialog route's back; and wrapping the field re-derives what mount/unmount gives free, while mounting it conditionally hits the element-re-inflation trap the `MenuAnchor` paragraph records. `test/lint/picker_popover_wiring_test.dart` counts the wrapper per host and pins its contract; the behaviour needs a real `Router` plus an Android back event to observe, so nothing about a new call site looks wrong at the call site. **The same mechanism covers the other family of non-route overlay**: `BackDismissibleOverlay` is the general form (`onBack` + an optional `canDismiss`), and `BackDismissiblePickerOverlay` is a two-line convenience over it. `token_search_field.dart`'s suggestion and segment menus are the only hand-rolled `OverlayPortal`s in `lib/` and they take the general form, because their visibility is driven by an `OverlayPortalController` and *deliberately decoupled from focus* — so the picker form's `unfocus()` would swallow the press and leave the menu on screen, which is worse than the bug. Their `onBack` is the **Escape handler's** pair (`_hideOverlay()` + `unfocus()`, `_closeSegment()`), never `onTapOutside`'s, which also `_commitPendingFreeText()`s: back cancels, it does not commit. That surface is not desktop-only either — `searchWide = wide || globalNav` and `Breakpoints.isGlobalNavVisible` is a raw `width >= 600` with no platform test, so every tablet and **every phone in landscape** reaches it, and the segment menu unfocuses before opening so there is no IME to absorb the first press. `test/lint/overlay_back_dismiss_test.dart` counts the wrapper against every `OverlayPortal` constructor in `lib/` (all three spellings — the SDK's own preferred `overlayChildLayoutBuilder` form contains no `OverlayPortal(` substring, so a substring rule would score such a file as zero hosts and pass it with no wrapper). Everything else that opens over the app is a route — `showMenu`, `PopupMenuButton`, `DropdownButton`, the custom picker routes, dialogs — and back closes *those* for free. **But a route pushed on top of a live overlay does not close for free, and that is the sharp edge of this design**: the `Router` consults child dispatchers before it pops anything, so a mounted wrapper out-ranks every modal route above it. A menu row that opens a date picker and awaits it hands the back press to the menu *underneath* the calendar. Hence `FilterSuggestionMenu.onDismiss` and `segment_menu.dart`'s reordered `onClose()` — **dismiss before the await**, the rule `token_search_field._onSelectValue` already stated for its own. A `ModalRoute.isCurrentOf` guard is not a substitute (`showDatePicker` is `useRootNavigator: true`, so it is not even on that navigator), and the wrapper cannot take that dependency anyway — `_claim` runs in a layout callback and its safety rests on `_RouterScope` being the only inherited widget it touches. The five pickers are immune for a different reason: their `canDismiss` is `focusNode.hasFocus`, and a pushed route takes the focus scope.

## Always the vertical ⋮, never the horizontal ⋯

**Always the vertical `⋮`, never the horizontal `⋯`.** Every overflow / "more" menu uses `Icons.more_vert` — the labeled `⋮ More` button on the wide detail and edit headers and the multi-select bulk bar (`_MoreMenu`, `entity_detail_actions_row.dart`), the compact `⋮` trigger one breakpoint down (`_OverflowMenuButton`), and every list row (`EntityActionsPopupButton`, which deliberately takes **no icon parameter** — the glyph is not a per-call-site choice). Banned in `lib/` by `test/lint/no_horizontal_more_icon_test.dart`, with a `// lint: allow-more-horiz` opt-out for the one thing the dots might legitimately mean instead (a text-truncation affordance). The two `IconData`s are interchangeable at every call site and nothing type-checks the difference, so a mismatch compiles, runs, throws nothing, and simply paints the wrong glyph: 15 of the 17 entity tiles passed `icon: Icons.more_horiz` for their narrow row while Clients and Vendors passed nothing and took the `more_vert` default, so the same list showed a different menu icon depending on which entity you opened, for the life of those files. Each widget test asserted whichever glyph its own widget happened to pass, so the **divergence between** them was what nothing could see. Note this is deliberately **not** Material's convention, which pairs a labeled overflow with `⋯` and reserves `⋮` for a bare icon; one glyph everywhere is the trade. **The commonest way to reintroduce `⋯` is by writing nothing at all**: `PopupMenuButton` defaults its trigger to `Icon(Icons.adaptive.more)`, and `Icons.adaptive.more` is `more_horiz` on **iOS and macOS** — both shipped — so a `PopupMenuButton` with neither `icon:` nor `child:` renders the horizontal glyph on two of the five platforms and no grep for `more_horiz` can find it, the offending token being the argument that isn't there. Four sites were in that state, one of them named `SettingsEntityOverflowMenu`; the lint's second test now walks every `PopupMenuButton` in `lib/` structurally (a `child:` is fine — it replaces the icon outright). Finally, two overflow triggers can now sit in one tree carrying the same icon, so a test that must tell **them** apart discriminates on the widget — `find.widgetWithIcon(OutlinedButton, ...)` for the labeled one, `find.widgetWithIcon(IconButton, ...)` for the compact one; a plain `find.byIcon(Icons.more_vert)` stays correct for asserting that neither is present, or where only one can be.
