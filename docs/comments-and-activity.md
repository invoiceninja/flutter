# Comments and the activity feed

Companion to CLAUDE.md § Design system (v2) (the comment and activity rules). A comment is an `activity_type_id = 141` row, so comments and activity are one feed rendered two ways. The main file carries one line per rule; this doc carries the evidence — the card's measured position, the detail tab strip's scrolling, and what an activity row may link to.

## A card that hides itself still costs a gap

**A card that hides itself still costs a gap.** `ClientDetailCardsGrid._stacked` and `VendorDetailCardsGrid._stacked` interleave `SizedBox(height: InSpacing.md(context))` with `for (var i = 0; i < cards.length; i++)`, so an entry returning `SizedBox.shrink()` from its own `build` leaves `md + 0 + md` between its neighbours — double, invisible in review and obvious on a phone. Nothing can detect "this will paint nothing" from outside without building it, so the **entry** must be conditional: that is what `hasContent` on Details / Address / Shipping address / Payment methods / Contacts is for, and every entry in both lists now has one. `VendorDetailDetailsCard` was the harder half — unlike its client twin it never self-hid at all, since `DashboardCardShell` paints its border, title and divider whatever the child, so a vendor with only a name got an empty bordered "Details" box. The **wide** branch is the opposite rule *for columns* and stays that way: an `Expanded` keeps its share of the row whatever its child does, so a wholly-empty Details card is kept on purpose to hold the three columns aligned, and a column is dropped only when that changes the column *count*. But "wide" is not the same as "nothing stacks" — the client grid's middle column stacks Address above Shipping and pays the same per-entry gap, so a client with a shipping address and no billing one wore an orphaned 12 px above Shipping that pushed it out of line with the cards beside it. Gate wherever cards stack, in either branch. Testing this needs care — `InSpacing.md` reads `MediaQuery.sizeOf(context).width`, which `pumpAt`'s `setSurfaceSize` does **not** move (`MediaQuery.fromView` reads `view.physicalSize / devicePixelRatio`, left at the harness default 800), so measure a suspect gap against a control gap in the same column rather than against a literal, and drive `tester.view.physicalSize` + `devicePixelRatio` when a widget's own branch keys off `MediaQuery` (as the contacts card's does, deliberately — `IntrinsicHeight` can't answer a `LayoutBuilder`).

## A record's comments live above the fold

**A record's comments live above the fold, and the card that shows them is the one place the gap rule inverts.** A comment is an `activity_type_id = 141` row; before invoiceninja/flutter#121 the only way to read one on a client was the Activity tab — 14th of 14, at the bottom of the page, interleaved with every system row. `EntityCommentsCard` (`lib/ui/features/billing_shared/activity/entity_comments_card.dart`) puts the two most recent on the detail body itself, immediately after the identity block and **above** the cards grid, with `View All` into a `Comments` tab that leads the strip on all eleven entities (`select(0)` everywhere — see § The record’s own history leads every detail strip below). The position is the whole point and it is measured, not felt: on a 390×844 phone the body is ~698 px and `ClientDetailCardsGrid._stacked` runs ~476 px for a typical client, so a card *below* it starts at ~732 — the worst possible number, just under the fold. Above the grid it starts at 232 on every record. Eight things here are load-bearing, and most of them fail silently. The card is **always mounted and owns its trailing gap**, returning `SizedBox.shrink()` when there is nothing — the documented exception to § A card that hides itself still costs a gap above, because the visibility test is *asynchronous* (so it must live behind a `ListenableBuilder`, and a builder returns one widget, not a spread) and because an `AnimatedSize` mounted only on the flip has no prior size to grow from and simply snaps. `kCommentsCardInlineLimit` is **flat, never branched on width**: a landscape phone is an ~890 px window 412 px tall, so a `>= Breakpoints.wide` branch hands the taller card to the shortest viewport there is. Overflow goes to the tab via `DashboardCardFooterLink`, never an inline expander — that would undo the height cap and is one-way besides; reaching the tab needs `EntityDetailTabs.selectTab` (a `TabSelectionController`, because a plain `ValueNotifier` goes silent on a repeat request) which also `ensureVisible`s the strip, without which a tap changes a tab 500 px below the fold and nothing appears to happen. **That link is gated on rows actually being held back, and its hit area is the whole header band.** It shipped gated only on `onViewAll != null` — i.e. never, since all eleven hosts pass one — so on the great majority of commented records it advertised a destination rendering exactly the rows already on screen, which is what invoiceninja/flutter#145 reported as a link that "doesn't do anything when tapped". The predicate is `pendingRows.length + comments.length > kCommentsCardInlineLimit`: the **provable complement** of what `_body` draws (`min(pending + comments, limit)` rows, pending first), rather than a second rule about it, and it cannot lie about the destination either — with `commentsOnly: true` the tab renders those same two lists off the same view model, and the one `kEntityActivityRows` window truncates both identically because `isComment` is filtered client-side *after* it. Queued rows count, because `_body` spends the budget on them first. Five things follow. **The tab is not a pure superset of rows**, so "nothing further to display" means rows and nothing else: it also unclamps the body (`bodyMaxLines: 2` here), shows the IP (`showIp: false` here against the row's default true) and heads itself with `Log call` as well as `Add comment` — each of which keeps another route (`⋯ → Copy` yields the unclamped text, the Activity lens owns the IP, `Log call` is in the entity `⋯` menu and the post-call prompter), and the tab is still one tap away in the strip below. **Adding a comment to a record that already had two makes the link blink** — shown while queued, hidden the instant `_onPendingTick` empties `pendingRows` before the refetch it triggers lands, shown again one round trip later; that is the same window the card's own `hasAnyComment` has always had when the *first* comment is added, and a ~5 px header change is its smaller half. **The countless label is the house split, not laziness**: `+N more` (`plus_n_more`) is a body/footer affordance meaning "this container is truncating a list you can also see here" and is hard-gated on `n > 0` at all five of its sites, while `view_all` is a header link meaning "this card is an index, the real surface is elsewhere" and carries no N at any of its four — and moving a count in here would swap a Transifex string for an app-local English-only one on eleven screens. By the same line, the other three `view_all` links are **not** this bug: `/activity`, `/tasks` and a full entity list are different collections, so they stay honest with one row. **`DashboardCardShell.onHeaderTap`** makes the band the target, because the link's own box is ~25 dp tall against `InSizes.touchTarget` and the rest of the header had no handler at all, so a near miss was indistinguishable from a dead link. It is a semantics-excluded, ink-free `GestureDetector` (an `InkWell` would add a tab stop, a second hover wash, a click cursor on the card title and a band that flashes whenever a thumb rests on it mid-scroll) with `HitTestBehavior.opaque` (the default `deferToChild` leaves the title's slack and the padding unhit) around a `ConstrainedBox` floor on the **`Padding`**, never the `Row` — on the row the band would come to 64. Measured: 45 px with the link, 53 at ≥ 600, 40 with a title alone, so the floor binds only in that last case and the 1 px of margin in the case that matters is the argument for pinning it. It is the shape the #128 paragraph bans — an opaque `GestureDetector` and an `InkWell` nested over one another — with the operands swapped, and the only thing that redeems it is that **both edges resolve to the same callback**; re-point either and the ban applies in full. **The touch gate lives at the call site, not in the shell**: `EntityDetailScaffold` wraps the whole detail body in a `SelectionArea` on everything but native mobile, where an opaque tap would claim the single clicks `SelectableRegion` uses to place and clear a selection (taking the first click of a double-click-to-select with it), while a dashboard card sits in no such region — `party_call_button.dart` gates its secondary gestures the same way, with the same warning that no test sees it because `flutter test` reports android. Mobile web gets both and is accepted. `onHeaderTap` is a footgun on a shell with ~88 constructions, so it asserts it has a header to sit in and its doc names the six of ten `trailing:` sites that would be wrong — `Add Task` would create a task, the shipping-address section would overwrite an address, two expense layouts would toggle a collapse. The single footer action is `Add comment` only — `Log call` keeps the tab head, the `⋯` menu and the post-call prompter, and two labelled buttons in a `Wrap` cost a second run at 1.4× on a 320 px card. The shell gets `padding: EdgeInsets.zero` and the rows a `horizontalPadding` of `InSpacing.lg(context)`, because `ActivityRecordRow` hardcodes 16 for `ActivityListCard` while the shell's header uses 12 below 600 px — misaligned only on a phone, correct on every desktop review. And no `ClipRRect` is needed **because** the footer sits below the last row — which is why `isLast` is *computed* as "final row **and** no footer" rather than hardcoded false: a read-only host (Project, Task, `EntityNoteActions.none`) has no footer, and there the last row's border would otherwise float above empty card. The card also matches the grid's **width branch** rather than capping unconditionally — the grids centre at 820 only below `Breakpoints.entityFormMultiColumn` and go full-width above it, so an ungated `CenteredFormColumn` left the card the only inset element on an otherwise full-bleed page.

## The record's own history leads every detail strip

**The record's own history leads every detail strip, and the strip now scrolls itself.** Comments and Activity are one feed — `vm.comments` is `vm.activities.where((a) => a.isComment)` off a single `EntityActivityViewModel` — yet Activity sat **last** on a client, 15th of 15, while Comments sat first: four screens of horizontal scrolling apart on the 440–560 px pane, which shows about three tabs (invoiceninja/flutter#122). They are now adjacent at the head of all eleven strips, so the nine writable hosts pass **`initialIndex: 2`** (it keeps the landing tab whatever used to be first — the gated tabs all sit *after* the pair, so index 2 picks the same tab at every module combination, right down to Client's six-tab minimum), and Project and Task gained one where they had none. `EntityDetailTabs.selectTab`'s negative-index support survives — documented, and pinned by `entity_detail_tabs_test.dart` — but has no production caller now that Comments is index 0 on the read-only pair too. `test/lint/comments_surface_wiring_test.dart` pins the order by walking the ordered `EntityDetailTab(` / `buildStandardDocumentsTab(` offsets in each host, **not** by scanning `label: context.tr('…')`: the billing screens carry unrelated `label:` lines (KPI cells), seven Documents tabs come from `buildStandardDocumentsTab` and so carry no label in the host file at all, and the other four compute theirs. Reordering needs no migration because `MasterDetailNavController.lastTab` is session-only and in-memory. Four things about `_TabStrip`, which until this had **no `ScrollController` at all** and so never moved horizontally: a tab could be selected without being on screen — by a restored `lastTab`, or by the card's `View All` — leaving the body changed under an unchanged, un-underlined strip, the horizontal twin of the bug `_onSelectRequested`'s `ensureVisible` fixes on the page axis. (1) The reveal is **minimal, and neither flavour of `ensureVisible` can do it**: the static `Scrollable.ensureVisible` walks *every* enclosing scrollable (`while (scrollable != null)`), so from inside the strip it would drag the detail page's vertical scroll down on each tab change — which is the opposite of a bug where the parent calls it, `_onSelectRequested` using exactly that walk to bring the strip itself into view; and `ScrollPosition.ensureVisible` always travels to the alignment it is given, so centring the way Material's `TabBar` does would centre the **landing** tab and scroll the head of the strip out of view — `initialIndex: 2` would arrive with "Comments" already clipped off the left edge, destroying exactly the visibility the pair is there to buy. No pixel figure is quoted for that, here or in the code: the widths move with the font, the text scale and the locale, and the `the landing tab leaves the head of the strip visible` test is what holds the line. (2) The reveal rect is the button **inflated by a full `_kStripEdgeFade`**, not by the strip's 8 px padding: a mid-strip target landed flush against the viewport edge sits *under* the 32 px gradient drawn there, and the last 24 px of the label it just revealed renders up to 75% opaque — on screen but veiled, which is why "is it on screen" is not the assertion the test makes. At the ends the extra slack is free: the clamp pins tab 0 to `minScrollExtent` (where the leading fade is not drawn at all) and the last tab to `maxScrollExtent`. (2b) The strip listens to `selectTab` **as well as** to the controller, because `_onSelectRequested` skips `animateTo` when the requested tab is already active — so a reveal hung off the controller tick alone never runs for the one case `TabSelectionController.select` exists to deliver: tap `View All`, scroll the strip away by hand, tap `View All` again. (3) The parent **replaces the `TabController`** whenever the tab count changes (a module toggle does), so the strip re-subscribes in its own `didUpdateWidget`; miss it and the auto-scroll dies from that moment on, silently. The per-index `GlobalKey`s are deliberately *not* cleared there: they are positional, so an index keeps naming the button at that position, and clearing them would re-inflate every button's subtree for nothing. (4) The edge fades are gated on `hasContentDimensions`, not just `hasClients` — the position is attached on the first build but its extents only exist after layout, and reading one early throws a null-check straight out of `ScrollPosition.minScrollExtent`; that is also why the strip rebuilds itself once post-first-frame, since `attach` adds the listener but never notifies, and a strip nobody scrolls would otherwise never paint its trailing fade. (5) A width change that leaves `pixels` alone — a rotation, a window resize, the pane widening until the strip fits — reaches **no** `ScrollController` listener: `applyContentDimensions` only schedules a `ScrollMetricsNotification`, its own source noting that listeners "have, by definition, already been built this frame". Hence the `NotificationListener<ScrollMetricsNotification>` above the strip; without it a resize leaves whichever fades the *previous* width called for, and once the strip fits there is no scroll left that could ever correct them.

## A note is not a sentence — the bypass is keyed on `isComment`

**A note is not a sentence — the bypass is keyed on `isComment`, not `isCallNote`.** `activity_141` is *"User :user entered note: :notes"* and `activity_description.dart` renders the whole `:notes` token in the `strong` weight, so every comment used to read as a repeated prefix over a wall of bold. `ActivityRecordRow` already bypassed that for a logged call and its own doc said why; the real split is "something a person wrote" versus "a templated system sentence", so the bypass now widens to `Activity.isComment` (which subsumes `isCallNote`) and the **Activity tab changes too, deliberately** — one rendering, no drift. Consequences: bypassing drops the `:user` token, so the actor is re-added to the meta from `refs['user']` **and nothing else** (there is no contact fallback to write — `harvestNoteEntities` carries no `contact`, `activity_141` has no `:contact` token, and `note()` always stamps the admin guard's `user_id`); `_rebuildSpans` must early-return on `isComment` or every theme/locale change allocates spans nothing paints; `showIp` splits card from audit lens exactly as `activity_feed_row.dart:47-50` already decided; and a comment past 24 h prints a date, because `formatRelativeTime` bottoms out at `3w` and the exact stamp is a `Tooltip`, i.e. long-press only on touch. **Do not add an `ActivityTone` for comments** — `ActivityFormatter.render` resolves a comment's *icon* from `activityIconFor(tone)` under a comment reserving that decision, `accentSoft`/`accent` is indistinguishable from `viewed` at 16 px, and `accent` is user-overridable, so a green-branded company would get a comment badge that reads as `paid`.

## A client's comment feed is mixed, so the source record must be named

**A client's comment feed is *mixed*, and the source record has to be named.** `ActivityController::note()` copies `client_id` off the parent, so a note typed on invoice #0012 lands in that invoice's **client's** feed with nothing saying which document it is about. The server anticipated this — `Activity::harvestNoteEntities` is a type-141 special case shipping the `:invoice` / `:task` / … refs even though the template has no tokens for them, and `Activity.fromApi` already maps them into `refs` — but nothing rendered them, and the bypass above is what would have made them permanently unreachable. `ActivityRecordRow.hostWireName` names the first ref that isn't the record on screen. It is text, not a link: a tappable ref needs its own `TapGestureRecognizer` and disposal, which the bypass has just removed. **"Isn't the record on screen" is not the same as "isn't the host token", and the gap is a wrong record, not a missing one.** `note()`'s `PurchaseOrder` and `RecurringExpense` arms each write the document's own id into **two** columns — `$activity->purchase_order_id` *and* `$activity->expense_id` (`ActivityController.php`) — and `Activity::expense()` is a `belongsTo` with **no company scope**, so that second one resolves against whatever `expenses` row shares the raw auto-increment id. Sorting `purchase_order` / `recurring_expense` ahead of `expense` in `kActivityDocumentTokens` covers every *other* feed, because the document's own token matches first; on the document's **own** screen that token is skipped as the host and the loop falls straight through to the alias. Hence `kExpenseIdAliasHosts`, which drops `expense` outright for those two hosts — and **only for a note**, which is `activityNoteSourceRef`'s `accept` and not the shared walk: a *templated* row's refs are named rather than harvested, so seven templates that spell `:expense` would otherwise be stranded on those two screens (both constants live in `lib/domain/activity/activity_refs.dart`). Without it every comment on every purchase order was labelled with an unrelated expense's number and `View record` navigated to it — on hosted, where ids are global, potentially another tenant's number. It is deliberately **not** a general "skip the parent" rule: `Credit` copies `$entity->invoice_id`, the credit's *real* invoice, so a credit's comment naming that invoice is true and stays. Note the ordering test alone could never see this — it pumped `hostWireName: 'vendor'`, which is exactly the case the ordering already fixed.

## A comment cannot be edited or deleted

**A comment cannot be edited or deleted, so the row offers what it honestly can and the dialog says so once.** Verified server-side, not assumed: `routes/api.php:181-184` registers `GET activities`, `POST activities/entity`, `POST activities/notes` and `GET activities/download_entity/{activity}` and **nothing else** — no `Route::resource`, no bulk route — `ActivityController` has eight methods and none mutates a row (every `$activity->save()` in the backend is on a fresh `new Activity()`), and `activities` carries neither `deleted_at` nor `is_deleted`, so even a soft delete has nowhere to land. React and the legacy Flutter app are add-only for the same reason, and both render an activity row inert. That was invoiceninja/flutter#123 ("doesn't seem interactive"), and the ask is BACKEND.md § F3d. `CommentRowMenu` (`comment_row_menu.dart`) is the one menu, shared by `ActivityRecordRow` and `PendingCommentRow` so the synced and optimistic rows cannot drift the way the twin add-comment dialogs did: **Copy** (the displayed text — a logged call's marker stripped, or Copy hands back a glyph nobody typed), **View record** (the `hostWireName` ref from § A client's comment feed is mixed above, which a *menu item* can reach without the `TapGestureRecognizer` the note bypass removed — and it is `view_record`, never the per-entity `view_*` keys, since `view_expense` is "View expense # :expense" and would print the token), and **Delete**. Six things are load-bearing. **Delete is offered only on a queued outbox row, and only while `state != 'in_flight'` — checked twice.** The outbox is the sole real undo the client has, and `SyncRepository.discardOutboxRow` re-reads the row and then deletes an in-flight one *anyway*, keeping its request in play: right for the Outbox screen's explicit Discard, and the exact lie this surface exists to avoid, on the one screen built to fix "no way to delete". The build-time gate alone is not enough — `guardedOnTap` holds the closure across the Confirm-actions dialog, which is long enough for a drain to claim the row (an open *menu* is safe; the rebuild drops the item) — so `_discard` re-reads before acting and bails silently, the synced row replacing it within a second. Rendering **nothing at all** when no item qualifies (a synced, text-less, ref-less comment) is #111's rule for the list-row call button, and the menu therefore **owns its own leading gap** — emptiness is not predictable from outside, so a gap left in the caller would strand 8 px at the end of a row with no button. The `MergeSemantics` on a comment row now wraps **only the text column**: it merges descendant *actions* too, so a merge stretched over the row would announce the button and swallow its tap — the same absorption the row's own doc cites for the recognizers, and `activity_record_row_test.dart` fails against the pre-fix shape. Delete is tagged `confirm` + `isDestructive` so `menuChildrenFor` → `guardedOnTap` gates it on the Confirm-actions preference at *tap* time, and its `confirmSubject` is the note text, because a card shows two rows and a tab shows every one. The discard's verdict comes from `outboxDao.byId`, never from the call, **and that check has to sit outside the `try`** — `discardOutboxRow` no-ops silently on a row it can't find, and it deletes the row *before* reconciling the parent's dirty flag, so that cascade can throw once the note is already unsendable; folded into one block the throw skips the check and tells the user their comment survived when it did not. `OutboxViewModel.discard` splits the two for the same reason. And the **Add Comment dialog carries a one-line permanence hint** (`comment_permanent_hint`), because Copy only helps someone who has already stopped looking for Edit. It is the field's `helperText`, not a sibling `Text` in a `Column` — `AlertDialog` gives `content` a `Flexible`, not a scroller, so a second child is height the dialog may not have on a landscape phone with the keyboard up — and `helperMaxLines` must be set, since its default of **1** ellipsizes the whole sentence away at 360 px / 1.4x, the width and scale where the line matters most. Note `flutter test`'s substituted font is a square-per-glyph one, so `add_comment_dialog_test.dart` measures roughly double a real device's line count; that pessimism is what keeps the copy short. The hint is deliberately not repeated in `log_call_sheet.dart`, a structured capture form already at its height budget on a phone. Delete both the hint and its test the day § F3d ships.

## An inline link in a sentence cannot be hit by a finger

**An inline link inside a sentence cannot be hit by a finger, so the activity row itself is the target.** `RenderParagraph.hitTestChildren` dispatches a `TextSpan`'s `TapGestureRecognizer` only when the pointer lands inside `glyph.graphemeClusterLayoutBounds` — the font-metric line box, with **no slop** — and `hitTestSelf` returns true, so the paragraph swallows every miss. For `0092` at `bodyMedium` that box is ~17 dp inside a 72 dp row: three-quarters of the row's height is dead, the words beside the number are dead too (they resolve to spans with no recognizer), and a miss is indistinguishable from a dead link because `ActivityRecordRow` had no row-level `onTap` to catch it. A mouse hits the rect every time, so it read as finished on desktop for the life of the file — invoiceninja/flutter#143, and `activity_description.dart` is still the only `recognizer:` in `lib/`. Six things are load-bearing. **On touch the recognizers are not built at all** (`linkRefs: !Env.isTouchPrimary`): a ref that kept its accent without a tap would be the worse half of the bug — a link the paint promises and the hit test refuses — and colour alone is the cue #128 already ruled out there. The gate is the input device, not the viewport: a tablet has fingers. A pointer platform keeps its spans (a mouse is precise, and `TextSpan.mouseCursor` defaults to `click` wherever a recognizer is present), so both live in one row: the innermost recognizer wins the arena on an exact hit and the row catches everything else. **The destination must be a record the sentence NAMES**, which is what `ActivitySpans.refTokens` is for. `Activity.refs` is broader than the template, because the server stamps related ids the sentence never mentions: `RefundPayment::createActivity` sets `invoice_id` on a `REFUNDED_PAYMENT` row whose only *document* token is `:payment` (`activity_40` also carries `:adjustment` and `:payment_amount`, and names no invoice at all), and `InvoicePaidActivity` sets `payment_id` on a *":user paid invoice :invoice"* row — so a priority walk over raw refs would put a chevron on a refund row that opens an invoice nobody mentioned. That is `kExpenseIdAliasHosts`' lesson generalized, and it subsumes it. **Token membership is locale-stable; token ORDER is not** — translators move `:tokens`, they do not delete them — so ties break on `kActivityDocumentTokens`, never on the order the tokens appear in the rendered sentence. The only template where that tie is observable is `activity_10` (resolved as `_manual` / `_online` — the bare key is never looked up), where payment and invoice are both named and invoice wins, which is what `activityDeepLinkTarget` answers too — so the two agree *there*, and nowhere else by construction: the global feed still walks raw ids, so the refund row above opens the payment on a detail tab and the invoice from `/activity`, the dashboard card and User Details. Closing that means teaching `ActivityFormatter` to report the tokens it substituted; it is a known divergence, not an oversight. **Parties are not a fallback and the host is skipped**, so a row that names no document other than the record on screen is inert — no chevron, no tap — the state `ActivityFeedRow` has always had for a row with no `activityDeepLinkTarget`. On a billing doc's own tab that is *most* rows, and on touch they are now wholly inert, because `linkRefs: false` took the `:client` / `:contact` spans with it (`activity_6` is the shape: emailed invoice X for client Y to contact Z, read on invoice X) — the accepted cost of one destination per row, with the party still one tap away in the detail header that #128 cued; a client/vendor fallback would instead put an identical chevron on every row of a document's tab, duplicating the header's own cued link. **The `Material(type: transparency)` goes *inside* the decorated box**: the nearest ancestor `Material` sits above `ActivityListCard`'s opaque surface fill, so an ink feature registered there paints under the card and is invisible (the `Ink` ban's mechanism) — and the row's padding goes inside the `InkWell`, so the whole 72 dp band is the target rather than the text. **The `Semantics(button:)` + `ExcludeSemantics` merge is conditional on the sentence carrying no recognizers** — always true on touch, which is the platform this is for — because merging over live spans is precisely what § A note is not a sentence forbids: `SemanticsConfiguration` folds descendant actions into one, leaving a screen reader a single ambiguous tap for a row with two or three destinations. That merge **re-declares `onTap` and `tooltip`**, because excluding the subtree drops both — the `InkWell`'s own tap action and the meta line's absolute timestamp — and the first omission shipped here before the lint existed. Two smaller ones: the hover fill now tracks interactivity, since a highlight on an inert row is the desktop version of the same false affordance; and `Icons.chevron_right` is declared `matchTextDirection: true`, so it must never be hand-mirrored for RTL. `test/domain/activity/activity_target_routes_test.dart` pins that every token in `kActivityDocumentTokens` routes to a wired entity with a `detailBuilder`, because `goEntityRecord` returns **silently** for one that doesn't — a chevron that does nothing, i.e. this issue again one entity later.

## The per-entity activity fetch is eager, shared and user-scoped

**The per-entity activity fetch is eager, shared, debounced and stale-while-revalidate — and its cache is user-scoped.** The detail **screen** owns one `EntityActivityViewModel` (`entity_activity_view_model.dart`) that the card and both tabs read, so three surfaces cost one request; a VM built inside a tab `bodyBuilder` silently re-introduces a second and leaves the card empty, which `test/lint/comments_surface_wiring_test.dart` pins along with `kick()` and `dispose()`. `kick()` is armed from the first `bodyBuilder`, not `initState` — the scaffold only builds a body once the record resolves, so a deep link to a deleted record never spends a request that can only come back **422** (`ShowActivityRequest` validates `entity_id` with `Rule::exists`). Four cache rules, each of which fails silently: the key carries the **credential fingerprint**, because `entityActivity` narrows to `where('user_id', …)` for anyone who `cannot('view', $entity)` — so a company-scoped key would serve an admin's feed to a lower-permissioned user on the same install; `clearCache()` joins the logout fan-out in `services.dart` beside `clearPeekCache()` for the same cross-user reason, and the **Sync** tail in `Services.syncNow` for a different one — staleness, not leakage: a pass that re-downloads every entity table would otherwise leave the next record opened seeding its first frame from a peek taken before the sync (invoiceninja/flutter#160), and bumps a **generation** so a request still on the wire can't write the outgoing user's rows back afterwards; `addNote` clears the **whole** cache rather than one key, because a note fans out to the parent's client and the mapping needed to find it (plural wire name in, singular out) is exactly the kind of thing that fails quietly; and the TTL is a stored timestamp, never a `Timer`, which on a process-wide singleton leaks into `flutter_test`. It is a **seed, not a suppressor** — the request always goes out, because the one failure a comments surface cannot have is a colleague's note arriving late. Two silent-zero paths survive all of this and are server-side: the endpoint's `rows` window is over *all* activity for the record (`kEntityActivityRows` widens it to 200; only a notes filter fixes it), and a permission-narrowed user gets a 200 carrying only their own rows, which no client-side logging can see. Both are in `BACKEND.md`.

## A `Viewed` pill is the way into the activity that recorded the view

invoiceninja/flutter#154. Users were tapping the `Viewed` status pill on an invoice and asking why it didn't tell them *when* and *who*. The data was already local — `Invitation.viewedDate` + `clientContactId`, per contact — and already rendered in the Email History tab (`billing_doc_sends_tab.dart`, `Viewed: <date>` per row). Nothing pointed at it. The fix is three layers, and the order matters: a `Viewed <date>` segment in the header caption (zero taps, **every** status), the pill as a link to the Activity tab (which scrolls the matching view entry to the middle of the viewport and flashes it), and a hover tooltip on pointer platforms naming the most recent viewer.

**The pill saying "Viewed" and `hasViewedInvitation` are not the same fact, and an early draft shipped on the assumption that they were.** `calculatedStatusId` checks its viewed branch **last** — behind `isCancelled → isReversed → isPaid → isPastDue` on an invoice, `isConverted → isApproved → isRejected → isExpired` on a quote, `isApplied → isPartial` on a credit, and `statusId == sent` on a purchase order. So a viewed-then-overdue invoice reads **Past Due**, and gating the link on `invitations.any(hasBeenViewed)` would hang a "viewed by" tooltip under a pill saying *Paid*. `ViewedStatusPillLink.isViewed` therefore takes the pill's own rendered status (`calculatedStatusId == <entity>StatusComputed.viewed`), and the invitations only decide *which* row to name. The consequence is that the pill has no door on most documents most of the time — which is exactly why layer 1 leads: *"they're 40 days late, did they ever even open it?"* is the most valuable form of this question and the pill cannot answer it. `BillingDatesCaption.viewedIso` is status-independent and always can.

**The caption segment is date-only** though the value carries a time. Three reasons: at 12.5 px the with-time segment is half again as wide and does not fit one run in the wide branch's pane with the PDF open; both neighbours (`Date`, `Due Date`) are date-only, so a clock would pull the eye to the least urgent fact in a header that also has a red overdue chip; and the Activity row it pairs with reads `activity.created_at`, which `InvoiceViewedActivity` (`implements ShouldQueue`, `public $delay = 5`) puts at least five seconds later — with minutes shown, the door and the destination can visibly disagree about one event. It is appended **last**, after the overdue chip, because `BillingDatesCaption` already recolours the Due Date *value* red and w600 when past: the chip is an annotation glued to the segment before it, and inserting anything between them wraps the red chip away from its date at 390 px. Purchase order is the exception — its header has no 12.5 px register at all (number+pill, vendor, then a `Wrap` of `_LabelValue` cells at 11/16), so the fact joins that `Wrap` beside Due Date instead.

**There is no long-press tooltip on touch, and the issue's premise for one was mistaken.** It asked for a hovertip "like the long-tap on the phone icon" — but `PartyCallButton` wraps in `Tooltip` only `if (!Env.isTouchPrimary)` and its long-press *copies the number*. No long-press-reveals-info pattern exists in this app. A `Tooltip` is also a poor container for this: it dismisses ~1.5 s after release, its `message` is one unwrappable `Text`, no `TooltipThemeData` is registered in `lib/`, it is unreachable by keyboard, and it sets `SemanticsProperties.tooltip` — which iOS appends to the label, so an ungated one makes VoiceOver read the whole answer twice on every swipe past the header. Pointer-only, one line, with `+N more` (`plus_n_more`) for the other viewers. That count is **people, not views**: `markViewed()` is gated on `! $invitation->viewed_date`, so the server records the first view per contact and keeps no repeat count.

**Three things make the Activity destination best-effort, which is why it is the accelerator and not the source of truth.** The view event is written once, on first view, behind that same gate — so it is among the *oldest* rows in a newest-first 200-row window (`kEntityActivityRows`) and the first to age out; CSV import calls `markViewed()` without firing the event at all (`BaseImport.php`); and offline with no cache the tab renders `ErrorView`. In all three the tab still opens and the caption has already answered "when". No toast — the floor is the same one `View All` has had since #145.

**On a credit the flashed row is worse than the bundled template suggests.** `activity_60` reads `":contact viewed quote :quote"`, and the server stamps `credit_id`, so `refs['quote']` is absent and `activity_description.dart` substitutes an absent ref with `tr(token)` — the row renders as **"Bob Jones viewed Quote"**, with no number at all. Upstream Transifex string; `_app_pending.json` can only add keys, never override. Worth reporting upstream; nothing local fixes it, and an implementer who sees it will otherwise go hunting a ref-resolution bug that isn't there.

**Landing the user on `3w` would have moved the complaint rather than fixed it**, so `ActivityRecordRow._timestamp` now prints an absolute date past 24 h for **every** row, not just comments. That reverses a deliberate, test-pinned choice (`a system row keeps relative time however old`), inverted in the same commit. No reason was ever recorded for the split, and the rationale in that function's own doc — *"`formatRelativeTime` bottoms out at `2w`/`3w`, which is not an answer to 'when did they promise Friday?'"* — never depended on the row being a comment. `ActivityRecordRow` has exactly two call sites; the global `/activity` feed uses `ActivityFeedRow` and is untouched.

Coverage is a derived lint rather than a list: `comments_surface_wiring_test.dart` asserts the set of `entityWireName:` literals across every `ViewedStatusPillLink(` call site **equals** `kViewActivityTypeIds.keys`, so a fifth billing doc gaining a viewed status with no link — or one of the four losing its — fails the build. Nothing else would notice: there is no widget test on any of the four detail headers.

## A status pill that leads somewhere paints its ink inside its own tint

`StatusPill.onTap` is opt-in and the `onTap == null` branch is byte-identical to what shipped, because the pill lives in ~30 places — narrow list rows and wide-table cells among them, where `docs/row-actions-and-values.md` § *A narrow list row has exactly one destination* forbids a second target, and inside `payment_link_detail_screen.dart`'s already-navigating row. Four things about the link branch are not obvious.

**The ink has to be painted inside the decorated box.** The pill draws an opaque `*Soft` fill in the `Container` it returns; a `Material` placed *around* that box registers its ink on a layer below the fill, so hover, pressed and focus are all invisible — the same mechanism `no_ink_widget_test.dart` and `ActivityRecordRow` both spell out. So the tree is `Container(decoration:) > Material(type: transparency) > InkWell > Padding > Row`, with the pill's own padding moved inside the `InkWell` so the whole box is the target rather than just the text. `overlayColor` is resolved explicitly because the M3 default paints an opaque dark wash over a tinted surface on macOS, and **focus is a border, not an overlay fill** — an opaque fill would erase the status colour it sits on, and this border is the only focus cue the pill gets.

**The at-rest cue is an underline on the label, and the colour does not ride along.** `linkOrText` pairs `underlineAtRest` with `linkAtRestColor`, and copying that pattern here would recolour the label to `accentInk` — a per-company derived colour, unmeasured against six status tints, on the one widget whose own class doc records that 20 of 36 theme × status combinations failed contrast and that the label is `ink` because of it. A trailing chevron was considered and rejected on three counts: `StatusBounceOverlay` hangs its badge at `top: -3, right: -3`, exactly where a chevron would sit, and a record can be both bounced and viewed; `Icons.chevron_right` means "opens another record" in this app while `arrow_drop_down` means "opens a list"; and it costs ~16 px taken straight out of the record number, since the pill is the header row's only non-`Flexible` child. An underline costs zero width. (Purchase order's header shipped with a bare `Text` there and had to be wrapped in `Flexible` to match the other three.)

**The tooltip and the tap are threaded *into* the pill rather than wrapped around it**, which is why `ViewedStatusPillLink` is a builder. Wrapping would put both outside `StatusBounceOverlay`'s `Stack`, nesting a second `Tooltip` around the bounce badge's own and putting the badge inside the tap target.

**The `ExcludeSemantics` covers the label only.** Without it the outer `Semantics.label` merges with the `Text`'s own node and a screen reader reads the whole answer and then the word on the pill again. Excluding higher up would take the `InkResponse`'s node with it — and that is where the tap action *and* the focus action live, so the pill would announce as a button that could be neither invoked nor tabbed to. That is a partial exclude spelled `child:`, the case `semantics_excludes_need_ontap_test.dart`'s own doc names as what its opt-out marker is for; re-declaring `onTap:` to satisfy the scan makes the outer node explicit, which stops it merging the InkWell's and **costs the focus action** — the asked-for fix making the control worse. `status_pill_test.dart` asserts the real node carries `hasTapAction` and `hasFocusAction`, which is the stronger guard.

Touch target, measured, so nobody re-derives this: the pill is ~22 × 75 and the header row's cross axis is the 22 px number's line box — ~26.6 px with Inter Tight at 1.21 line height, and exactly 22 px under `flutter test`'s fixed-metric font. So the headroom for a `minHeight` is ~5 px real and **3 px in test**, and anything above 22 would fail `status_pill_test.dart`'s own `link.row.height == plain.row.height` assertion. It already exceeds the app's documented exception for this shape in both dimensions (`_kTriggerHeight = 20` tall × `actionButtonSize()` ≈ 32 wide, `party_call_button.dart:22-42`), and it deliberately does **not** reach for 44, which would push the dates and KPI strip down on all four headers. The test asserts the *row's* height and the pill's *width* are unchanged at 1.0× and `kTextScaleMax`.

## A one-shot reveal outlives its consumer, and the row scrolls itself

`ActivityRevealController` is a `ChangeNotifier` carrying `(activityTypeId, seq)`, and both halves are load-bearing. **`seq` increments on every call** so tapping the same pill twice re-fires — a plain `ValueNotifier` goes silent on an unchanged value, the trap `TabSelectionController.select` exists to fix. **The request persists** rather than being a pure event, because on the first tap the Activity tab is not mounted: the strip lands on Overview, and `_activated.add` + `setState` build the body the frame *after* `select()`. The tab reads `controller.request` in `initState` as well as listening.

It is deliberately not state on `EntityActivityViewModel`: that class must not notify from a build (`kick()` runs inside the host's `build`, which is why `_adopt` takes `notify: false` on both paths), and it is shared by three surfaces on eleven hosts, so a reveal notify would repaint the Comments card for nothing. The VM gains one non-notifying addition, `hasSettled` — the gate for giving up when the requested row is not in the window.

**`select()` comes before `reveal()`.** On the path where the tab is already mounted but offstage, notifying first runs its listener while the tab controller still points elsewhere.

**The row scrolls itself, from its own `State.context`, and there is no `GlobalKey`.** Two reasons. `EntityDetailTabs` arms a post-frame `Scrollable.ensureVisible` on the *strip* during the tap handler and each `ensureVisible` cancels the previous, so whichever is registered last wins — and a callback registered from the row's build phase always lands in the same frame's snapshot after the tap-phase ones, on first activation and on the already-mounted path alike. And a *conditionally attached* `GlobalKey` would be worse than useless: `Element.canUpdate` matches on `runtimeType + key`, so the key arriving and leaving would re-inflate the element at both ends of the flash, taking the `AnimatedContainer`'s tween with it (a fresh state initialises **at** its target, i.e. no fade either way) along with `_spans`' recognizers and the row's focus.

**The ticker mode is read inside the post-frame callback, not when the flash is requested.** `TabController.animateTo` notifies synchronously, but the `AnimatedBuilder` that rebuilds the `Offstage`/`TickerMode` pair only runs next frame — so a read at request time is always stale-false. It matters because a reveal can resolve *after* the user has moved on (tap the pill, the fetch lands two seconds later, they are on Overview), and scrolling an offstage row jerks the page. The flash is kept; only the scroll is skipped.

**The flash is its own nested layer, not the hover `Container` made animated.** That box carries the hover fill *and* the bottom hairline; animating it would put a 250 ms ramp on hover for every row on all eleven hosts — five times the framework's own 50 ms — which reads as lag when the pointer runs down a long audit list. Nested, the flash also paints over the hover fill and stays mounted, so the tween is continuous. It resolves to an **index**, not to `Activity.id` (which is `@Default('')`, so a server omitting `hashed_id` would highlight every row) and not to the `Activity` itself (freezed value equality, so two content-identical rows would both light up). 1600 ms, not the 900 the manage-cards sheet uses: there the row appears in a short list already under the cursor, here the whole page changed and the row lands mid-viewport ~280 ms after the tap.

## The activity tone map is the server's catalog, not a guess

`activityToneFor` mapped ids **10** and **25** to `ActivityTone.viewed`. Per `app/Models/Activity.php` those are `CREATE_PAYMENT` and `RESTORE_INVOICE`; the four real view events (7 `VIEW_INVOICE`, 21 `VIEW_QUOTE`, 60 `VIEW_CREDIT`, 136 `VIEW_PURCHASE_ORDER`) fell through to `neutral`, so "the client opened your invoice" rendered with the same grey circle as "someone archived a vendor". Nothing caught it because a wrong tone is not an error, and no test asserted a tone at all. Eight more arms were wrong the same way (22, 23, 24, 26, 27, 32, 36, 37 — all archive, delete or restore).

It is now `kActivityTones`, a `const Map<int, ActivityTone>` with the server constant name against every id, and **deliberately partial**: archive / delete / restore and the payment-failure ids fall through to `neutral` on purpose, because there is no failure tone and `ActivityTone.expense` paints red. Wrong arms were re-homed rather than dropped where the row still means something — `10 CREATE_PAYMENT` moved to `paid`, or payment rows would have gone grey; `11 UPDATE_PAYMENT` went to `draft`, because the tone follows what the event *means* and editing a payment is a record changing, not money arriving.

The guard is what matters more than the fix. `activity_formatter_test.dart` derives the expectation from the bundled `en.json` templates in **both directions**: every `activity_<N>` whose English text matches `\bviewed\b` must be in the `viewed` arm and the arm must contain nothing else (that set is exactly {7, 21, 56, 60, 136} — 56 is a vestigial "viewed ticket" key with no server constant, mapped rather than allowlisted so the sweep stays a pure derivation), and the same for `\bemailed\b|\bsent\b`. A third case cross-checks every toned id against `kActivityTypeLabelKeys`, the React-derived catalog — by substring for the two lexical families, which the catalog spells many ways (`payment_emailed`, `email_statement`, `einvoice_sent`, `remind_*`), and by exact key for `paid` / `draft` / `expense`, which have no lexical signal. Restating the map would only have pinned the mistake.
