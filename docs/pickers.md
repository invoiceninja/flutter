# Searchable pickers

Companion to CLAUDE.md § Forms — Searchable pickers. The main file carries which widget to reach for and one line per rule; this doc carries the evidence. Dismissal — outside taps and Android back — lives in `docs/popup-dismissal.md`.

## Opening a picker that already has a value shows the whole list

**Opening a picker that already has a value shows the whole list, and that takes two cooperating rules — don't remove either.** `RawAutocomplete` filters by the field's text, and the text of an untouched picker *is* the selected item's own name, so the naive reading offers back only the value the user already has; the ✕ (which also fires `onChanged(null)`) was the only escape. That was invoiceninja/flutter#34, and it applied to all ~109 call sites (plus 13 more through `OverridableSearchableDropdownField`), not just task Status. The fix: (1) `_isPristine` — while the text still equals the committed label the query counts as **empty**, so `optionsBuilder` returns the idle list; (2) an `onTap` bounce that writes the text away and straight back, because `RawAutocomplete` recomputes its options *only* on a text change (`_onChangedField`) and so a tap right after a selection would otherwise reopen nothing. Both are mirrored in `ClientPickerField`. Consequences worth knowing: the committed item is **hoisted to the top** of the idle list (it stays visible in a 250-row list, and the default highlight — row 0 — is then the current value, so Enter / Android's "Done" can't silently pick whatever sorts first); it carries a check and re-picking it routes through `unfocus()` rather than `onSelected`, because `RawAutocomplete._select` early-returns on an unchanged selection *before* hiding the overlay; and the hoist is **guarded** on `initialValue` still naming it, or the "add to a chip list" callers (`MultiEntityPicker` and friends, which keep `initialValue: null` and drop the picked item out of `items`) would re-offer what was just added.

## The options popover must not wrap itself in an `Align`

**The options popover must not wrap itself in an `Align`.** `RawAutocomplete` already wraps `optionsViewBuilder`'s output in `ConstrainedBox(tight) → Align(topStart | bottomStart)`, and a bare `Align` shrink-wraps only under an infinite constraint — so one of ours would fill the whole bounding box, leave the SDK's alignment nothing to move, and strand an upward-opening popover at the top of the screen. Related: pass `optionsViewOpenDirection: OptionsViewOpenDirection.mostSpace`, or a field low on a phone gets only the space beneath it, floored at a 48 px sliver — `test/lint/picker_popover_wiring_test.dart` now fails the build on a `RawAutocomplete` that doesn't (the line-item tax cell was the one that never did).

## Touch gets a different picker without a different widget

**Touch gets a different picker without a different widget.** `Env.isTouchPrimary` grows option rows to `InSizes.touchTarget`, and a list of **≤6** options drops the soft keyboard via `keyboardType: TextInputType.none` (**not** `readOnly` — `EditableText._shouldCreateInputConnection` ignores `keyboardType` but honours `readOnly`, and since `flutter test` forces `TargetPlatform.android` that would break every `tester.enterText` into a short-list picker). Six, not the usual ~10 "short fixed enum" figure: at 10 the rule reaches pickers that mean to be typed into (the import/export column mapper says so in a comment) and the design pickers sit close enough that one extra custom design would silently flip it. Row height also scales with `MediaQuery.textScalerOf` — a fixed extent clips Inter Tight's descenders past ~1.14× text scale.

## The ▾ is the only visible way to close a picker, so it must be a button

**The ▾ is the only *visible* way to close a picker, so it has to be a button.** `_reopenOptions` gates its close branch on `_suppressKeyboard` — the ≤ 6-options-on-touch case — so above that threshold the field is typable and a tap on it, or on the arrow, could only ever RE-open: the arrow was a bare `Icon` and its taps fell through to the field. On the Tasks filter bar from #134 that left the **Client and Project pickers with no tap-to-close at all**, and cost the Assigned User picker its own the moment a company hired a seventh user — the one control that looks like a toggle wasn't one, and which pickers had the bug depended on how much data the account happened to hold. It is now an `IconButton` sized exactly like the ✕ beside it (`buttonSize`, `tapTargetSize: shrinkWrap` — touch-target traps 2 and 3), calling `_focusNode.unfocus()` when `_optionsVisible` and `requestFocus()` + `_reopenOptions()` otherwise. Three things are load-bearing. An `IconButton` in the suffix **wins its own tap**, so `TextField.onTap: _reopenOptions` does not also run and re-open what the button just closed — the ✕ has worked that way in the same `Row` since it shipped. The open branch's two calls are **order-insensitive and must stay so**: `requestFocus` applies in a microtask, so the synchronous text bounce may recompute options while `hasFocus` is still false, and the overlay opens when focus lands because `RawAutocomplete` re-runs its visibility check on the focus listener — don't "fix" it into a post-frame callback. And the **glyph does not flip**: making it `▴` while open needs `_optionsVisible` to become observable, and notifying from `optionsViewBuilder` fires mid-build into the suffix's own `ListenableBuilder`, which has already built that frame. Hence the state-neutral `tr('options')` label; Material's `DropdownButton` keeps one glyph too. On touch a populated field now carries **96 px** of suffix (two 44 px targets plus `InSpacing.sm`), against ~72 before — so every call site lost 24 px of input width on touch, 12 on pointer. The narrowest host is not 360: the dashboard currency picker in `settings_popover.dart` renders inside `showMenu`, which caps at `_kMenuMaxWidth` = 280, landing the field at roughly 216–232 px — and `dashboard_mobile_app_bar.dart` reaches it on touch. It fits, but at 1.4× text scale a long label there ellipsizes one size class earlier than it used to, and a `TextField` scrolls rather than ellipsizing so a long *value* clips silently. That is the case to re-measure if a narrower host appears.

## A picker's empty state has to say something

**A picker's empty state has to say something, and its selection must not be resolved by scanning the list.** Two failures that look unrelated and share a screen. First, `SearchableDropdownField` renders a **disabled** placeholder when `items` is empty — and its `hintText` was **invisible**, which is the non-obvious half. `InputDecorator` gives the hint's slot to a label that has not withdrawn (`showHint = isEmpty && !_hasInlineLabel`), and `_labelShouldWithdraw` is `!isEmpty || (isFocused && enabled)` — a disabled, empty field can be neither, so the hint sat under `AnimatedOpacity(opacity: 0)` and `RenderAnimatedOpacityMixin.visitChildrenForSemantics` dropped it at alpha 0, so it was not announced either. The user got an outlined, un-tappable box with no ✕, no ▾ and no explanation. The fix is `floatingLabelBehavior: FloatingLabelBehavior.always` on that one branch, which withdraws the label and lets the hint paint at all ~100 call sites; a test asserting `decoration.hintText != null` is what let it ship, so assert the computed opacity, since **`find.text` cannot see it** — the `Text` is in the tree either way. Then `emptyHintKey` becomes meaningful, and it is worth passing wherever the entity can genuinely have zero rows: the default is `'loading'`, which promises something that will never arrive to a company that simply has no projects. Don't pass it where an empty list really *is* a loading state — the assignee roster arrives bundled on `/refresh` and always holds at least the signed-in user. Second, **resolve the selection with `EntityPickerField`**, whose class doc exists to kill `items.where((c) => c.id == draftId).firstOrNull`: every list stream in the app is active-only, so archiving (or deleting) the selected record drops it from `items`, `didUpdateWidget` blanks the field **without firing `onChanged`**, and the ✕ goes with it (`canClear` reads the controller text) — leaving a blank field over a list still filtered by an id nothing displays. `TaskFilterBar` had both, and a third: `watchPage(loadedPages: 100)` offered whatever page 1 of the login prefetch left in Drift, alphabetically-first out of the 50 *newest*, decoding every row to do it — where the Tasks list's own `ClientFilterKey` reads `clients.watchActiveNames`. A **filter** offers the whole local set (`watchActiveNames` / `watchAllForPicker`, idle cap 50); an edit form's picker offers one value (idle 20). `test/lint/task_filter_bar_wiring_test.dart` pins all three, structurally — `EntityPickerField`'s own suite already proves the mechanism, so what is left to protect is the wiring, and a widget test of that bar would need a `noSuchMethod` `Services` stub with three fake repositories to assert what a grep can see.

## The assignee roster has one home, and five invisible rules

**The assignee roster has one home now, and the five rules it enforces are each invisible at a call site.** `AssignedUserPickerField` (`lib/ui/core/widgets/assigned_user_picker_field.dart`) and its task-only sibling `TaskStatusPickerField` (`lib/ui/features/tasks/widgets/`) wrap `EntityPickerField` and read `Services` directly — the trade `UserNameLabel` and `UserAvatar` already make, and a deliberate break with `EntityPickerField`'s own "stays a leaf" rule: that rule is worth one line per call site only while the projections differ per entity, and for the roster they never do. (1) **`watchAllForPicker`, never `watchPage`** — a paged read offers only what page 1 of the login prefetch left in Drift and pays a `jsonDecode` per row for it. (2) **`UserDao.watchAllForCompany` is a bare `select(users)..where(companyId)`** — no `ORDER BY`, no state predicate — so the active filter and the sort are re-applied on top, and both halves bite: `archivedAt` is an int epoch (0 = not archived) and **never null**, so an `== null` test analyzes as dead code and filters the roster to *nothing*; and `List.sort` is not stable in Dart, so without the `a.id.compareTo(b.id)` tiebreak two users sharing a display name swap places between Drift emissions and reorder the list under the user's finger. (3) **The selection resolves through `watch(id)`** — both streams are active-only, so archiving the assigned user (or the status) otherwise drops the row from `items`, `didUpdateWidget` blanks the field *without* firing `onChanged`, and the form silently loses a value it still holds. (4) **Neither passes `emptyHintKey`**, because both collections arrive bundled on `/refresh` — the roster always holds at least the signed-in user (`CompanyTransformer::includeUsers` is not admin-gated) and the server seeds four statuses per company — so an empty list really is loading; note the #150 hide rule below is what keeps that true, since it never hides you. (5) **The hide rule is applied here and nowhere else** — `assignableUsers` (`lib/domain/assignable_users.dart`), gated on the device-local `services.hideUnverifiedUsers`. It rides in the `WatchBuilder` cache key, because that is the only thing that re-creates the stream, and the widget must **listen** to both of its inputs rather than read them once — the preference, because an edit screen stays mounted behind `/settings/**` while the switch is flipped; and `auth.session`, because `AuthRepository.restore()` starts `userId` empty and leaves it so whenever the restored company's `user_settings` row is missing or its lookup throws. An unlistened empty id exempts nobody, and since `_persistAndActivate` writes your own row without the three signals, *you* then satisfy every conjunct and vanish from your own field — with no rebuild to heal it. See § Hiding unverified users below. The four window-scan copies came onto the leaf with #150 — `project_edit_details_section.dart`, `client_edit_settings_section.dart`, `payment_link_overview_tab.dart` and `billing_doc_settings_tab.dart`, that last one feeding all five billing edit screens and keeping its own `User` label through the leaf's `labelKey` parameter. They had to: the hide rule cannot be applied to a picker that resolves its selection by scanning `items`, because narrowing the list there blanks a field that still holds a value — which is exactly what those four did. `task_filter_bar.dart` is a fifth call site and keeps its own copy, which since #150 is **no longer byte-identical and must not be "restored to parity"**: a *filter* has to offer every user the data might reference, or work already assigned to a hidden person becomes unfindable. Only the fields that *write* an `assigned_user_id` filter. `test/lint/assigned_user_picker_wiring_test.dart` pins all six assignment hosts — none of the four migrated ones has a widget test of its own, and neither do the five billing edit layouts — including that `_Lockable` still wraps both pickers on the task edit form — `IgnorePointer` alone only overrides hit testing, so without it Tab still reaches a picker on an invoiced task and the whole edit can be driven from the keyboard.

## The create-task-from-a-line sheet seeds the Status, not the assignee

**The create-task-from-a-line sheet seeds the Status and deliberately does not seed the assignee.** `emptyTask()` leaves `statusId: ''` and `watchAllByStatus` groups strictly on that key, so a task created there sat in **no** kanban column until the server's `TaskRepository::setDefaultStatus` assigned one on the round trip — i.e. never, offline. That is invoiceninja/flutter#135's defect in a second place — and not the last one, because the Daily / Weekly / Calendar FABs all `goToCreateRoute(context, '/tasks/new')` bare and `TaskDailyActions.logTime` seeds only a `timeLog`, so every one of those still creates a task no column shows until it syncs. The fix here is a subscription of its own in `initState` (not the picker's — `EntityPickerField` requires `itemsStream` to hand back a fresh stream per call, and drift dedupes the identical query so the second watch is free; and not a `StreamBuilder`, which would be a `setState` during build) latching off on a `_statusTouched` flag that is set by **any** change, a clear included, or the next emission silently undoes the user. "First" means `watchAll`'s first row — `statusOrder`, then name — which is the board's leftmost column; the *server* picks its own default by `id ASC` instead, and ours is deliberately the order the user can see, with no post-sync jump either way because `setDefaultStatus` only runs when `status_id` arrives empty. The assignee gets no such default because there is no correct one — an invoice's own `assigned_user_id` is usually whoever raised it, not whoever does the work. Two more things about that sheet. The pickers sit **below** the Date / Start time / Duration / Rate block, not beside the description: the sheet exists to answer "when does this work happen" (#88), and on a phone bottom sheet two ~66 px fields above that block push the whole point of the screen under the fold; the full task form agrees about the relative order, keeping both as the last of its identity block. And they are **stacked full width, never paired into one `Row`** like the two above them — on touch a populated picker spends 96 px of its width on the ✕ + ▾ pair, so half a phone leaves under 100 px for a name, and a `TextField` scrolls rather than ellipsising, so a long one clips with no cue at all. Finally, worth knowing before answering a user: **assignment notifies nobody, ever.** `TaskRepository::save` runs `$task->fill($data)` in *both* of its branches before the `$data['assigned_user_id'] != $task->assigned_user_id` guard, and the column is `$fillable`, so the two sides can never differ and `TaskAssigned`'s single dispatch site is unreachable — on an update as much as on a create. Server-side, the app already sends the field correctly; details and the fix to propose are in BACKEND.md § F7.

## Re-picking the value the field already holds is a real command

**A re-pick of the value the field already holds is a real command, not a no-op.** `RawAutocomplete._select` early-returns on an unchanged selection *before* hiding the overlay, so routing the committed row through it is a dead tap under a popover that stays open. The row calls `onChanged` and unfocuses directly instead — several callers depend on it (re-seeding a payment allocation's auto-filled amount, re-binding a stream, retrying a change their own handler vetoed, re-adding an item whose chip was deleted). Enter / Android "Done" deliberately does **not** do this: it dismisses, so the Done key can't silently re-add a chip-adder's last item.

## A picker needing inline create can't be a `SearchableDropdownField`

**A picker that needs inline "create new \<entity\>" can't be a `SearchableDropdownField`.** Two of its properties defeat that, both silently: Flutter's `RawAutocomplete` only mounts the options overlay while the option list is **non-empty** (`_canShowOptionsView`, `autocomplete.dart`), so its `footerBuilder` is unreachable for a name that matches nothing — the one case inline-create exists for; and it renders a **disabled** placeholder when `items` is empty, so an account with no rows yet gets a dead field. Build a dedicated `RawAutocomplete` that appends a synthetic create option (keeping the list non-empty), and route that option from `InkWell.onTap` plus an `onSubmitted` interceptor — **never** through `onSelected`, because `RawAutocomplete._select` early-returns on an unchanged selection and `optionsBuilder` doesn't re-run for unchanged text, so the row goes permanently dead after one cancelled create. References: `ClientPickerField` (`lib/ui/core/widgets/client_picker_field.dart`), `TagPickerField`, and `_ProductCell` (`line_item_editor/line_item_table_desktop.dart`). **Tab is a fourth routing path, not a variant of Enter**: `_ProductCell`'s key interceptor calls `onFieldSubmitted()` directly and so bypasses `TextField.onSubmitted` entirely — a create routed only through `onSubmitted` still dies on Tab. `searchable_dropdown_field_test.dart` pins the footer limitation; `test/lint/inline_create_routing_test.dart` pins both the `onTap` routing and the no-self-`Align` rule above (which had no test at all, and which `tag_picker_field.dart` and `_ProductCell` were both violating).

## Hiding unverified users

**A user with no evidence of ever having signed in can be kept out of Assigned User fields, and the rule is deliberately much narrower than the flag the issue named.** invoiceninja/flutter#150 asked for a config toggle keyed on `Verification Pending`, but `email_verified_at == null` means **four** different things (BACKEND.md § F4) and three of them are active, working users: a hosted owner who never clicked verify, anyone who has ever changed their email address, and pre-2021 self-hosted owners. Hiding those is invoiceninja/flutter#47 — "this looks like the account was compromised" — in a worse place, and invoiceninja/flutter#46 separately settled that the account owner must stay assignable app-wide (`test/lint/no_user_list_owner_filter_test.dart`). So `isHiddenFromAssignment` (`lib/domain/assignable_users.dart`) is a conjunction, and **every conjunct rules out one reachable class of real user**: `email_verified_at == 0`, **`!has_password`** (`UserFactory::create`, the `POST /users` invite path, never sets one, and `VerifiesUserEmail::confirmWithPassword` is what sets it when an invite is accepted — so cases 2-4 are excluded by *mechanism*, not by heuristic), `oauth_provider_id` empty (an OAuth signup writes `'password' => ''` and leaves `email_verified_at` null — `LoginController`'s `email_verified_at = now()` there is commented out — so a Google/Apple/OIDC owner is password-less *and* unverified; every OAuth path that can authenticate someone sets that column first, and the Google branch outright *rejects* a sign-in for a provider-less user, so there is no silent-link path), `last_confirmed_email_address` empty (an **OAuth user who changes their email** trips all three of the above at once, because `UserController::update` nulls `email_verified_at` and all four `oauth_*` columns together — this is the only thing left standing), not the account **owner**, and never **you** (`_persistAndActivate` hand-builds your own row's payload without `email_verified_at`, `has_password` or `last_confirmed_email_address`, so after any delta `/refresh` you look un-onboarded to yourself — and that exemption is also what keeps the roster non-empty, which is why rule 4 above still holds). `has_password` had no other consumer in `lib/` when this shipped, so it has never been validated end-to-end here; the conjunction contains that risk, since a wrongly-`false` `has_password` degrades the rule to roughly the raw flag and never widens past it. `passkey_enabled` / `passkey_count` are on the wire but unmodelled — a passkey-only signup path would need a sixth conjunct.

**The preference is device-local and off by default** (`nav_state.hide_unverified_users`, schema v10, `HideUnverifiedUsersController`) — the opposite default to its two bool siblings, because this one removes people from a form rather than adding chrome to one. It is applied in exactly one place, `AssignedUserPickerField`, and therefore only to the six fields that *write* an `assigned_user_id`; the Tasks assignee filter, the Clients `assigned:` filter and the Activity user filter are untouched, or work already assigned to a hidden person would become unfindable.

**`isHiddenFromAssignment` has two renderers and that is the point.** Besides the picker, Settings → User Management badges a hidden row "Hidden from assignment" (muted, not warning — the `current_user` badge beside it set that precedent) while the toggle is on. It has to, because that badge and the neighbouring `verification_pending` one deliberately do **not** cover the same rows: the latter is broad by #47's decision and is also true of an active owner and of anyone who changed their address. Without it a hidden row and a visible one look identical on the one screen someone visits when a colleague has gone missing from their pickers — and that screen is also where **Resend Email** is, which is why searching Settings for "verification" is catalogued to land there rather than on the toggle. The row passes `signedInUserId: isSelf ? user.id : ''`, which reproduces the leaf's self-exemption without threading the id twice, and the screen resolves the preference once in a `ValueListenableBuilder` so `_UserRow` stays a listener-free const build. **The badge also carries its own `!isArchived` guard, which is deliberately NOT part of the shared predicate**: `assignableUsers` drops archived and soft-deleted rows *before* the hide step, so an archived user is absent from every picker whether the preference is on or off — badging one would claim an effect the toggle does not have, and would contradict `hiddenFromAssignmentCount`, which excludes them, so the card would say "1 user hidden" while this screen badged two.

**Three things about it are legible only in the Device Settings card**, which is why that card carries a live count (`sidebar_counters_section.dart`'s `_BadgePreview` is the precedent — "picking 'Overdue' shows the actual red number you're about to get"). The off-state sentence says "would be hidden" rather than naming the email flag, because the number is the narrow rule and "has never confirmed their email address" describes a wider set — an email-changer and an unverified owner both satisfy it and are badged Verification Pending, yet are deliberately not counted. The count collapses at zero but **the card never does**, per `phone_actions_section.dart`'s rule that a disappearing control reads as a bug; the card's heading is `users`, not `assigned_user`, because that key is the literal label of the Tasks *filter* picker and of the `assigned_user` list column on eight entities, none of which this governs; and the `:count` strings stay out of `kAssignedUsersSearchKeys`, because `settings_search_catalog_test` fails the build on a catalog key that resolves with a placeholder.

Two limits worth knowing before answering a report. **The roster is only refreshed by a full sync** — `company.users` rides in the server's `first_load` / `mini_load` include sets and the delta `/refresh` sends neither, `UserRepository.refreshAll` has no caller in `lib/`, and users are not in `Services._resyncSteps` — so a colleague who verifies today stays hidden until the next cold start (`restore()` forces `fullSync: true`) or until someone opens User Management, whose paged `GET /users` upserts fresh rows. That is why the card's link points there. And **clearing a hidden assignment is a one-way door**: `EntityPickerField` splices a currently-assigned hidden user back into the list, so they can be re-picked while the field still holds them, but clear it and save and they cannot be re-assigned without going back to Device Settings.
