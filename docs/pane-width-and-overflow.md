# When content doesn't fit its pane

Companion to CLAUDE.md § Design system (v2) (the pane-width rules). Four surfaces that overflowed a narrow pane, and the arithmetic behind each fix. The recurring trap: the gate must be computed ONCE per screen and threaded to every half, because an AppBar is built outside the body and no `LayoutBuilder` inside it can inform the other.

## A filter surface too tall for its pane becomes an icon

**A filter surface too tall for its pane becomes an icon, and the chip strip that replaces it renders nothing at all when nothing is filtered.** Three stacked full-width pickers cost ~180 px of a 412x915 phone, ~230 once a filter adds the Clear row — with the ~60 px view header below it, close to a third of a 915 px viewport, and the Tasks calendar grid never scrolls so it came straight out of the day cells (invoiceninja/flutter#136, the fourth density report from the same Android tester after #101, #104 and #125; #131 is theirs too but asked about placement and colour, not density; #101 settled the shape: *"this doesn't need to be a box if the box itself is not a field that can have data entered into it"*). Below the breakpoint the pickers move into `openTaskFilters`, reached from a `FilterIconButton` (`lib/ui/core/widgets/filter_icon_button.dart`) in the AppBar, and the body keeps only a `Wrap` of removable chips once something is applied. `/activity` shipped this first and `client_statement_screen.dart` shipped the gate; the leaf is shared so the dot cannot drift. Ten things are load-bearing. **The gate is computed once per screen and threaded to both halves**, because `Scaffold.appBar` is built outside the body and no `LayoutBuilder` inside the bar could ever inform it: compute it twice and a 600-648 px pane renders the stacked pickers *and* suppresses the icon, while a 600-832 px window (the 232 px rail leaving a sub-600 pane) renders both chromes or — with the polarity flipped — neither, making the filters unreachable with previously-set chips you can delete but never set. All of it is silent and all of it looks right on a desktop. **`buildTasksViewAppBar` therefore takes `wide` as a parameter** rather than reading `MediaQuery`, the split `EntityListAppBar` already makes (chrome from the pane, hamburger from the window) — which also makes that function's own claim about the toggle's position stable across views true for the first time, since the Tasks *list* had been pane-gated all along. **The threshold subtracts the gutters**: the gate this replaced sat *inside* the bar's `Container(padding: horizontal: 24)`, so it really tested `pane − 48 >= 600`, and `taskFiltersInline(paneWidth:isPhone:)` keeps that arithmetic in one testable place. **`!isPhone` is the other term** (flutter#51 again — a landscape phone is a ~658 px pane on a 412 px-tall viewport, and each picker there spends 96 px of its width on the ✕ + ▾ suffix). **The early return sits above the `Container`**, or the free case still pays a ~17 px bordered slab; and `context.read<Services>()` lives inside `taskFilterPickers`, so the collapsed-and-unfiltered path touches no DI at all and is pumpable with no `Provider<Services>` in the tree — which is exactly how its 0 px is asserted. **Never `actions:` in a `flexibleSpace` AppBar branch**: `AppBar` builds `Stack([flexibleSpace, Material(toolbar)])`, so the toolbar paints over it and — hit-testing being reverse paint order — an action there sits on top of whatever the `Row` put at the trailing edge and swallows its taps. That branch's children also get **45 px** (`InSizes.headerBand` 69 − 24 of padding), and a default 48 px `IconButton` there neither fits nor throws: the constraints clamp it and it renders short, so pin it with `actionButtonSize()` and assert the *size*, never the absence of an overflow. **The chips are labelled by dimension, not by value**, and the width is measured rather than guessed — with the bundled Inter Tight, because `flutter test` substitutes a square-per-glyph font that over-measures text by roughly half and would have argued the opposite. All three dimension chips are **one 65 px run** on a 412 px phone at any text scale, wrapping to a second (117) only at `kTextScaleMax` or on a 320-360 px one; a resolved name is several times the label's width, so three value chips cannot share a run and the strip would cost most of what collapsing it saved, in the one state the user actually works in. The `*NameLabel` resolvers would also each misbehave inside a chip (`ProjectNameLabel` prints the raw hashid unresolved, `UserNameLabel` an empty label and then a bare em dash for an id the roster cannot resolve, and all three hardcode a font size over the chip's own label style). `assigned_user` rather than the shorter `user` is affordable *because* of those measurements, and is worth it: Activity's strip already uses `tr('user')` for a different dimension, so the short word would mean two things across two filter strips. **The chip body opens the sheet and only the ✕ removes** — `FilterTokenChip`'s contract, not Activity's `_Chip`, because here there *is* a per-dimension editor to land on and a mis-tap should not destroy the filter it was aimed at. `Wrap`, never a horizontal scroller: a chip pushed off the edge hides an active filter, which on the kanban board makes the `filtersActive` drag lock inexplicable. **The sheet is height-capped, not fractioned** (`line_item_picker_sheet.dart`'s recipe, including subtracting the keyboard inset from the cap as well as padding by it): three fields under Activity's `heightFactor: 0.92` would cover the board and hide the live, Apply-less filtering the sheet performs. Its body needs a `ListenableBuilder` on the filters or `clear_filters` empties the view model while all three fields keep their old values — `EntityPickerField.selectedId` is a constructor argument. And **the filter notifier needs the disposed guard its four hosts already apply to their own async notifies**: a bottom sheet is pushed on the shell **branch** navigator and the dialog on the **root** one (`showModalBottomSheet` and `showDialog` default `useRootNavigator` differently, which decides what can dismiss each), `RunningTimerPill` paints *above* the shell over either, and its tap opens a task pane — which locks `TaskListScreen` to the plain list, unmounts the four custom views and disposes their view models, leaving an open sheet bound to a dead `ChangeNotifier` (asserts in debug, silently no-ops in release). Two smaller consequences: a collapsed bar owns no gap, so nothing may rely on it for spacing (the day / week / month headers draw the next band's border themselves, and on kanban the AppBar's `surface` over the body's `bg` is the only seam); and a filtered view that yields nothing now offers `clear_filters` instead of a dead end on Daily and Weekly, the escape hatch `EntityListScreenScaffold._emptyState` already gives every entity list — reusing its two Transifex keys and its reasoning, but not inheriting it, because these four custom views never go through that scaffold at all and the ones its comment lists as having fallen through are *entities*, the Tasks list among them. It matters *more* once the pickers collapse, since the pickers used to be the explanation sitting directly above the emptiness. **These copies are gated on `hasFilteredOutRows`, never on `filtersActive`** — which is also where they diverge from the generic one, whose `hasActiveFilters` is the best a list VM can do (its rows *are* the filtered set, and the unfiltered comparison is a query); a day or week VM holds both sets in memory, so it can answer the honest question: a day or week with nothing logged is equally empty with a filter applied, so the bare flag sends someone whose Tuesday was simply idle to "Clear filters" — which reveals nothing — and on Daily takes away the `Log time` action they came for. The predicate is `filtersActive && rows.isEmpty && <the same derivation over the unfiltered set>`, in that order, so the second pass only runs once the first has already come back empty.

## The three time-oriented Tasks headers take the screen's pane bool

**The three time-oriented Tasks headers take the screen's pane bool, and the calendar one had no width branch at all.** `TaskDailyHeader`, `_WeeklyHeader` and `TaskCalendarHeader` each render inside the content pane, and the first two used to answer that with `MediaQuery.sizeOf(context).width` — the *window* — so in the 600-832 px band (rail up, pane under 600) they drew full-label chrome into a narrow pane. They now take `required bool wide` from the same `LayoutBuilder` local that feeds the AppBar and the filter bar; one read per screen, four consumers, and `task_daily_header.dart` drops its `adaptive.dart` import with it. The calendar header had **neither** a branch nor anything that could shrink — the month label was a bare `Text` and the only flexible child was a `Spacer` — so on a hosted account with a connected calendar it asked for ~677 px inside a 412 px pane and clipped directly above the grid; self-hosted it still clipped at 320 px, and at `kTextScaleMax` everywhere (`task_calendar_header_test.dart` sweeps three account states across seven widths and both text-scale ends, and the old shape fails most of them). Three things fix it and the **first is the one that makes an overflow impossible** rather than unlikely: the label moves into an `Expanded` with `maxLines: 1` + ellipsis, so the row finally has a child that can absorb what is left; `Today` collapses to `Icons.today_outlined`, the swap its two siblings already make; and `CalendarConnectMenu` gains a `compact` state, without which the arithmetic still fails by ~128 px at 412 — it is a `Row(mainAxisSize: min)` with no flexible child and a `ConstrainedBox(maxWidth: 200)` around the account address, i.e. 171-280 px that cannot shrink. Compact is an **icon plus a menu, never a bare icon**, because this header is the only place in the app that shows which calendar account is connected and the only place to disconnect it (there is no calendar screen under `/settings`): the address rides in the menu as a disabled row and Disconnect routes to the same confirm dialog, where a tooltip would have put the address behind a long-press on the one platform that collapses the row. Narrow also shortens the label — a readability call, not a width one, since the full name is 145 px in `es` and the `Expanded` would ellipsise it. **Both lengths go through a `DateFormat` *skeleton* (`yMMMM` / `yMMM`), never a literal `'MMMM yyyy'`**, and that is a general rule for any month-or-year label: a literal pattern pins the field order and drops the locale's own connectives, so it rendered "septiembre 2026" and "setembro 2026" without the `de` that `es` and `pt_BR` require, and "9月 2026" instead of "2026年9月" in **both** bundled CJK locales — a backwards date. Several unbundled server languages are worse, since a literal `MMMM` takes Polish, Russian, Greek, Finnish and Croatian's *genitive* month ("września 2026": correct inside a full date, wrong standing alone), and `formatter.settings.locale` is the company's language, not the UI's. Two things make the skeletons safe: `GlobalMaterialLocalizations` runs `loadDateIntlDataIfNotLoaded()`, which loads intl's per-locale symbols **and** its skeleton patterns from Flutter's own generated set — so `main.dart`'s delegate list is what makes this work, and a widget test whose delegates are only `kTestLocalizationsDelegates` throws `Locale data has not been initialized` for any explicit locale while passing for a null one (which resolves to `en_US`, the single locale intl ships uninitialised). And that generated set carries `pt` and `zh` but **not** `pt_BR` / `zh_CN`, the two the app actually declares, so those resolve through `Intl.verifiedLocale`'s short-locale fallback — verified to render identically, but it is a fallback, not a match. Measure such a label under the *app's* delegate path, never intl's own `initializeDateFormatting()`, whose data is the full CLDR set and therefore not what ships. **Which of the two states the chip takes is a *second* width read, and deliberately a local one.** `wide` answers "does this pane get desktop chrome?" for the whole screen; whether the address fits inline only this row can know, because it turns on this row's own gutters, its own controls and the active text scale — so the header carries a `LayoutBuilder` inside its padding (making the constraints the content box) and compares it against 524 px of fixed wide chrome plus `textScalerOf(context).scale(145)` for the label (`Today` is the row's only other text-bearing child and is pre-counted at its `kTextScaleMax` width, which keeps the fixed term scale-safe at the price of a gate 15 px conservative at 1x). Sized for the **label**, which buys the strong invariant: on the wide branch the month label is never truncated, and it is the address that steps back into its menu. No flex arrangement can do this instead, which is worth knowing before trying: at a 600 px pane the wide row's fixed children already come to 524 of the 552 px content box, so making a child shrink only moves which one gives way: an `Expanded` label alone starved to "…" at a 602 px pane (22 px of the 112 it needed), and adding a `Flexible` around the chip on top of that traded the starvation for a 7 px overflow *inside* the chip at 648 px and `kTextScaleMax`, since the chip has no flexible child of its own. `RenderFlex` allocates flex *proportionally and before laying out*, so "give the label what it needs and the chip the rest" is not expressible; and a `Flexible` around the chip is wrong in the other two states as well, since a compact — or self-hosted, where the widget paints nothing — child takes less than its share and the remainder is stranded as trailing space, floating `Today` in from the right gutter. Both compact triggers must pass `icon:` explicitly or `no_horizontal_more_icon_test.dart` fails the build: `PopupMenuButton`'s default trigger is `Icons.adaptive.more`, the horizontal ellipsis on iOS and macOS. And measure this kind of fix with the **bundled** font loaded — `flutter test` substitutes a square per glyph and roughly doubles every string, which is enough to move a width assertion either way. After the threading, **no pane-shaped widget under `lib/ui/features/tasks/` reads the window's size at all**: the four `MediaQuery.sizeOf` reads left there are modal-presentation forks (`task_filters_sheet.dart`'s dialog-vs-sheet and its height cap, `create_task_from_line_item_sheet.dart`, `edit/time_entry_editor_sheet.dart`), which genuinely want the window. `tasks_view_wiring_test.dart` pins that per file, and pins it as "no window-size read" rather than as the one receiver the bug happened to use — hoisting `MediaQuery.sizeOf(context).width` into a local, or reaching for the older `MediaQuery.of(context).size`, re-introduced it with the older grep green. `textScalerOf` is deliberately not on that list.

## A tab strip is a width budget, and Material spends 52 px first

**A tab strip is a width budget, and Material spends 52 px of it before you write a line.** The narrow billing-doc edit strip ran **582 px of content in a 411 px viewport** — 1.42 screens on the reporter's Pixel-class phone (1080 physical at dpr 2.625) — and it was the one strip in the app with no edge fade, no `ScrollController` and no reveal, so the tabs past `Settings` were simply cut off with no cue at all (invoiceninja/flutter#140, the fifth density report from the same Android tester after #101, #104, #125 and #136). The ask was to move the `PDF` tab to a button beside `Save`; **that alone leaves 524 px, still 1.2 screens**, because three separate things caused the overflow and only one of them was PDF — the measured ladder, rendered with the bundled font, is 582 → 492 (drop the E-Invoice tab) → 440 (drop Material's leading offset) → 382, which fits with 29 px to spare. `billing_doc_edit_tab_strip_width_test.dart` asserts each rung as `maxScrollExtent`, and it must keep its `FontLoader`: `flutter test` substitutes a square-per-glyph font that over-measures by roughly half, so without it every number there is fiction in both directions. Eight things are load-bearing. **The 52 px is `TabAlignment.startOffset`** (`_kStartOffset`, `tabs.dart`), the M3 default for a scrollable `TabBar` and therefore the failure mode of writing nothing at all — no grep can find it, and it also de-aligns the first tab from the content beneath. It **cannot** move to `theme.dart`: `TabAlignment.start` *asserts* on a non-scrollable `TabBar` (`_debugTabAlignmentIsValid`) and the app has three, one of them (`debug_panel_section.dart`) scrollable only when narrow, so a global theme would crash on a wide window. **The E-Invoice tab was never gated**, against its own file's class doc ("surfaces only when company has eInvoice enabled — gated in M4"); React's predicate is `enable_e_invoice === true || e_invoice_type === 'PEPPOL'`, and the PEPPOL arm is not redundant — the switch defaults false while the type defaults to EN16931, so a PEPPOL company that never touched the toggle still needs the form. It resolves off the **async** `SettingsRepository.resolved`, never the synchronous `resolvedIfReady` seed, which is refreshed only as a side effect of a `resolved()` call and would hold a stale answer for the rest of the session after someone switches e-invoicing on — `peek_is_seed_only_test.dart` fails the build on the attempt, and it is right to. The tab therefore **starts hidden and arrives** two frames in: a tab that appears is ordinary async UI, where one that vanishes can take a tap with it, and it is the last tab, so on a phone it arrives off-screen. The gate is resolved **once in the layout and threaded into the desktop notes card**, or the two widths disagree about the same company. **A conditional tab means the count is dynamic**, so `TabController(length: 7)` is gone: each layout hands `BillingDocEditTabStrip` (`billing_shared/edit/billing_doc_edit_tab_strip.dart`) one `List<({String label, Widget body})>` built from its own `_tabKeys`, and the strip sizes its controller from that list's length. Label and body travel **together** through a single `switch`, because the parallel `tabs:` / `children:` lists this replaced could drop an entry from one and not the other, and the mismatch throws at runtime rather than compile time. The strip is one widget rather than five copies for the same reason the KPI strip is: what it holds is not markup but a controller lifecycle — the plural `TickerProviderStateMixin` (`SingleTickerProviderStateMixin.createTicker` asserts `_ticker == null` and never resets it, so the second controller throws on exactly the resize this handles), the index clamp, and disposing the outgoing controller *before* the rebuild, which is safe because `TabBar` and `TabBarView` both detach behind `_controllerIsValid`, reading `_controller?.animation != null` and so skipping a disposed one. **The width is read ONCE, in the screen, and threaded to both halves** — the strip and the button must appear together or not at all, the AppBar is built outside the body so no `LayoutBuilder` in the layout could inform it, and both closures are created in one `build`, so a bool is all it takes (the Tasks filter-bar rule again). `EntityEditScaffold` still measures its own header slot for the spread-vs-compact action bar, and that third read is deliberately **not** threaded: the header slot is always narrower than the screen, so `narrow` implies compact and the ordering is what keeps the button's `Tooltip` out of `OverflowView`; the reverse disagreement, roughly 600-680 px, is a compact bar with no preview button in it and is harmless. The threshold is **`Breakpoints.wide` (600), not the body's own 1024**: at ≥ 600 the strip already fits so there is nothing to move, and — the non-obvious half — pane < 600 guarantees `EntityOverflowActionBar` takes its `compactBar()` branch, which is what keeps the new button out of `OverflowView.flexible`, where `entity_edit_scaffold.dart` forbids the `Tooltip`/`OverlayPortal` it carries. **The button previews the DRAFT**, not `⋮ → PDF → View PDF`, which `go`s to `/invoices/:id/pdf` and renders what the server last stored — a different document the moment the form is dirty, and no document at all on a create form; it pushes `BillingDocPdfScreen` with `revision` null, so it fetches once where the tab re-fetched 600 ms after every keystroke. It is **disabled, never hidden**, without a client (a vendor, on purchase orders): hiding it makes the header jump the moment a party is picked. And **the residue is the point of the fades** — German (441), a 360 px phone, text scale past ~1.08 and recurring invoices (472, the extra `Schedule` tab) all still scroll, so `ScrollEdgeFades` (`lib/ui/core/widgets/scroll_edge_fades.dart`) says so. It is driven by **notifications rather than a controller** — `ScrollNotification` for position plus `ScrollMetricsNotification` for a width change that leaves `pixels` alone, which are siblings rather than subclasses (`Notification` vs `LayoutChangedNotification`), so one listener cannot catch both. Not because `TabBar` hides its controller (it exposes `TabBar.scrollController`) but because staying controller-free is what lets the leaf wrap *any* scrollable with no lifecycle for the caller to own, which is the precondition for it ever replacing the two hand-rolled strips; Material documents the same pattern for a `TabBar` in its own `tab_bar.3.dart` sample. Its gradients are copied from `EntityListStatusTabs._edgeFade` — `PositionedDirectional` + `AlignmentDirectional`, RTL-correct — and pointedly not from `EntityDetailTabs._edgeFade`, which is plain `Positioned` + `Alignment` and is not.

## A `Stack` mounted for a FAB loosens what is under it

**A `Stack` mounted for a FAB loosens what is under it, and that is what left an empty state in the corner.** The narrow Items tab on all five billing-doc edit screens wrapped its `SingleChildScrollView` in a `Stack` for one reason — to hang the picker FAB at `bottom: 16, right: 16` — and a `Stack`'s non-positioned child gets `constraints.loosen()`, so the scroll view shrank to its content and the `Stack` parked it at its default `AlignmentDirectional.topStart`. A populated list hid that completely (its `ReorderableListView` fills the cross axis, which is why every screenshot of a real invoice looked fine), while a draft with no rows collapsed to the width of its two buttons and hugged the top-left of an otherwise empty screen — invoiceninja/flutter#141, asking for it "centered and prominent like on other similar areas". `BillingDocEditItemsBody` (`billing_shared/edit/billing_doc_edit_items_body.dart`) is now the one host for all five. Eight things are load-bearing and every one of them is silent. **`StackFit.expand` is the fix**, not the `Center` it enables — and the `Stack` stays mounted even with no FAB in it, because dropping it on the narrow branch would unmount the scroll view on every resize across the table breakpoint and lose the user's position, where a conditional *child* costs nothing. **Vertical centring is a `ConstrainedBox(minHeight: viewport − gutters)` plus a bare `Center`**: inside a scroll view `maxHeight` is infinite, so `RenderPositionedBox` shrink-wraps to `max(child, minHeight)` — the block lands in the middle of the viewport and a tall one (large text scale, landscape) simply scrolls, with no branch to get wrong. Subtract the padding or every Items tab scrolls by a hair for ever. **`SliverFillRemaining(hasScrollBody: false)` is the idiomatic-looking alternative and is forbidden here**: it calls `getMaxIntrinsicHeight` on its child, and this subtree contains `LineItemEditor`'s `LayoutBuilder`, which throws on an intrinsic query in debug and answers 0 in release. **`minHeight` must be ZERO on the wide-table branch**, which is the one thing here that fails *visibly* and was still nearly shipped: `RenderFlex` ends in `constraints.constrain(...)`, which honours a `minHeight` whatever the `mainAxisSize`, so applied there it stretches `LineItemTableDesktop`'s **bordered** container to the full viewport and leaves a tall empty box under the last row. It is a ternary rather than a conditional widget so the tree shape stays constant across the breakpoint. **The FAB follows the TABLE, not the layout branch.** The narrow tabbed layout runs up to a 1024 px pane while `LineItemEditor` switches to the desktop table at 700 px of *content*, so there is a band — an iPad Pro 12.9 in portrait, any desktop window around 964–1255 px with the rail up — where this tab renders that table, and the table has no inline picker affordance at all (`line_item_table_desktop.dart` says outright that "bulk adds go through the items-section FAB"). Removing the FAB by layout branch would therefore strand the picker exactly where there is no ⌘N to fall back on. It is gated instead on `lineItemEditorShowsWideTable`, a top-level predicate the editor itself calls, so the two cannot drift — and the host subtracts the same gutters the editor's own `LayoutBuilder` sits inside, since one reads the pane and the other the content box (the Tasks filter-bar rule, in its sharpest form: the two reads are not just in different widgets, they are on opposite sides of a `Padding`). The **desktop page** FAB at ≥1024 is deliberately kept. **Both add buttons render in both states.** `Add Items` used to appear only while the list was empty, so on a phone — where the FAB is now gone — the picker became unreachable the moment one row existed; `_AddItemActions` is one widget used by the empty state and the populated footer so they cannot diverge, `Wrap` rather than `Row` (two labelled buttons take a second run at 320 px or past ~1.2× text scale), and each needs `minimumSize: const Size(64, 40)` or `theme.dart`'s `Size.fromHeight(40)` — infinite width — stretches it edge to edge. The populated footer's old borderless `TextButton` is gone with it: it read as a tertiary link beside the outlined pair, which is what invoiceninja/flutter#142 called out. **The labels are `Add Line` and `Add Items`**, not `Add Item` and `Add Items`: they are now permanently adjacent, they do different things (type a one-off row vs. pick an existing Product / Task / Expense), and #142's reporter had already conflated the FAB with the button beside it. `add_line` is an existing translated key. And **`Add Line` opens the editor BEFORE appending** — `showLineItemEditDialog` on `newItemFactory()`, appending only a non-null result — where it used to append a blank row and leave the user to find the resulting "Untitled" card; the dialog takes `titleKey` / `actionKey` so it says *Add* rather than *Save* on a record that does not exist yet, which is what makes its Cancel honest. `test/lint/billing_items_affordance_test.dart` pins the wiring per layout (scoped to the `_ItemsTab` class body, since the other tabs use `Stack` and `SingleChildScrollView` legitimately), and the behaviour is pumped in `billing_doc_edit_items_body_test.dart`, `line_item_card_list_mobile_test.dart` and `line_item_editor_wide_gate_test.dart`.
