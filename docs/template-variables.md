# Email-template variables as chips

Companion to CLAUDE.md § Forms — Template variable fields and § Rich text editing. One topic that used to have two homes: the chips are super_editor inline placeholders, so the field rules and the editor rules belong together. The main file carries one line per rule; this doc carries the evidence.

## Which variables a template supports is a property of the server engine

**Which variables a template supports is a property of the server engine, not of a list.** `HtmlEngine` renders invoice / quote / credit / reminder / recurring emails, `VendorHtmlEngine` purchase orders, `PaymentEmailEngine` payments — but `payment_failed` goes through `HtmlEngine` (plus `$payment_error`), `statement` gets `HtmlEngine` values plus `$start_date` / `$end_date` from `ClientService`, and `custom1-3` go out with any document, so they never warn. `lib/domain/email_template_variables.dart` (imports nothing) holds the scopes, the picker groups and, per catalogued token, the set of engines that define it; "in scope" is computed from that set, never from which group happens to list a token (`HtmlEngine` defines `$vendor.name` although no invoice group offers it). `test/domain/email_template_variables_test.dart` re-extracts the `$data['$…']` keys from the three PHP engines when the server checkout is present and reports **skipped**, never passed, when it isn't — the `totals_parity_test` contract — and asserts every token of every server default template is in scope, which is what caught the statement template's `$start_date`. The reference card that used to sit under these fields listed `$client_address1`, which exists in no engine — it is gone now, along with the rest of the card: every token is a labelled chip in the fields themselves, and "Insert variable" lists them with search and values, so a second copy-to-clipboard catalogue was one more thing to fall out of date. The **View docs** link stays; it covers more than the tokens. A catalogued token the scope's engine lacks warns amber "Not available"; an uncatalogued one stays plain text in Templates & Reminders, which has no way to ask the server.

## A single-line field can't hold chips and be edited as text

**A single-line field can't hold chips and be edited as text,** because a `WidgetSpan` standing in for a 13-character token breaks `EditableText`'s 1:1 text↔layout offset map. So `TemplateVariableFieldShell` has two modes: at rest a `Text.rich` of chips inside an `InputDecorator` built exactly as `TextField` builds its own; tap the text and the owner's untouched `TextField` swaps in (tokens tinted by `TemplateVariableTextController`, offsets 1:1, the IME's composing underline left alone), caret at the tapped character. Three rules. **Blur is focus leaving the whole shell**, not the text field — Tabbing into its own suffix button must not swap the view and unmount the button that just took focus. **The owner wires the supplied tap-outside handler** (`dismissPickerOnTapOutside`): on touch an outside tap never unfocuses a field, and the user would be stuck staring at raw tokens. **Edits made through a chip are programmatic** and don't fire `onChanged`; they arrive through `onEdited`. An inherited value (`interactive: false`) is inert and unfocusable — the `IgnorePointer` in `OverridableField` doesn't stop Tab.

## The default template is shown, never silently saved

**The default template is shown, never silently saved.** Most companies never customise a template, so an empty subject and body are the common case. At company scope both fields render the statics default (muted, with a "Default" badge / caption); chip edits and typing work on a copy, and the value stays `''` until a real edit — text equal to the default writes `''` again, and "Reset to default" writes `''`. That matters beyond tidiness: the server localises an *empty* template per client at send time, and a saved one is fixed text in one language. The statics key isn't always the template id (`staticTemplateKeyFor`: `payment_partial` → `partial_payment`); credit and custom templates have none.

## Values come from the server, exactly, or not at all

**Values come from the server, exactly, or not at all.** `/api/v1/templates` returns rendered text but no variable map; it does, though, substitute a *subject* with plain `strtr` — no markdown, no escaping — leaving unknown tokens literal. So `resolveTemplateVariables` sends a subject of the tokens behind `[[in<nonce>:i]]` markers (no `$` in them, so `strtr` can't match one) with a body of `'.'` (Laravel turns `''` into null and the engine would load the default body), and reads each value back out; an echoed token is "Not recognized". It is a free function over `render`, not a `TemplatesApi` method — four tests `implements` that class — and it **throws when unbound**, because an unbound render substitutes another record's values (#31); the composer only builds a `TemplateVariableValuesController` when `emailPreviewBinding` is bound. One probe on open covers the whole catalog; later only new tokens are asked about; every failure is silent and a permanent one stops probing. Values reach the body's chips too, through `MarkdownTextField(values:)` → `templateVariableChipBuilder(values:)`, and the frame's `Semantics` summary with them — a screen reader hearing "Amount" where the subject beside it says "Amount, £10.00" is a regression against the field's own sibling. One value is dropped: the one that just **repeats its own label**. `$view_button`'s probe answer is the button's caption, which is also its name, so the chip read "View Invoice  View Invoice" — and every server default body ends with that token. The predicate is the duplication and deliberately **not** `isMarkup`, which the probe sets for *any* HTML in the rendered value: `$public_notes`, `$terms` and `$footer` are stored as HTML by this app's own editor, so suppressing on markup blanked their values, and label-only renders identically to "the probe hasn't answered yet". `template_variable_picker.dart` routes its value column through `describeTemplateVariable` too, so a row cannot print what the chip it opens from hides. On a phone the composer also shows the rendered subject under the field, since the preview is a tab away. Both Send Email fields show the server's template muted, behind a "Default" badge — `defaultText:` on the subject's shell, `defaultValue:` on the body's editor — and send `null` while it is untouched, so the server resolves it in the *client's* language rather than receiving a snapshot fixed in the sender's. One caption covers the pair (`showDefaultCaption: false` on the subject), and it is not the settings one: `default_template_caption_send` says the edit applies to this email, where "your first edit saves a custom copy" would read as "editing this rewrites my template for every future send". Scheduling after an edit asks first — the server's scheduler ignores subject/body overrides (BACKEND.md) — and the composer flushes the editor's debounce **before** that check, not merely before the send, or a body typed a moment earlier is silently dropped by the server. `PopScope.canPop` is read during build and cannot flush at all, which is what `MarkdownTextField.onEditing` (synchronous, pre-debounce) exists for.

## A rendered `raw_body` is the request echoed back

**A default is adopted only from a render that asked for it, and never survives a template switch.** `TemplateEngine.php` assigns `raw_subject` / `raw_body` *after* `setTemplates()`, so they are the stored template only while the request posts an empty one — the moment the user types, a render echoes their own text straight back under those keys.

Testing the *current* field is not enough, because `PreviewController` bumps its token only inside `_fire()`: a non-immediate `schedule()` just restarts the debounce, leaving an in-flight request valid, so the response to "Hel" can land after the field has been cleared. That made the user's own deleted draft the muted "Default". `TemplatePreviewLoaded` therefore carries a `TemplatePreviewRequest` (template, `subjectWasEmpty`, `bodyWasEmpty`) and the composer adopts only when it matches — plus the existing emptiness re-check, which still closes the same-template typing window.

**`_onTemplateChanged` clears both caches unconditionally**, edited field or not. An edited field is exactly the case that can never be refreshed (every adopt path needs our own value empty), and a stale cache there is not cosmetic: `_editedSubject` compares against it, so typing the *old* template's wording back read as "unedited" and sent `null` — i.e. the **new** template's subject — while the user watched their own on screen. For an unedited field the same clear avoids the other lie: the first reminder's body under a "Default" badge while the third renders, where a blank box for one render cycle is merely empty.

The rest of the poisoning followed from the same root: Reset restored the edit it had just discarded, and emptying the body reseeded it from the user's text (`_reseedDefault` fires at the editor's 150 ms debounce, well before the 400 ms round trip could un-poison anything).

## A field action is a labelled button outside the field

**"Insert variable" sits above its field, right-aligned; "Reset to default" sits below it, right-aligned; both are `FieldActionButton`.** Neither is a bare glyph inside the input any more. A suffix icon has no tooltip on touch, so it said nothing about what it did; the two of them competed for the one `suffixIcon` slot; and an insert `+` sat on top of the chip row that a long subject runs underneath.

The split by position is the useful part: insert acts on the **caret**, so it belongs with the label at the top, beside the field's name; reset undoes the **whole value**, so it reads as a conclusion under the field, after the default caption that is the sentence it answers. Putting both in the label row invited the wrong one.

`FieldActionButton` (`lib/ui/core/widgets/field_action_button.dart`) exists because the touch-target style is not optional and was copied four times: `VisualDensity.compact` subtracts 8 from `minimumSize` (§ Design system, trap 2), so a 44 written there renders 36, and `MaterialTapTargetSize.padded` — the mobile default — hides that behind a 48 px floor that is not the button.

## A markdown field reports both edges of dirty

**`MarkdownTextField.onEditing` is a `ValueChanged<bool>`, and the false edge is load-bearing.** The true one is synchronous — fired on the first document change, before the debounce — because a host whose dirty answer is read *during build* (`PopScope.canPop`) cannot wait for `onChanged`, and one that reads it before an `await` (the Send Email schedule warning, which is the only thing standing between a just-typed body and the server discarding it) would read a stale one.

The false edge exists because `_emitCurrent` returns early, **without** calling `onChanged`, whenever the document serializes to what it already did. So an edit that round-trips — typing a character and deleting it, or the ordinary "clear the default and change my mind" — emits nothing, and a host latching on the true edge alone stays dirty for ever: a Reset button over an untouched default, a discard prompt on every close, and a schedule warning about edits that do not exist. `_emitNow` and `_flushNow` both retract unconditionally, because once they return the parent holds the current value by construction.

## A late `defaultValue` waits for a pristine document

**A changed `defaultValue` reseeds only when the document is pristine and no editor is mounted over it; otherwise it waits for the blur.** `_defaultSerialized` is computed nowhere but `_seedDocument`, so a default arriving after the first build — statics landing late in settings, and *always* in the Send Email composer, whose default comes from a preview render — needs its own reseed arm or it never renders at all.

That arm cannot key on `_lastEmitted.isEmpty`. The debounce restarts on every keystroke, so "the parent holds nothing" stays true for a whole typing burst: reseeding on it threw away everything the user had just typed, silently and with nothing emitted or logged. `_isPristine` (`_debounce == null && _lastSerialized == (_defaultSerialized ?? '')`) is the real question. It cannot key on `_showingDefault` either — that getter requires a default to have *already* arrived, which is exactly false for the first one.

And it must not fire under a live editor: `_seedDocument` disposes the composer a mounted `SuperEditor` is still holding (the hazard `_restore` and `_onFocusChanged` both defer a frame for), and flipping `_defaultSerialized` off null re-parents the frame, remounting the editor under the caret. A `_pendingDefaultSeed` latch carries it to `_onFocusChanged`'s existing post-frame callback instead. An external *value* change still reseeds at once — that is the parent deliberately overwriting, and it predates this.

## Template variables are inline placeholders the markdown never sees

**Template variables are inline placeholders the markdown never sees.** With `templateVariables:` set (the Templates & Reminders body — invoiceninja/flutter#139), a recognised `$token` is a super_editor inline placeholder (`TemplateVariablePlaceholder`, one atomic character to the caret, selection and backspace) rendered as a chip through `Stylesheet.inlineWidgetBuilders` (`markdown_template_variables.dart`). The pinned serializer has no placeholder hook — a placeholder serializes as a literal U+FFFC — so chips are created *after* deserializing (`tokenizeTemplateVariables`) and turned back into their tokens before **every** serialize (`_serialize()`, the only serialize call in the file). Five things are load-bearing. **The round trip must be byte-identical**, or an untouched field emits a spurious change: attribution markers are remapped through an offset map rather than stitched, and `markdown_template_variables_test.dart` pins a corpus that includes the server's default bodies after `markdownFromLegacyHtml`. **Only a uniformly formatted token becomes a chip**: the server substitutes *before* it parses markdown, so `**$client**.name` is `$client` plus a literal `.name` — a chip there would change what the email says; inline code and tables stay raw too. **The chip builder must claim every placeholder of its type**, known or not — super_editor adds nothing to the span for an unclaimed one and the layout's offsets then drift from the document's. **Taps never reach a chip widget**: inline widgets sit under an `IgnorePointer`, so the editor routes them through a `ContentTapDelegate` (built fresh per `Editor` — SuperEditor disposes delegates when its editor changes) and the tap-to-edit reader, itself under `SliverIgnorePointer`, hit-tests the host's tap against `SuperReader(documentLayoutKey:)`; for the same reason body chips have no hover, no ripple and no semantics of their own (the frame carries a `Semantics` value summarising them). **Reactions order**: every reaction's `react` gets the same change list and a request issued in `react` runs at once, so the typed-token conversion reaction is appended **last** (`installTemplateVariableReactions`) — shrinking the text before `LinkifyReaction` ran would leave it on stale offsets. Opening the picker is a route, which blurs the editor and clears its selection, so the target is captured first and the caret restored after. Copy/paste of a chip drops it (super_editor copies a placeholder as U+FFFC, which serialize discards) — accepted. `defaultValue:` renders the server's default template when the value is empty and emits nothing until a real edit; a document edited back to exactly the default emits `''`, and one emptied outright shows the default again — at once at rest, and on blur while editing, from a **post-frame** callback: SuperEditor's own blur handler runs after ours and executes a `ClearSelectionRequest` against the composer a reseed would already have disposed. The caption under it sits in a wrapper that stays mounted for as long as a default exists — wrapping on the showing-default flag itself re-parented the frame at the first keystroke into the default and remounted the live editor under the caret, which `markdown_text_field_template_variables_test.dart` catches by asserting the `SuperEditor` state survives. A super_editor bump must re-run `markdown_template_variables_test.dart`. Logged in `docs/upstream-workarounds.md` § 9.

## Every markdown field guards `$variables` from linkify

**Every markdown field guards `$variables` from linkify.** super_editor's `LinkifyReaction` matches loose URLs over the whole space-delimited word, so typing `Dear $client.name, ` (`.name`, `.city`, `.date` are TLD-shaped) produced `[$client.name,](https://$client.name,)` — and the server, which also substitutes variables in terms, notes and footers (`PdfBuilder.php`), then replaced the token in both halves and rendered broken link markup. `TemplateVariableLinkScrubReaction` runs directly after `LinkifyReaction` on every `MarkdownTextField` and removes a link whose URL is `https://` + its own text when that text holds a variable; `healTemplateVariableLinks` applies the same predicate on seed, *before* the baseline, so content saved while the bug was live is cleaned on the next real edit without a spurious emit. A real URL still links. `docs/upstream-workarounds.md` § 10.
