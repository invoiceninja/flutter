# The list search field

Companion to CLAUDE.md § List state filter. That section owns what the lifecycle filter may *hold*; this doc owns the box that edits every filter — `TokenSearchField` and its popup (`lib/ui/core/list/search/`): where the popup lands, what a key press does, what Enter is allowed to commit, and why the list header grows around it. CLAUDE.md is at its size cap, so these rules are indexed from `docs/README.md` rather than from a bullet there.

Everything below shipped broken first and was found by reading, because **nothing pumped the wide field** — `token_search_field_test.dart` covered the parser and the chip and said so. `test/ui/core/list/search/_token_search_harness.dart` is the harness that now does; § Testing the field says what it has to get right.

## The popup is placed in the layout pass, from the input

**The suggestion menu is positioned by `OverlayPortal.overlayChildLayoutBuilder`, and the portal wraps the *input*, not the whole box.** The report was "the popup often appears too far over", and it was four bugs with one root. The menu was positioned inside a plain `overlayChildBuilder`, which runs in the **build** phase, from `RenderBox.localToGlobal` and `RenderEditable.getLocalRectForCaret` — i.e. from the *previous* frame's layout. Measured against that code with the harness, on a 700 px box:

| Flow | Menu left edge | Should be |
|---|---|---|
| Re-open on existing text (`acme corporation`, click at its end) | 550 | 287.5 |
| Edit a chip (`name:acme` written in the same frame) | 715 | 569 |
| Backspace away a chip with the menu open | 639 | 457.5 |

The first is an anchor bug (it hung from the **caret**, so a text-width right of the token), the second is the stale frame, the third is an anchor captured once and never refreshed.

`overlayChildLayoutBuilder` runs its builder during **layout**, with the portal child's rect already in the hosting Overlay's coordinates (`info.childPaintTransform`). That also deletes the hand conversion from global coordinates that existed because the list's Overlay starts at the sidebar's width, not at 0. Two things are load-bearing. **The portal must wrap the thing being measured.** The SDK guarantees the child's own rect and every ancestor's are final when the callback runs; it does not promise the child's interior. The search box is an ancestor of the input, so reading it alongside is safe — reading the input from a portal around the *box* is not. **The callback does geometry only.** No `setState`, no `OverlayPortalController.show()/hide()` (both assert there), no notifier writes; the cached anchor fields are plain assignments. The menu subtree is built once per `_buildWide` and handed in, so a re-run caused by the box moving (a resize, a page scrolling under an embedded list) repositions it without rebuilding it. The portal carries a `GlobalKey` because it is a child of a `Wrap` whose earlier children — the chips — come and go; without one its State, and the open menu, would be torn down on every chip.

The comment this replaced said `CompositedTransformFollower` had been rejected because it broke `TapRegion` hit-testing. `TapRegion` decides inside/outside from the hit-test path and never calls `globalToLocal`; a `Positioned` in the layout builder gives the menu a real offset, which is all it needs.

## The placement rule is one pure function

**`placeFilterMenu` (`filter_menu_placement.dart`) is the whole rule, with no widgets in it.** The menu's row *content* starts at the anchor (so the painted edge is `kMenuRowInsetLeft` before it); it never leaves the search box horizontally when the box is at least as wide as the menu, and falls back to the Overlay's extent when it is not; RTL mirrors, hanging the menu's *end* from the token start; height is capped to the room above the soft keyboard. It flips above the anchor only when below has room for fewer than about three rows and above has more — and the side is **latched for as long as the menu is open**, or a rising keyboard flips it mid-aim. The keyboard overlap is measured against the Overlay's own bottom edge in global coordinates, not read off `MediaQuery.viewInsets` at the field: a `Scaffold` between the two may or may not have consumed the inset, and only the ones *above* the Overlay shrank it. The per-chip segment popups use the same function with `containInField: false`; they used to clamp on the left only.

## The anchor holds while a multi-select list is being ticked

**x is re-captured when the menu opens and when the applied chips change, and held while a `checkboxMultiSelect` list is open.** Typing never moves the start of the token, so there is nothing to chase — but ticking a row widens that key's chip, which pushes the input right, and a menu that followed would slide out from under the pointer mid-click. y is held too from a tick made by tap or click until the next key press (`_pointerTicking`) and follows the box otherwise. That flag is set where the tick is handled, which knows what made it — not read off `FilterSuggestionController.movedByKeyboard`, which is true for every fresh list until a mouse *moves* and so reads "keyboard" for every touch tap. The chip anchor (a pinned picker opened from a chip) is cleared whenever the pin clears; it used to outlive it and leave the filter list under the old chip.

## Focused text is the search, and a matched key is not

**One predicate decides "the user is building a filter": `TokenSearchController.parseInput().matchedKey != null`.** It is pin-aware, and it replaced `text.contains(':')`, which was wrong in both directions: `INV:001` contains a colon and is a search, while text typed into a pinned Status picker contains none and is not — it used to live-search the list behind the picker, and stayed applied after a tick and a click away. Three more consequences. **Emptying the box clears the search**; the live commit used to be gated on non-empty text, so backspacing a term away left the list filtered by its last letter. **`setSearch` cancels its debounce before its no-op return** (and `clearAllFilters`, a restored snapshot and a deep link cancel it too): typing `status:` at normal speed left `statu` armed, and it fired a quarter-second later under the open value list. And **a click that starts a filter decides about the search explicitly** (`TokenSearchController._setAsideBoxText`) rather than through the text listener — on desktop a text field unfocuses on any mouse press outside itself, a menu row included, and the listener only writes the search for a focused field. (A test sees that only with `tester.tap(…, kind: PointerDeviceKind.mouse)`: `tester.tap` is a touch, and a touch never unfocuses.) Since the search chip that decision is no longer always "clear" — § The search is box text until the box is needed. Every write of `vm.search` from the field goes through `writeSearch`, so `syncExternalSearch` can tell the field's own writes from everyone else's.

**A typed prefix resolves only to a key the picker would offer** (`typeableKeys`: available and not locked). `client:` typed on a client's own Invoices tab used to add a second client beside the parent scope and empty the list; a hidden custom column applied a filter with no chip.

## Enter commits a row only if the rows are for this text

**Published rows carry a stamp of the input they were built for, and `commit(expecting:)` refuses a mismatch.** Rows are published in a post-frame callback, so for one frame they belong to the previous text. A barcode scanner, or a paste followed at once by Enter, lands the key in that frame: Enter ran "Search for acm" under a box reading `acme`. On a mismatch the typed path commits what is actually in the box.

The stamp guards the *input*; a second guard covers the *data*. When the query changes, the value list's stream is swapped, and `StreamBuilder` keeps handing its builder the previous stream's rows until the new one emits — a frame for an in-memory list, as long as the query takes for a Drift-backed one. Those rows stay on screen (blanking the list per keystroke would flicker) but each emission is tagged with the key and query it answers (`_Suggestions`), and rows for an earlier query are published under a stamp that matches nothing: typing `zeta` into a Client list and pressing Enter before the new list arrived used to apply the first client of the old one. Rows left over from a different *key* are not shown at all. And a list whose typed value is not a value yet publishes **no** rows — an action that runs and does nothing still counts as "committed".

The typed path is one method for both hosts, `TokenSearchController.commitTyped`. The phone sheet had none, so `name:acme` + Search there searched for the literal text `name:acme`. The same goes for what a pick *means*: `pickKey`, `editChip`, `pickOp`, `dropBoxText` and the chip keys (`handleChipKeys`) live on the controller. The field and the sheet each carried a copy and drifted three times — custom fields pinned in one, `directApplyValue` honoured in one, the typed text dropped in one — so the hosts now keep only what is theirs: anchors, the overlay, navigation.

## A pick-only key never takes typed text

**`FilterKey.acceptsTypedValue` is false for every key whose values are ids or enum names.** `client:acme` + Enter with no matching row — or Enter that beat the list's first emission — used to apply `client_id=acme`: a chip reading `client acme` over an empty list. Now the input and the menu stay. Every key now opens through the pin (§ Every key opens through the pin); `opensViaPin` is left deciding only where a chip's editor hangs — under the chip for a pick-only key or a custom field, whose picker has no text, and from the input for a typed key, whose value is written into the box to edit. One predicate for wide and sheet; they had each carried a copy and drifted.

## A typed value goes through the key's normalizer

**`FilterKey.normalizeTypedValue` returns the canonical wire value or null to refuse.** Three bugs lived in the gap. `balance:<500` + Enter committed `> 500`, because the operator rows always pre-selected row 0 — they now pre-select the comparator that was typed (it is part of the row keys, so typing one re-keys the list). `balance:abc` was accepted and sent as `gt:abc`; amounts now follow `parseDecimal`'s separator rule under the company's decimal convention, but parsed *strictly* — `parseDecimal` answers zero for what it cannot read (it is built for form fields, where blank is zero), so `1.2.3` would have become `> 0`. And a typed date could not be committed at all: Enter picked the comparator row, then the "back" row, in a loop. A date that `DateColumnFilterKey.parseTypedDate` accepts now shows one-step rows that read the way the chip will (`is on or after 14 May 2026`). The pre-selected row is the comparator typed in front of the date, else the one picked from the list before typing, else the key's default — and the picked one is held in `_ValueListState`, because typing swaps the preset widget for the typed-date widget and a choice kept in the swapped-out State went with it (pick "is before", type the date, Enter applied "is on or after"). Text that is not a date says so and gives Enter nothing to commit; it used to walk the highlight through a comparator and then "1 hour ago".

**A pasted value passes the same gate** (`applyPastedQuery`, the clipboard-free half of `handlePaste`). It used to go straight to `addValue`, so pasting `client:acme balance:abc` applied both. A typed-value key normalizes it; a pick-only key takes it only when it names one of the key's own values exactly, resolved through the synchronous `quickValueSuggestions` (`is:archived`, `status:paid`). Whatever is refused stays in the box as text.

`parseTypedDate` deliberately accepts less than `parseDateInput`. That function also reads `20`, `+1` and `0514` as dates — right for a date field committed on blur, wrong halfway through typing `2026-05-14`, where Enter would commit "the 20th". Here a date needs a digit either side of a separator, or a word. `today` and `yesterday` become rolling `rel:d0` / `rel:d1` tokens so a saved view keeps meaning "today" — on a window-only key too, since a window's bounds resolve wherever it is read (§ A rolling date is one token per bound); it used to freeze to the date typed. `May 14, 2026` contains a comma and is a single date, so a single date is tried **before** the comma is read as a window.

## A chip's body edits, and only ✕ removes

**Tapping a chip never removes its value.** For a multi-value key the tap used to remove the value first and then open the picker, so Escape or a click away deleted the filter — against the chip's own contract (`docs/pane-width-and-overflow.md`). The value now stays applied: the controller remembers the chip being edited (`beginEdit`), and a pick swaps it through `FilterKey.replaceValue`, one write for the set-backed keys. A multi-select or custom-field chip opens its list with the applied values ticked instead.

Two presentation rules ride along. **The label keeps its case** — it was lowercased for a `key:value` look, which gives `kunde` and `ust-idnr.` in German and mangles a company's own custom-field label. **An aggregate chip names two values and counts the rest** (`Status Draft, Paid +1`, full list in the tooltip): three labels in one chip is what pushed the input onto a second line.

## Multi-select rows toggle, and "Only" replaces

**The whole row ticks or unticks and the menu stays open; a trailing "Only" picks one value and closes.** The row used to be split invisibly — the 20 px checkbox added, the label replaced the selection and closed — so clicking "Paid" with Draft and Sent ticked silently dropped both, and a near-miss on the checkbox wiped the selection. "Only" shows on the highlighted row, and on every row on touch, where there is no hover to reveal it. After a tick made with Enter the typed query is cleared so the full list is back for the next one; a tap or click leaves it, so the list does not reshuffle under the finger working down it. Which it was is asked of the commit (`FilterSuggestionController.committingByKeyboard`, true only while `commit()` runs a row).

## The first view leads with the suggested filters

**With nothing typed the picker shows `Suggested` — the keys marked `FilterKey.isPrimary` — and then `All filters`, A→Z.** It used to be one flat A→Z list with no hints: on Clients, State — the filter the placeholder advertises — was row 12 of 15, and eight rows fit. Primary is a flag on the key (State, the per-entity Status, Client, the document's `date`, a client's Name), not "the first N in registry order": that order also drives chip order and the cross-key value matches, and it is not a ranking — Invoices registers Tags before Status. The headers appear only when both groups have rows, so a settings list with State alone stays a bare row. While typing, keys whose label, id or alias *starts* with the query lead the ones that merely contain it (`rankFilterKeys`); a flat A→Z of every substring match put `Custom…` ahead of `State` for someone typing `st`.

On a pointer platform each row also shows what to type to reach it without the menu (`status:`), and a footer shows the keys — the command palette's caps and words. Neither on touch, and no type-hint for a custom field, whose id is exactly what its configured label exists to hide. The value list's header is a "‹" back to the picker: the only way back that needs no hardware key, since a soft keyboard sends no event for Backspace on an empty input. A list still waiting on its first emission says "Loading" rather than "No matches", and an idle list cut to `FilterKey.idleSuggestionCap` says so in a trailing row.

## The keyboard: Escape in two stages, Tab accepts, Backspace arms

- **Escape** lets go of an armed chip first, closes the menu second and leaves the box third. One press used to close and leave at once, so every filter built from the keyboard cost another `/`. Android back still does both at once: back cancels.
- **Tab** accepts the highlighted row when something is typed; otherwise, and for Shift+Tab, it closes the menu and lets focus move on. The menu's visibility is deliberately not tied to focus, so a Tab that simply moved on left it open with nothing able to close it. "Accepts" means something was actually committed: a typed value the key refuses keeps the input for Enter, but a Tab that did the same was swallowed on every press, so a refusal closes the menu and lets Tab through (`_Commit`).
- **↓** opens a closed menu. `/` focuses the box without opening anything.
- **Backspace** in an empty box arms the last chip (accent border); a second press removes it — the whole *chip*, so an aggregate `Status Draft, Paid +1` goes in one, not one value at a time under a highlight that said the chip would. A key *repeat* never reaches a chip — that is someone holding the key to clear their text. With a filter being built, Backspace first goes back to the filter list.
- **← / →** walk the chips — § A chip is armed, never focused.
- **Arrow keys repeat.** A held ↓ used to fall through to the text field and walk the caret.
- A mouse click on a multi-select row refocuses the input; the click had unfocused it and left the open menu with no keyboard at all.

## Hover moves the highlight only when the pointer moves

**Rows listen to `MouseRegion.onHover`, not `onEnter`.** `onEnter` also fires when a row *appears* under a pointer that is not moving — the menu opening beneath a cursor parked below the box. That row took the highlight and Enter committed it instead of "Search for …". A keyboard move scrolls its row into view (through the nearest scrollable only — an embedded list's field sits inside the record page's own scroll view); a far jump in a lazily-built list is scrolled from the index by `_MenuScroll`.

## The header grows because `preferredSize` is a ceiling

**`EntityListAppBar` shrink-wraps, and `preferredSize` is how tall it *may* get.** `Scaffold` wraps its app bar in `ConstrainedBox(maxHeight: preferredSize + inset)` and places the body under the height the bar actually reports, in the same layout pass; Material's `AppBar` only ever looked fixed because it expands to fill that ceiling. So nothing is measured and no frame lags. The header used to be an `AppBar` with a fixed `toolbarHeight`, which gave the search row 45 px however many chips it held. Measured before the change: on desktop a wrapped input sat at y 47–79 in a 69 px bar — painted over the first rows of the table and, being outside the bar, not clickable — and on a touch platform a *single* chip (17–67, its ✕ padded to 40 px square) already overran its box.

Both header modes are one widget with both halves mounted (`IndexedStack`, which sizes to the taller child). That is what keeps the row under the pointer still when it is ticked: the selection chrome is as tall as the normal chrome it covers, wrapped chips included, by construction rather than by two classes agreeing on a number. The hidden half is excluded from focus, pointers and semantics. Past the ceiling (`maxExtentFor`: under half the available height) the box scrolls its chips instead of clamping; that scroll view is `hitTestBehavior: deferToChild` with the scrollbar off, because either would swallow clicks on the blank part of the box. For the ceiling to be reached at all the box needs a *bounded* height: in the narrow header the search row is a `Flexible` child of the header's `Column` (a non-flex child is laid out unbounded, and overflowed the bar instead of scrolling), aligned with `Align(heightFactor: 1)` rather than `Container(alignment:)`, which under a bounded height expands to fill it.

## One line is `InSizes.headerRow` on every platform

**The search box floors to `InSizes.headerRow` (the band less its padding), and everything beside it sits in a `HeaderRowSlot` of that height.** The row is top-aligned, so without the slots the "New" button slid down the header each time a chip wrapped. Three sizing traps, all on touch, all hidden until the fixed-height bar stopped clamping them: the theme pads an icon button's *layout* box to 48 px; the input was 40 px (a pointer platform's compact density takes 8 off the decorator, touch does not); and a chip's ✕ was 40 px square. Inside the box they now take their height from the line and keep a finger's width — the axis `docs/touch-targets.md` reclaims. `FilterTokenChip(compact:)` is that switch; the phone sheet has the room and leaves it off. The focus ring thickens by shadow, not border width: a wider border grew the box by a pixel on every focus, which a header that sizes to the box would pass to the whole list.

`searchWide` is `(wide || globalNav) && !Breakpoints.isPhone`: a landscape phone clears the 600 px test and has about 190 px above its keyboard, so it gets the summary row and the full-screen sheet like a portrait one.

## Testing the field

**Assert on global rects, in a host with a second Overlay.** The shell hosts a list in a branch Navigator whose Overlay starts 232 px in; a test that hosts the field in the root Overlay cannot see a lost origin. The harness reproduces that, uses a real view model (the bugs are in how the field and the VM talk), and never calls `pumpAndSettle` — an open popup re-lays-out every frame. Every test ends with a pump long enough for the VM's debounced `nav_state` write, which is a Timer. Seed filters *after* the first pump. And `flutter test` defaults to Android: pin `TargetPlatformVariant` or the key hints, the 40 px rows and hover are all absent. Three more: a click that should take focus off the input must be `kind: PointerDeviceKind.mouse`; a paste reads the clipboard through `TokenSearchController.readClipboard` — `pumpWideField(readClipboard:)`, `FilterEntrySheet(readClipboard:)` — because awaiting `Clipboard.getData` hangs a widget test at 0% CPU; and the menu's lists are lazy, so a row below the fold of a 320 px menu is not built and no finder can see it.

## The search is box text until the box is needed

**The box owns the search; it is set aside as a chip only when a filter is started and the text did not find that filter.** A search and a filter could not be combined at all: `acme`, then State, dropped `acme` — `pickKey` cleared the box and the search with it. The view model is untouched; this is all how the controller shows `vm.search`.

| The box holds | The search shows as | Typing in the box |
|---|---|---|
| the search (default, and on every mount) | box text | the live search — every rule above |
| a filter being built, or a candidate | a `Search for "acme"` chip, last, beside the input | a candidate: not applied live |

- **Lift or drop** (`_setAsideBoxText`). Text that the key list was ranked by and that names the key picked (`keyMatchesQuery`, the predicate `rankFilterKeys` ranks with) was only how the key was found — `sta` for State — and is dropped, as is text that picked a value directly (`act` → Status Active). Any other text is lifted: applied at once (`immediate: true`) and shown as the chip.
- **Settled.** A menu opened on a box whose text is the applied search, untouched since (`searchSettled`), is not ranked by it: it shows its "Search for" row over the ordinary first view (`FilterSuggestionMenu.rankByQuery`). Ranked by `acme`, the list offered no filter at all. It is also how a search that happens to name a filter is kept: Enter on `stat`, re-open, pick Status. The edit that unsettles it is a *text* change — the caret placed by the click that opens the menu notifies the text listener too, and used to open it as if typed into (`_showOverlay(byTyping:)`).
- **Candidate.** Beside the chip, typed text is not applied; Enter, Tab or the "Search for" row commits it, and it replaces the search and gives the box back. A tap away leaves it unapplied: committing would replace the search the chip shows with text that may have been abandoned. Text spent finding a key or a value beside the chip is dropped, and the chip stays.
- **The chip.** Its body puts the term back in the box, ahead of any candidate, where it is the search again (`unfoldSearch`); ✕ or Backspace removes only the search, and any candidate becomes it (`removeSearchChip`). The phone summary is unchanged: its `+N` already counted the search.
- **A change from outside** (`syncExternalSearch`) — a restored `nav_state`, a saved view, a deep link, Clear filters — puts the box back as on a mount: no chip, no pin, the search as box text. An empty search ends a chip whatever the focus; a chip standing for nothing would make the next typing a candidate that never applies.

## Every key opens through the pin, and the key being built is a chip

**No `<id>:` is ever written into the box.** Picking Balance used to write `balance:` — the raw English id in every locale, and `custom1:` for a field the company named. Every key now opens its value list through the pin, and the key shows as a `PendingKeyChip` in front of the text: `[Balance] <500`. It sits inside the input's `OverlayPortal` child, so the menu still hangs from the start of the token. It has no ✕ — nothing is applied yet — and its tap, like the value header's "‹" and Backspace in the empty box, goes back to the filter list. It is not shown while a picker hangs under the chip it is editing (`pinnedFromChip`), where it would say the same thing twice.

A typed prefix becomes the same pin the moment its colon lands (`adoptTypedPrefix`): `balance:` turns into the Balance chip over an empty box, keeping the caret's place in the value, and `status:pa` typed under a pinned Name hands the box to Status. Never while an input method is composing — Japanese and Chinese are bundled, and rewriting text under an open composition breaks it. Only a colon after a key's id or alias counts: `Net:30` under a custom field is its value.

**Words in front of the key are the search** (`_trailingKey`): `acme status:` lifts `acme` into the search chip, beside any search chip already there, and pins Status. The whole `acme status` used to be read as a key name. It matched nothing, so the box live-searched the literal `acme status:`. The longest run of trailing words is tried first, joined as an id spells it (`due_date`) and with its space. Otherwise `acme due date:` would pin Date and lift "due". Not while a key is pinned: the box then holds that key's value, and `north status` typed under a custom field is a value with a space in it.

When the menu closes, a half-typed value for a key that takes one (`[Name] ac`) stays with its pin, as `name:ac` always did; a pick-only key's query and a multi-select's leftover are debris, as before.

## A chip is armed, never focused

**← at the very start of the box arms the last chip; ← / → walk the row and → past the end returns to the text; Delete or Backspace removes the armed chip, Enter or Space opens its editor, Escape lets go.** Real focus stays in the text field throughout. The moment it left, the list's bare keys came back on — `N` makes a record, ↑ / ↓ move the list selection, `G` arms the leader — because they stand down only while a text input has focus (`isTextInputFocused`). So the highlight is a value on the controller, like the menu's, and the keys reach it through the field's own `Focus` (`handleChipKeys`, called first by both hosts).

- **Which chip** is a `BoxChip.id` — key and value, or key alone for an aggregate — because `boxChips` builds fresh chips on every read and the row changes under the highlight. An id no longer in the row reads as nothing armed.
- **Disarmed on a text change only.** The controller notifies for a caret moved or a selection made too, and the field used to disarm on every notification.
- **← enters only when it has nothing else to do:** a collapsed caret at offset 0, no modifier (Shift+← selects; Alt+← and ⌘+← move by word and line), no composition, no filter being built. In right-to-left text the chips sit to the right, so it is →.
- A screen reader is told the armed chip (`Semantics(selected:)` and an announcement), since focus does not move; the box scrolls it into view when the header is at its ceiling.

## Paste reads what it understands, where the caret is

**⌘V (Ctrl+V and Shift+Insert elsewhere) and the context menu's Paste are one path, `TokenSearchController.paste`.** Only the right-click Paste understood a query; a keyboard paste dropped `status:paid client:acme` in raw, which became one Status query that matched nothing. The keyboard paste is a `TokenSearchPasteAction` in an `Actions` directly around the `TextField` — `EditableText` makes its paste overridable and looks the override up from there. It is always enabled (the default is disabled until the platform has reported pasteable text) and never hands back to the default, which would read the clipboard a second time. The phone sheet keeps the platform's own text menu and routes only its Paste here (`contextMenuBuilder` swapping that one `ContextMenuButtonItem`'s action): on a phone the long-press Paste is the only paste there is, and it used to drop a query in raw.

What a paste understands goes through the typed gate, as before (`applyPastedQuery`). What it does not now lands where the caret is, the way any paste does: it joins the search already in the box (`acme` + `is:archived corp` searches `acme corp`), replaces a selection, or joins the candidate beside a search chip — it used to replace the whole box. A refused filter is left to finish — its key pinned and its value, as pasted, in the box, the shape picking the key and typing gives — with the paste's free text and any search the box owned set aside as the search chip. It used to be written into the box as text, where the typed-prefix rule made everything after its colon its value: `balance:bogus acme` was Balance `bogus acme`, and the search was lost. Only one filter can be built at a time; any further refused ones are named in a toast (`filters_not_applied`). Text with no filter in it — `INV:001` included — pastes as text.

On the web neither path runs: ⌘/Ctrl+V and the context menu are the browser's (`DoNothingAndStopPropagationTextIntent`), and the text arrives as typing would — where a typed `status:` still becomes its chip.

## The lexer keeps quoted and typed values whole

**Whitespace inside double quotes does not split, and commas split only an unquoted value of a pick-only key** (`lexFilterInput`). `country:"United States"` used to lex as `"United` plus a search for `States"`. A key that takes typed text reads its own commas — a date window (`date:2026-01-01,2026-02-01`), a date with one in it (`date:"May 14, 2026"`), a decimal comma (`balance:1,5`) — and splitting before the value reached the key made a window two dates, the second overwriting the first. A quote with no partner is an ordinary character.

## A rolling date is one token per bound

**This month is the window `date,rel:m0s,rel:m0e`** — a `RelativeDateToken` in each bound of the ordinary three-part wire (`lib/data/models/value/relative_date_token.dart`). The grammar adds `rel:<w|m|q|y><K><s|e>[p]` to `rel:hN` / `rel:dN`: the first or last day of the week, month, quarter or year K periods back (`-1` ahead), with `p` the week's first day or the fiscal year's first month, captured when the chip is written and left out for the default.

- **Per bound, not per window**, so the map-wide rewrite resolves it on the wire unchanged and every parser that reads a window's last two parts still works; one period token for both bounds would be read by those parsers as a two-part legacy window.
- **Captured, not live**: resolution is a pure function of the token, so the device and the server read the same dates, and nothing reloads when the company arrives. The price is that a chip made before the company changed its fiscal year keeps the old one until it is picked again; the tooltip shows the real dates.
- **Resolved wherever a window is read** — on the wire (`resolveRelativeFilterTokens`) and in every local parser (`_parseWindowFilter`), which used to compare the date column against the text `rel:…`. A token this build cannot read gives no filter on either side: dropped from the wire, no local predicate. A token is recognised only where one can stand — the whole value, after an operator, or a window bound (`RelativeDateToken.inValue`); unanchored, `Laurel:north` in a name or custom-field filter read as one, and the filter was dropped from the fetch.
- **Day arithmetic is date arithmetic** (`Date.addDays`): `DateTime.subtract(Duration(days: 7))` from 00:30 the night after the clocks went forward landed a day early. `rel:hN` resolves to a UTC instant with its `Z` — the server reads a time with no offset as UTC, so a local wall time was off by the device's offset.
- **The menu offers the current periods first** (`DateColumnFilterKey.windowPresets`), then the last ones, then "Custom range": the menu shows about four rows before it scrolls, and paired as `This week, Last week, This month …` This month was below the fold. A due date (`lookAhead`) offers the next week and month instead of the last ones; only a column with a time of day (`hasTime`) offers "1 hour ago" — on a date column that matched nothing all day.
- **The chip reads `Date · is · This month`**, its dates one hover away. Switching its comparator to a single date seeds the *resolved* first day, or "on or after the first of this month" would move every month under a chip that names a date.
- **The range picker's presets roll too** (`pickDateRangeWindow` → `DateWindowPick`): "This month" used to come back as the dates it covered on the day it was picked, and "All time" as a fifty-year window; it now clears the filter.

## A period can be typed, and is matched as it is typed

**`date:this month` is the This month window, and `date:th` lists the periods it starts** (`DateColumnFilterKey.typedPresetMatches`, the menu's `_TypedPeriodRows`). Every keystroke of `this month` used to read "Not a date yet". A typed date still comes first: `today`, `yesterday` and anything `parseTypedDate` reads keep their comparator rows.

- **What matches.** A period's name starting with the text (`this mo`), or for one word any word of it (`month` → This, Last and Next month). Both the active language's name and the English one count. A typed comparator (`>=th`) matches nothing: a period has none.
- **Under a comparator already picked, the period is its bound.** "Is before" + `this month` is `lt:rel:m0s` (before the 1st), "is after" is `gt:rel:m0e`, the inclusive pair take the same bounds inclusively, and "is on" is the window. Committing the window instead silently dropped the comparator the user had just chosen.
- **Every period, not only the key's menu.** A due date's menu offers Next month, but someone who types "last month" there means it. The key's own presets lead, in menu order. Each row shows the dates it covers today.
- **By full name with no menu** (`typedPreset`, from `normalizeTypedValue`): Enter in the phone sheet and a pasted `date:"last quarter"` commit the same rolling window. The lexer still splits an unquoted `date:this month` on the space, since it reads no key's grammar, so a paste needs the quotes.

## A record key asks the server for every query

**`client:`, `vendor:` and `project:` show the local cache's matches at once and add the rows the server finds for the same text when it answers** (`namesWithServerSearch`, `server_name_suggestions.dart`). The cache holds only the pages someone has browsed. On a large account, `client:acme` answered "No values match" for a client that exists. Asking the server *only* when the cache had nothing was the first fix, and it left one cached "Acme Ltd" hiding every uncached "Acme Corp". So every settled query is asked.

- **Only an empty first answer is held back**, until the server replies. The menu shows its loading row until a stream emits for the current query, so emitting the cache's `[]` first would flash "No values match" in front of a hit. Cached matches never wait. A failed fetch (offline) ends where the cache did.
- **The server's hits are the rows its search matched**, not the rows whose name contains the text. `?filter=` also matches a number and a contact's name, email and phone. They are re-read through the repository's local search (`watchPage(search:)`), which mirrors that field set, and shown from the key's own names stream, so they keep its fallback, order and active-only rule.
- **Debounced 280 ms and dropped with the query.** The menu resubscribes on every keystroke; cancelling cancels the pending fetch, so a fast typist sends one request and an older reply cannot paint over a newer query.

The bundled lists (tags, groups, statuses, categories, languages) are always fully cached and keep the plain local filter. Pinned by `test/ui/core/list/search/server_name_suggestions_test.dart` and `client_filter_key_test.dart`.
