# DocuNinja

Companion to CLAUDE.md § Strict rules. DocuNinja is Invoice Ninja's e-signature add-on: documents sent for signature, templates, and the signing of invoices, quotes and purchase orders in the client portal. This doc covers what the app reads from it, how it is gated, and the contract the app relies on. The work ships in phases, and each section below says what has shipped.

**Read React at its upstream ref.** The reference client is React (`invoiceninja/ui`); read it with `git -C ~/Code/react show origin/HEAD:<path>`. The local checkout has lagged hundreds of commits behind, and the DocuNinja screens changed in that gap.

## DocuNinja is a separate service, and the server only stores what it reports

DocuNinja runs on its own host (`https://api.docuninja.co`; `docuninja.co` is the marketing site). The Invoice Ninja server does not proxy its API. A private hosted package hands each IN user a DocuNinja token (`POST /api/docuninja/login`), provisions accounts, users and seats, embeds DocuNinja signing in the client portal, and writes the results back onto the entity.

What the app reads from the IN API (Phase 0, shipped):

| Field | Where | Meaning |
|---|---|---|
| `company.enable_modules` | `Company.enableModules`, Drift `companies.enable_modules` (schema v20) | DocuNinja is on for the company. Server `Company::docuninjaActive()` = hosted (or local) && this flag && the invoice-settings plan feature. **Not** the `enabled_modules` bitmask. Set by the hosted service and not fillable, so it is read-only: `CompanyApi` excludes it from `toJson`. |
| `account.docuninja_num_users` | `AuthSession.docuninjaNumUsers` (via `accounts.features_json`, no migration) | DocuNinja seats bought. Nothing reads it yet: it does not decide access (see the session table below), and the plan screen (Phase 5) will show it. |
| `sync` on invoices, quotes, POs | `Invoice.sync`, `Quote.sync`, `PurchaseOrder.sync` | `dn_completed` (every signer has signed), `dn_document_hashed_id`, `invitations[{invitation_key, dn_id, dn_invitation_id, dn_sig}]`. Read-only: kept in the stored row, never sent (`_domainToCompanion` spreads it over `toApiJson`, as for invoices). Credits carry a `sync` too, but no portal flow signs them. |
| `can_sign` on contacts and invitations | `Contact.canSign`, `VendorContact.canSign`, `Invitation.canSign` (tri-state) | Which contacts the portal asks to sign. Set per invitation by "Authorized to sign" under each invited contact on an invoice, quote, credit, recurring invoice or purchase order. The contact's own value (client and vendor forms) is what a new invitation starts with. Both show only while `enable_modules`. The save rules are in `docs/contacts-and-invitations.md` § A save sends an invitation's key only with its can_sign. |

## A signed document is marked beside its status, and the mark opens the signed PDF

When `sync.dn_completed` is set and DocuNinja is still active for the company (`enable_modules`, and a hosted Pro, Enterprise or trial plan: `docuNinjaPlanActive`, the plan half of `docuninjaActive()`, since a lapsed plan leaves `enable_modules` on), the invoice, quote and purchase order detail headers show React's green **Signed Document** pill (`signed_document`) next to the status pill (`SignedDocumentPill`, the header's `signedPill` slot, decided by `showSignedDocumentPill`). The signed state comes from `isDocuNinjaSigned` (`lib/domain/docuninja/docuninja_signed.dart`), which accepts `true`, `1` and `"1"`. The DocuNinja check is there because the server serves the signed copy only while `docuninjaActive()`; with DocuNinja off it renders afresh, and the pill would open an unsigned PDF. React shows its badge on `sync` alone. The screens pass no pill at all for an unsigned document rather than one that hides itself, because the header's `Wrap` spaces even a zero-size child.

A quote or purchase order stored before the app kept `sync` has none until it is fetched again, so an already-signed one shows the pill only after its next refresh or a Sync.

A tap opens the document's PDF route with `?signed=1` (`/<entity>/<id>/pdf?signed=1`). For a signed document that PDF is the signed copy: the stored-PDF route serves the DocuNinja-signed file in place of a fresh render (`lib/data/services/stored_pdf.dart`, `CreateRawPdf`). **`signed=1` keeps that true while the record has unsynced edits**: the app's PDF otherwise swaps to a `live_preview` of the local edit (`storedPdfInvitationKey` is null when `isDirty`), which would open an unsigned render under the "Signed Document" label. The signed file does not depend on the edit, so the PDF route reads `signedPdfInvitationKey`, which ignores `isDirty`, for a request the pill made.

**`signed=1` is a request, not a promise** (`SignedCopyRouteMixin`). The server serves the stored signed file only while DocuNinja is active, the document is signed and the file is still attached (`CreateRawPdf`, `BaseModel::getSignedPdfDocument`, which looks up `sync.dn_document_hashed_id` among the record's documents); otherwise it renders the saved record afresh. A remembered or restored link can outlive any of those, so the route re-checks them (`showSignedDocumentPill` and `hasSignedFile`, reading the company row first) and otherwise shows what the PDF route always does, a dirty record's `live_preview` included. The delivery note's "unsynced edit" warning is unaffected: it is the server's saved copy either way. React's badge opens the DocuNinja document (`/docuninja/{sync.invitations[0].dn_id}`, read by `docuNinjaDocumentId`). The app keeps the PDF, which needs no DocuNinja seat; the DocuNinja page (`/docuninja/:id`) exists now, so a link to it for a user who has access is a later step.

Clones drop `sync` (`sync: null` in the invoice, quote and PO clone actions; the cross-entity clones start from an empty document), so a copy of a signed quote is not marked signed.

## DocuNinja talks only through `DocuNinjaClient` (`api.docuninja.co`, its own token); its IN-side handshake passes `unauthorizedIsAnswer`, so no DocuNinja 401 ever ends the IN session

Phase 1a, shipped: the session and the client, with no screens yet.

**The handshake.** `DocuNinjaLoginApi` posts `/api/docuninja/login` to the Invoice Ninja host root (not `/api/v1`), through `ApiClient` with `unauthorizedIsAnswer: true` and `readOnly: true`. A user with no DocuNinja account gets a 400 or 401, and on `ApiClient`'s normal path a 401 runs the permission sniff, a `/ping` and, if that ping fails (offline, a captive portal), a forced logout. The flag skips that whole block, so the refusal arrives as `DocuNinjaRefused`. React does the same with `skipIntercept`. `docuninja_login_api_test` pins that no 400 / 401 reaches `onUnauthorized` or sends a `/ping`.

**What it answers** (probed live on a hosted test account, Nov 2026; fixtures in `test/fixtures/docuninja/`, with tokens, keys, emails and signed URLs replaced):

- One answer per *user*, the same whichever Invoice Ninja company asks: the DocuNinja user, `companies[]` (each with its own `token` and `ninja_company_key`), and the user's `company_user` (`is_admin`, `is_owner`), `account` (`plan`, `num_users`) and `permissions`, once at the top level, not per company.
- The DocuNinja company for the active Invoice Ninja company is the one whose `ninja_company_key` equals the company's `company_key` (`DnLogin.companyFor`). Only the Invoice Ninja companies with `enable_modules` on had one; the others are React's company-setup step.
- The DocuNinja plan was `pro`, with a per-company `document_limit`.

**The session.** `DocuNinjaSession` (`Services.docuNinja`) holds the answer in memory only and maps it to a `DocuNinjaAccess`, as React's provider, Join and Documents pages decide:

| State | When |
|---|---|
| `unavailable` | self-hosted (DocuNinja is hosted-only); the server is never asked |
| `notJoined` | the handshake refused (400 / 401): Join. React's provider sends *every* refusal to `/docuninja/join?ie=true`, and `ie` skips Join's "the account has seats" redirect, so seats bought make no difference: an eligible owner or admin is offered Create, everyone else is told to ask their admin |
| `planWall` | a DocuNinja admin whose DocuNinja plan is not `pro` (`useDocuNinjaAdmin`, the DocuNinja role, not the IN one). Checked **before** company setup, in `Documents.tsx`'s order |
| `companySetup` | an answer with no company paired to this one |
| `ready` | everything else |
| `offline` / `failed` | the handshake could not reach the server / failed otherwise |

**The company key is read first.** The pairing is by `company_key`, so a company without one (credentials stored before its row) is `failed` with Retry and DocuNinja is not asked; read as "no company paired", it would offer a Set up that posts `/create` for a company that may already be paired. React refuses the same way ("No company key"). A failed read is `failed` too, never a spinner that never ends.

**A forced reload that fails keeps what worked.** A 401's refresh that cannot reach DocuNinja (or fails) leaves a ready session as it was: its token may still be good, and the screens, the socket and a half-typed search survive the blip. A token refresh that spans a company switch hands back no token, so the request that asked is never sent with the next company's. A timed-out write is an error, not "offline": the timeout does not stop it, so the screen re-reads rather than invite a second send.

It resets on sign-out and on every company change (`Services.build`, beside the calendar connection), and a generation counter drops an answer that lands after a reset, so a late handshake never hands company A's token to company B. A forced reload (Reconnect, a 401) keeps the current state and token until the new answer lands. A load starts its work a microtask later: the screens start it from `didChangeDependencies`, inside a build, and its first change notice (`loading`) would otherwise mark the provider above them dirty mid-build, which debug builds refuse (`docuninja_session_test`).

**The client.** `DocuNinjaClient` uses its own `http.Client` (`createDefaultHttpClient`), never `ApiClient`, whose 401 handling belongs to the Invoice Ninja session. It sends `Authorization: Bearer <company token>`; a 401 re-runs the handshake once (`DocuNinjaSession.refreshToken`) and retries, and a second one surfaces as `DocuNinjaException`: a list shows Retry, and a document the user has no DocuNinja access to points to DocuNinja's home (Join, setup). Server messages are logged, never shown raw as a toast; a refused field's own message shows beside that field. `DocuNinjaApi` holds the document endpoints the list and detail screens use.

**Online-only.** DocuNinja data is not in Drift and does not go through the outbox (both are exceptions in CLAUDE.md): it is another service whose state machines (send, sign, void) run server-side, and a queued write against them could not be replayed safely. Page previews are signed URLs that expire after an hour (`DnFile.previews`), so they are re-read with the document, never stored; they send `Access-Control-Allow-Origin: *`, so the web build can draw them.

## The DocuNinja screens follow React's, decided by the session

Phases 1b–1d, shipped: the sidebar entry, the screens before the documents, the list and the detail page. Each mirrors React's (`pages/documents/…` at `origin/HEAD`), in the app's chrome.

- **Entry.** A fixed branch, `FixedBranchKind.docuninja` at `/docuninja` (branch 23), the sidebar row "DocuNinja" (`Icons.draw_outlined`, not the Documents list's icon) and `G N`. Like React's nav it shows for every *hosted* user; on self-hosted there is no row, no Customize-sheet entry and `G N` is refused, since DocuNinja is a hosted service.
- **Before the documents** (`DocuNinjaScreen` switches on `DocuNinjaAccess`):
  - **Join** (`Join.tsx`): the logo, tagline and three features, then Create for an Invoice Ninja owner or admin on Pro or Enterprise (`/api/docuninja/create`, then the session and the company refresh, since the server turns on `enable_modules`), Upgrade for one on another plan, and React's "contact your admin" for everyone else.
  - **Company setup** and the **plan wall** (`DocumentStates.tsx`). React hard-codes the setup sentence in English; the app's is `docuninja_company_setup_help`.
  - **Create** (`/api/docuninja/create`) passes `unauthorizedIsAnswer`, like the handshake (React's `skipIntercept`), so its 401 is an error toast, never a sign-out. Once it succeeds the handshake always re-runs, even when the company refresh after it fails.
  - **Upgrade** goes to Account Management (`/settings/account_management`), as React's does. That screen already follows the store rules, so nothing here offers a purchase.
- **The list** (`Documents.tsx`, `useTableColumns.tsx`): on a pane of 720 px or more, React's table (contact, user, document, files, status, created at, the date of the first file); narrower, a row per document. A page of 20 at a time, pull to refresh. The status badge keeps React's colour families in this app's tokens, and deleted or archived win over the status. A row opens the detail page; React opens a draft without invitations in the builder; the app keeps the detail page one tap from it (the builder opens in the browser until the embed is on).
  - **Each row has React's `⋮`** for what acts at once: Edit (the builder), Timeline (the document page), View PDF, Clone, Clone to Template, Void, Archive / Restore / Delete, with the document page's conditions and confirmations. Send, Options and the downloads open dialogs that live on the document page, a tap away.
  - **Bulk selection** (React's table checkboxes, `withResourcefulActions`) on the documents, templates and users lists, sharing one piece (`DnListViewModel`'s selection and `applyBulk`, `widgets/docuninja_bulk.dart`). The ⋮ menu's Select (an icon on the templates and users lists), a long press on a row, or on a pane of 720 px or more the row's checkbox slot (shown on hover) starts it; a tap then ticks instead of opening, the row's ⋮ steps aside, Back leaves selection first, and the search row gives way to Cancel, "N selected", Select all visible and the actions. Archive, Restore and Delete go out as one `POST <resource>/bulk {action, ids}` for the rows that can take them (Restore only for rows that are not active, as React shows it; the users list leaves out the owner and the signed-in user); the rest are reported as skipped. Archive and Delete ask first while Confirm actions is on (React asks nothing). The rows re-read afterwards, whether or not the request failed, since a timed-out one may have landed, and a row that leaves the list leaves the selection, so a bulk never reaches a record no longer shown. The users list re-counts its seats after one. The template plurals (`archived_templates` …) are app strings; React toasts `archived_blueprint`, which no bundle has.
  - **Search is `search`.** DocuNinja ignores `filter` (measured: every document came back).
  - **One `status` list carries both filters.** React's table sends the lifecycle states (active / archived / deleted, default active) and the statuses (`useDocumentFilters.ts`) together, and DocuNinja matches a document whose state *and* status are both listed (measured: `active,sent` found the sent document, `active,completed` nothing). The state set is never empty; an empty pick means active.
  - **The next page loads when the end is in view, not only on a scroll** (`_checkAfterLayout`): a first page that fits a tall window never scrolls. A failed page stops that, shows a Retry footer (`DocuNinjaInlineError`) under the rows, and the next attempt clears the error. **No next page is asked for while a search waits out its debounce**: the rows and page count are still the old search's, so it would be the new search's page N+1 appended to them.
  - **A failed first page for a new search or filter drops the old rows**, which would read as its results; a failed refresh of the same query keeps them, with its Retry notice above the rows, where the pull happened. The file count stays plain text: it holds a translated word, so forcing it left-to-right would scramble it in a right-to-left language.
  - **The search field sits in the body**, not the app bar's fixed-height `bottom`, so it grows with the text size.
  - **A changed query drops a page still in flight, and clears the load-more flag itself** — the stale request's own `finally` no longer owns it, so without that the list stops paging for good (`docuninja_documents_view_model_test`).
  - **The list re-reads after any change on a detail page** (`DocuNinjaSession.documentsChanged`), as React refetches its documents after every action.
  - **A refresh keeps the user's place.** It reloads as many pages as are showing, up to five (`DnListViewModel.kRefreshMaxPages`), and swaps them in together, so a live event from a teammate, a return from the browser or an action on a detail page never drops a user sixty rows down back to the first twenty (React's table keeps its page number). The templates and users lists share it.
  - **The list waits while it is off screen.** The DocuNinja branch stays mounted once visited, and the list stays under a document opened from it, so a refresh asked for while the user is elsewhere (a live event, a return to the app) is held and run once when the list shows again (`TickerMode`), instead of a stream of background requests; a refresh while one is in flight shares it, and Retry after a failed deep refresh keeps the depth. The company's handshake after a switch is never held: Templates, Users or Settings may be showing over the list and wait on it. The list widget is keyed by its view model, so a new company's list starts at the top in that company's date format.
  - **Dates are the user's calendar day** (`dnLocalDate`): DocuNinja stamps UTC, so the date part of the string is the wrong day for anyone far from UTC.
- **The detail** (`show/Document.tsx`): the title and status, the signers in signing order (`Invitations.tsx`, with where each is and a resend) beside the timeline (`TimelineLayout.tsx`, its UTC times shown local), and React's actions in its order where they apply: view PDF, send, audit log, download (completed only), clone, void (sent only), options (description; expiry until sent), archive / restore, delete. They are `EntityActionItem`s in `EntityActionsPopupButton`, so the menu closes on Android back and void, delete, archive and clone confirm through `guardedOnTap` (the Confirm actions preference). Archive and Clone carry React's questions (`archive_document_description`, `clone_document_description`): unlike the app's other Clones, which open an unsaved edit screen, this one creates the copy on DocuNinja at once.
  - **The route is keyed by the document id** (`router.dart`), as the entity detail routes are: go_router keys a page by its pattern, so Clone's `go` to the copy would otherwise keep the original's State and view model, and every action would still hit the original.
  - **View PDF** is React's `shouldShowPdf`: completed, not deleted, with a file. Download and the audit log stay completed-only.
  - **The header shows Deleted or Archived beside the status**, as React's does (`DocuNinjaLifecyclePill`), and passes no lifecycle pill at all for an active document, since the header's `Wrap` spaces even a zero-size child. The list keeps one badge, where deleted and archived win. A document whose status is unknown offers no Resend.
  - **A re-read that fails after an action (or a pull to refresh) says so** with an inline Retry above the signers, so a success toast never sits beside stale data unexplained.
  - **Share / Copy Link** opens the document in the app on its company: `<base>/app/docuninja/<id>?company=<id>` (`buildDocuNinjaDeepLink`, parsed by `parseAppDeepLink` beside the entity links, which accepts `/docuninja` and `/docuninja/<one segment>` and nothing deeper; that segment can also name `templates`, `users` or `settings`, which then open, gated as everywhere). On a self-hosted server the route's redirect sends such a link home.
  - **The body is selectable** (`AppSelectionArea`), and emails, dates and times render left-to-right in a right-to-left language: as their own `LtrText` run inside the selectable page, so a copy carries no invisible direction marks (`ltrIsolate` only where the text is not selectable). Success toasts are React's keys (`voided_document`, `document_archived`, `document_restored`, `deleted_document`, `cloned_document`).
  - **Send** follows React's `useIsSendable`, which checks the *Invoice Ninja* role and permissions (`edit_documents`, `create_documents`, `requires_approval`), not DocuNinja's. React also lets a creator send their own document by comparing the DocuNinja document's `user_id` with the Invoice Ninja user id, which never match; the app leaves that arm off.
  - Send opens React's `send_confirmation` dialog listing who will be emailed (scrollable, for a long list), its primary not autofocused because it emails customers.
  - **Each signer** is labelled React's way, `Client Contact:` or `User:`, and has React's Copy Link, which copies on every platform (below): the web app's sign page for that signer (`dnWebAppSignLink`), which, as in React, opens behind the web app's sign-in, so it is for the team, not a link to send the signer.
  - **Resend** is shown until the document is completed, voided or deleted (`dnShowsResend`); with a signing order only the next unsigned signer's is enabled (`dnCanResend`, React's `canSendInvitation`). It confirms first, since it emails a customer.
  - **Delete stays on the page**: the document reloads deleted, with Restore. It goes through `POST /api/documents/bulk` with `delete`, like archive and restore: that is the call React's list makes, while its `DELETE /api/documents/{id}` sits in code no route reaches (React's own detail page never shows archive, restore or delete, because its action hook checks for a `/documents` path; the app offers them).
  - **Options saves from inside the dialog**, cannot be dismissed while it saves, and stays open on a refusal, showing the field errors, so an edit is never lost. The expiry is the stored string's calendar day, and it is sent only when it changed while the document can still expire — an untouched field is never re-sent shifted a day.
  - The signed PDF opens at `/docuninja/:id/pdf` in `PdfPreview`. Downloads go through `downloadPdf` under DocuNinja's own file name, with `sanitizeFileName` (docs/file-downloads.md); one runs at a time.
- **A new search or filter shows a thin bar** above the previous query's rows until its first page lands (`isRequerying`), and an empty previous result shows nothing rather than "no records found" meanwhile. A row action that navigates after its request (Clone, Void, Clone to Template) does nothing if a company switch replaced the list meanwhile.
- **A page that is not the home says why** when DocuNinja is not ready (`DocuNinjaGoHomeState`: the Join tagline, the company-setup sentence, the plan wall's or the offline one), with the way to DocuNinja's home, which has what to do about it. A 403 on a document reads `unauthorized_action`, not "Document not found", which is kept for a 404.
- **Each signer's link always copies** (`copy_link`), on touch too: the link opens behind the web app's sign-in, and a share sheet beside a client contact's name invites sending it to a client who would meet a sign-in wall. The document's own link keeps Share Link on touch.
- **Clone to Template asks the app's generic question.** React asks with `make_template_description` ("Create your own template using your own PDF document to upload"), which describes the wizard, not a clone.
- **Restart keeps Templates, Users and Settings.** `companySafeLocation` strips a document id (`/docuninja/<id>`) on a switch or a restore, but those three pages are keyed by the company, so they stay; a record under them (a template's builder, a user) goes back to its page.
- **Not yet:** the embedded builder switched on (it is built, behind `kDnEmbeddedBuilder`, waiting on React's embed mode; until then the builder opens in the browser, below).
- **Strings** are React's keys. The handful missing from this app's `en.json` (`docuninja_join_*`, `docuninja_creating_account`, `signatories`, `send_emails_to_following`, and `docuninja_company_setup_help` for the sentence React hard-codes) have their English in `_app_pending.json`. Most locale bundles already translate them (they came from the server's language files), so a locale's `_app_pending_<locale>.json` carries one only where its bundle does not: React's own translation where it has a real one, the app's otherwise (Serbian is Latin script here, so never React's Cyrillic).

## The field builder opens in the browser for now

Phase 2 embeds React's field builder in the app (a React-hosted embed page in a WebView). Until that ships, the app does what React's own pages do around the builder and hands the builder itself to the browser.

- **New Document** (`showDocuNinjaCreateDialog`, the list's `+`, shown when the DocuNinja role may create documents) is React's `Create.tsx`: a name and the files, uploaded in one `multipart/form-data` `POST /api/documents` (`DocuNinjaApi.createDocument`, `DocuNinjaClient.postMultipart`).
  - The accepted types are the drop zone's: pdf, doc, docx, odt, xls, xlsx, png, jpg and jpeg (`kDnUploadExtensions`). React accepts `image/jpeg` by MIME type.
  - The name starts as the first file's, as React's `getDocumentNameFromFile` writes it (`dnDocumentNameFromFile`), until the user types one.
  - A password-protected PDF is asked for its password and uploaded as `name.pdf|password`, as React does. The app detects the `/Encrypt` trailer entry (`dnLooksPasswordProtected`) where React asks pdf.js, which is not the same answer: a PDF with only an owner password (permissions, nothing needed to open it) is encrypted too, and React would not ask. So the prompt takes an empty answer as "it opens without one" and uploads the file as it is.
  - **A multipart body can be sent only once,** so the client rebuilds the request for its retry after a 401 (`_sendWith`). An upload gets five minutes, not a JSON call's sixty seconds.
  - Then, as React navigates to the builder, the app lands on the new document and opens its builder.
- **Edit** (the detail page's edit button, React's) opens the builder. As in React it is disabled once the document is completed or voided.
- **The builder opens in the browser** at `https://app.invoicing.co/#/docuninja/<id>/builder?company=<company id>` (`dnBuilderWebUri`, `openDocuNinjaBuilder`). The hosted web app uses the hash router. `?company=` makes a fresh tab open on the document's company (React's `resolveCompanyIndex` reads it once on load and pins that tab), so a user with several companies does not land on the wrong one.
- **Coming back re-reads.** The list and the detail page refresh when the user returns after at least five seconds away (`dnRefreshOnReturn`), so fields placed and documents sent in the browser show up. "Away" starts the first time the app stops being active, so a desktop window that only lost focus for a moment does not re-read.
- **The dialog hands back its photos.** A camera or gallery capture sits in `shared_intake/` until released; the dialog releases every one it took when it closes (sent, removed, refused or abandoned), as the other photo sites do, rather than leave a photographed contract for the launch sweep.
- **Rows still open the detail page**, where React opens the builder, and Clone still lands on the copy's detail page. Opening a browser from a row tap would be a surprise; both move to the builder once the embedded builder is on.

## On the web a builder opened after an await is a toast button

After an upload, a clone or a new template, the builder opens only once the server has answered. On the web that is outside the tap's user activation (about five seconds in Chrome, one in Safari), so `window.open` is blocked, and silently: `url_launcher_web` opens with `noopener` and cannot tell, so it reports success and no toast appears. There `notifyAndOpenDocuNinjaBuilder` shows the success toast with an Edit button instead, whose tap is a fresh activation and which runs on the root navigator's context, since a `go` to the new document may have replaced the caller's page by then (Use Template does); everywhere else it shows the toast and opens the builder at once. A builder opened straight from a tap (Edit, a template row) calls `openDocuNinjaBuilder` directly.

## The field builder runs embedded where a web view can

Phase 2's in-app builder is **the hosted web app's own builder page, in a web view, in embed mode**, not a separate embed page. React's builder pulls from the whole React app (client search and `ClientCreate`, preferences and tours, the company's date format, i18n, the company store), so a standalone page would need an adapter for each and drift from React's own. The React side is a small change in invoiceninja/ui ([#3457](https://github.com/invoiceninja/ui/pull/3457): `src/common/helpers/embed.ts`, the `Default` layout, `Builder.tsx`); until it is live on the hosted app the embed stays off (`kDnEmbeddedBuilder`, `--dart-define=DOCUNINJA_EMBED=true`), and Edit opens the browser as above.

- **Where.** `/docuninja/:id/builder` (`DocuNinjaBuilderScreen`) on iOS, Android and macOS (`webview_flutter`) and Windows (WebView2), through `DnEmbedSurface` (`dnEmbedSupported`; docs/windows-web-view.md). Linux and the web open the browser. The app draws the title, Back and an "open in browser" button; the page draws the builder and its Send / Save for later.
- **The page** is `https://app.invoicing.co/#/docuninja/<id>/builder?company=<company id>&embed=1` (`dnEmbedBuilderUri`). `embed=1` makes React render without its sidebar and top navigation, and remember the mode for the tab.
- **Sign-in is a handshake, never a URL.** The page boots only after it posts `ready` and the app answers with `InvoiceNinjaEmbed.init({v, token})` (`dnEmbedInitScript`, the token JSON-encoded). **Every boot asks**, and every `ready` is answered: React reloads itself (on a 401, after an update), and a page left waiting would stay blank. React enters embed mode only when the app's channel exists, and boots without a token after fifteen seconds, so `?embed=1` pasted into a browser tab strands nothing. React keeps the token in `sessionStorage`, the way a tab opened on another company does (`company-session.ts`), so it dies with the web view; `?company=` then pins the tab to the document's company. The app hands the token over only while the web view is on the web app's origin (`dnEmbedAllowed`).
- **Only the web app loads.** Any navigation off its origin is refused, and a main-frame web link opens in the browser instead; the page's own new-tab links come as `openExternal`, opened only when http(s); a new-tab link to the web app itself (React's Sign) opens in place instead, keeping the page's sign-in, which the browser would not have.
- **The sign page** (`signInvitationId`) reports `loaded` and then `signed`; a signature refreshes the document and closes the page.
- **A page that cannot sign in** (a 401, which React answers with a reload that would boot with the same token, forever) reports `error` instead, and the screen offers the browser, with a sentence saying the editor could not open here (`docuninja_builder_unavailable`). A 429 shows React's own toast and the page stays: embedded, React never reloads on one. The app bar's button reads "Open in browser", not Edit or Sign, since the user is already in the editor.
- **A builder that never comes up says so.** Once the page has asked for its token, the twenty-second fallback no longer applies; if the builder still has not reported `loaded` sixty seconds later (a document it cannot open never does, and React's own message sits under the cover), the cover offers the browser with `docuninja_builder_unavailable` and keeps waiting. A `ready` carries no nonce, so one with another protocol version is acted on only after a main-frame page start: no other frame can turn the screen off.
- **Sign saves first.** Embedded, the builder's Sign saves the document before it opens the sign page, so a signature is never put on a version missing the latest fields.
- **File inputs** work in the web view on iOS, which answers them itself, and on Android, whose chooser goes through the app's file picker (`setOnShowFileSelector`). **macOS has none:** `webview_flutter_wkwebview` does not implement WebKit's open panel there, so a file input in the embedded builder does nothing; the document's own files are uploaded before the builder opens, and a file added in the builder needs the browser. The builder's Google Drive import is hidden embedded, since Google refuses its sign-in inside an app's web view; the page's own frames load where it puts them.
- **Every message after `init` carries the screen's nonce.** The app generates a secret per screen (`Random.secure`), hands it over with the token, and ignores any message other than `ready` that does not echo it: the channel is open to every frame on the page, and a message is no proof of who sent it. The init script itself runs only on the web app's origin (`dnEmbedInitScript` checks `window.location.origin`), and a `ready` clears the unsaved flag only after a main-frame page start (`pageStarted`), so a `ready` some frame posts cannot wipe it.
- **Messages** are JSON `{v, type, payload, nonce}` on the `InvoiceNinjaApp` channel (`DnEmbedMessage`, handled by `DocuNinjaBuilderViewModel`): `ready`, `loaded`, `dirty`, `saved` / `saveError`, `sent` / `sendError`, `documentUpdated`, `mapSignatoriesSent` (the app closes the builder, where React navigates to the list) and `openExternal`. Another `v` is not driven. A page that never says `ready` within twenty seconds (the server has no embed mode, or the load failed) offers the browser instead; once it has, it is an embed however long the builder then takes (previews of a large upload can take minutes).
- **Unsaved work.** The builder keeps no dirty flag, so the page derives one: what a save sends (fields, signers and their order and details, the files' order) against a baseline taken when the document first loads and after each save. The builder reloads the document on its own as previews arrive, restoring local edits, so a later load keeps the baseline. While the flag is set, Back, the shell's navigation and any other route change ask before discarding (`UnsavedChangesScope`, the route's `onExit`). A new boot clears it (a reload has no unsaved edits), and so does leaving the builder for another page of the web app. With nothing unsaved, the builder's own reload after a save is the new baseline, so a save never reads as unsaved changes.
- **The route exists only where it works.** `/docuninja/:id/builder` redirects to the document when the embed is off or the platform has no web view, so a restored or typed address never builds a screen that cannot draw.
- **Storage is cleared** before each load, when the screen closes and at sign-out (`clearLocalStorage`, `clearDocuNinjaWebStorage` in `onSessionReset`, for an app killed with the builder open): React keeps the DocuNinja token in `localStorage`, and no visit or user may inherit another's.
- **Not verified on a device yet** (spike 2 in the plan): pdf.js on iOS before 17.4, the file picker inside the web view on macOS and Android, and placing fields by touch on a phone.

## Templates

React's templates (the API's blueprints) at `/docuninja/templates` (`DocuNinjaTemplatesScreen`, reached from the DocuNinja screen's templates button), gated as React's routes are: viewing needs `blueprints` view, creating and editing need `blueprints` create (the template builder's route checks create, not edit).

- **The list** (`Blueprints.tsx`): name (`untitled_template` when blank), React's type (`<Entity> Design` for one made from an Invoice Ninja design, else Custom) and an Active / Archived / Deleted pill; search, paging and pull to refresh through the same `DnListViewModel` as the documents (`DocuNinjaTemplatesViewModel`). A row opens the template builder.
- **Row actions** (`blueprints/common/hooks/useActions.tsx`): Use Template, Options, Archive / Restore / Delete through `POST /api/blueprints/bulk`. React confirms none of them; the app confirms Archive and Delete, as its own lifecycle actions do.
- **Use Template** is `POST /api/blueprints/{id}/action {action: make_document}` with no mappings, then the new document's builder with `from_template=true`: the builder itself asks who each of the template's signers is (its `mapSignatoriesFlow` dialog) and React starts its template tour. React's separate `map-signatories` page is unreachable code, so the app has none.
- **New Template** is React's wizard (`BlueprintWizard.tsx`), in a dialog: an Invoice Ninja design for one document type not yet made (the first hundred active templates decide which; `POST /api/docuninja/stub_blueprint {entity}` on the Invoice Ninja server, `DocuNinjaLoginApi.stubBlueprint`, which like the handshake never ends the session on a 401), or a template of the user's own (`POST /api/blueprints {name, description}`). Its PDF is uploaded in the template builder. React's gallery option is commented out, so it is not offered.
- **Options** (`EditBlueprintModal.tsx`) writes the whole template back with the new name and description (`PUT /api/blueprints/{id}`), as React does; Save needs a name.
- **Clone to Template** on a document (`make_blueprint`) asks first, then opens the new template's builder.
- **The template builder** is React's `templates/<id>/edit`, embedded or in the browser exactly like the document builder (`/docuninja/templates/:id/builder`, `dnBuilderRoute`, `dnWebAppBuilderUri(template: true)`); the React embed reports the same events from it (`useEmbeddedBuilderEvents`). React's Send on the template builder is unreachable, so there is none.

## Settings

DocuNinja's own settings at `/docuninja/settings` (`DocuNinjaSettingsScreen`, the DocuNinja screen's gear), for a DocuNinja admin (`dnIsAdmin`, React's `docuNinjaAdmin`), in React's five tabs (`CompanyDetails.tsx`, `useSettingsTabs`).

- **Email settings, notifications and widget defaults** edit the DocuNinja company's `settings` and put the whole company back. Each tab keeps only what the user changed on it and lays that over the company's current settings on save, so one tab never writes back another tab's stale values, nor a display default the server never held (`PUT /api/companies/{id}`, `updateCompanySettings`, the login answer's company kept whole in `DnCompany.raw`). The company is the one paired with this Invoice Ninja company; React reads the first in the list, which is wrong on a multi-company account. A save hands the session the company as saved (`DocuNinjaSession.replaceCompany`) where React refetches its login: the other tabs build their next save on it at once, with no second handshake for another tab's save to race and no failure to tear the screen down; one company save runs at a time. An empty from-name or reply-to is sent as null, as React does; React's English-only help text and placeholders on that page are left out.
- **A save that spans a company switch sends nothing.** A company tab re-reads the company (the handshake) before its PUT; if the session's epoch moved meanwhile, or DocuNinja no longer pairs the company, the save stops there rather than send this company's record under another company's token. The PUT also leaves out the login's bearer `token`, which rides along in the company the login returned.
- **Leaving asks first.** Each tab knows what differs from the company as saved (a flag held as `1` is the switch's `true`, and a display default is not an edit), and while one does, Back, the shell's navigation and a company switch ask before discarding (`UnsavedChangesScope`, the route's `onExit`). Discard puts the tabs back as saved. A company tab's Save is off while another company tab saves, rather than silently doing nothing.
- **Email templates** (`GET /api/templates`, saved together through `POST /api/templates/bulk {action: update}`): a subject and a plain-text body per template, picked from a list (React uses a tab per template; the server names them). React's variables card lists the `{{ ... }}` tokens the server fills in.
- **Reminder schedules** (`/api/reminder_schedules`): a toggle that saves at once, edit and delete (confirmed), and add. New ones start at one day after the event, enabled; like React there is no control for the direction, so an edit keeps it. Archived and deleted ones are hidden, as React hides them.
- **Strings.** Seventeen of React's keys for these pages are not in this app's bundle (`widget_defaults`, `reminder_schedules`, the widget and reminder keys); they are in `_app_pending.json`, each locale carrying React's translation where it has a real one and the app's otherwise.

## Users

DocuNinja's users at `/docuninja/users` (`DocuNinjaUsersScreen`, the DocuNinja screen's people button), for the DocuNinja owner only, as React's `docuNinjaOwner()` guards them. React leaves its grant-access page unguarded, though only the owner's list links to it; the app guards it too.

- **The list** (`Users.tsx`): the users of the DocuNinja company paired with this Invoice Ninja company (`GET /api/users?ninjaCompanyKey=`), name, email and an Active / Archived / Deleted pill, the lifecycle filter (`DnFilterDialog`, without it an archived user could never be restored), and Archive / Restore / Delete through `POST /api/users/bulk` (confirmed, as the app's lifecycle actions are).
- **One seat count.** React counts seats three different ways; the app uses one: DocuNinja's `account.num_users` against the account's DocuNinja users (`_seats`, active and archived, counted with an empty company key as React's alert counts them, since the limit is the account's). As in React, an account without `num_users` has no seat: New User is off when none is left, and the count and an upgrade link say so. If the count cannot be read, New User stays on and the server decides.
- **Editing a user** (`users/edit/Edit.tsx`, `/docuninja/users/:userId`): the name and email read-only, as React shows them; the Administrator switch and React's permissions grid (`DnPermissionsGrid`: create, view, edit, delete per model, requires approval for documents, an All row; switching the role clears the grants, as React does); and the notifications (`DnNotificationChoice`: all, the user's own, none, or per document event, encoded as React's codes `all`, `all_user`, `<type>`, `<type>_user`). Save puts the whole user back (`PUT /api/users/{id}`; an admin carries no permissions) with every grant it came with: the grid shows only global grants, and a grant scoped to one record, and each grant's id, go back as they came, as React sends them. Notification codes the app does not list are kept too. React's grid labels the `blueprints` model with a key its own bundle lacks; the app uses `blueprint`.
- **Grant access keeps Add off until the re-read after a failure lands**, so a request that timed out but went through drops its user from the selection before a retry could grant them twice. Deleting a user drops the editor's unsaved edits first, so the way out asks nothing about a deleted user.
- **The owner and the signed-in user cannot be archived or deleted** here (`_lifecycleLocked`): either would lock the owner out of the screen that restores users. React offers both; the row keeps the empty slot so the column stays aligned.
- **Leaving the editor asks first** while the role, a grant or a notification differs from the user as last read, as every other edit screen does (`UnsavedChangesScope`, the route's `onExit`).
- **Signature and initials** (`e_signature`, `e_initials`) are edited the three ways React's user page offers (`Details.tsx`), in `DnSignatureField`, and go back with the user's save:
  - **drawn** on a pad in a dialog (so a stroke never scrolls the page), black on white in either theme;
  - **uploaded**: a click or a drop on the box (`FileDropZone`), any image `dart:ui` decodes, decoded at no more than twice the stored size (a phone photo decoded whole is ~200 MB of pixels on the UI isolate);
  - **generated** from typed text in one of React's five handwriting fonts (Dancing Script, Great Vibes, Pacifico, Satisfy, Alex Brush). They are Google Fonts, fetched on demand with `google_fonts` as the invoice designer fetches its fonts, rather than bundled (about 1 MB, with their licences). google_fonts can only wait on every font in flight, with no timeout, so Generate waits at most 20 s, ignores the other previews' failures, and then checks the chosen font really draws (a fallback face is a different width) before using it; offline it says so, and Cancel stays live throughout.
  - **Stored as React stores it** (`image-compression.ts`): a JPEG data URL on white, at most 600 × 200 for a signature and 200 × 150 for initials, quality 0.7 (`dnSignatureDataUrl`). That is why `image` is a runtime dependency, for its JPEG encoder only; decoding goes through `dart:ui`, so the decoders are not linked in. A drawn or typed one is first trimmed to its ink with React's 40 px margin (`dnTrimToInk`); React trims only the typed one, and the untrimmed pad left a drawn signature small in its field.
  - The label is `invoice_signature` ("Signature"): React's `signature` key reads "Email Signature" in every bundle, React's own included.
  - A changed signature or initials counts as unsaved, so leaving asks first.
- **Granting access** (`UserSelection.tsx`, `/docuninja/users/access`): the company's Invoice Ninja users from the roster the app already holds (`watchAllForPicker`, so no fetch) who are active, not the owner, and have no DocuNinja user of the same email; picked within the seats left, with one role and set of permissions for all of them; one `POST /api/docuninja/create_user` per user on the Invoice Ninja server (`DocuNinjaLoginApi.createUser`), which like the handshake never ends the session on a 401. They go one at a time: if one fails, only the users still without access stay selected and the list and seats re-read, so a retry never grants anyone twice (React fires them together and leaves the whole selection). React lists the whole account's users; the app lists this company's.

## Signing your own invitation

React lets the signed-in user sign a document they are a signer of from its builder's Sign button; the app offers the same as Sign on the document page (`_Action.sign`), for the user's own invitation (`dnOwnInvitation`: theirs by the login's DocuNinja user id, not a client contact's, not yet signed, the document neither completed, voided nor deleted).

- **It opens React's own sign page**, `/#/docuninja/sign/<document>/<invitation>?sig=<invitation>&company=<company>` (`dnWebAppSignUri`): embedded at `/docuninja/:id/sign/:invitationId` where the builder is (`DocuNinjaBuilderScreen(signInvitationId:)`, the same handshake and allow-list), else in the browser, where the web app needs its own sign-in.
- **Unverified.** React's builder sends the invitation id as `sig`, and its sign page passes no `sig` at all; whether DocuNinja answers that with the `x-signer-token` the submit needs could not be checked (the server is not open source). The native signer the plan describes waits on that answer.

## Live updates

DocuNinja broadcasts on its own Pusher host, not Invoice Ninja's (the public Invoice Ninja server never sends these events, though React's list listens for them there). `DocuNinjaRealtime` (`lib/data/services/docuninja/docuninja_realtime.dart`) is a second `PusherConnection`:

- `wss://socket.docuninja.co/app/docuninja-key`, React's builder package's host and key; the channel is the paired DocuNinja company's `private-company-<id>`, signed by DocuNinja's `/broadcasting/auth` with the company token (`DocuNinjaClient`, so a 401 re-runs the handshake, never the Invoice Ninja logout).
- It follows `DocuNinjaSession`: connected while the session is ready, dropped on any reset (sign-out, company switch) or refusal, and closed in the background.
- `DocumentWasSigned` and `DocumentFilePreviewGenerated` only bump `DocuNinjaSession.remoteChanged`; the documents list, the templates list and an open document re-read on it (React's detail page refetches on `DocumentWasSigned`). Nothing is written, and no Invoice Ninja `/refresh` is scheduled.
- Like the Invoice Ninja socket it exists only with `Services.build(realtimeUpdates: true)`, which only `main.dart` passes (`realtime_opt_in_test` pins that literal to `main.dart`; that the socket is built only inside `if (realtimeUpdates)` in `Services.build` is not linted, so keep it there).
