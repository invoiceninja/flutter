# Server-seeded contacts and invitations

Companion to CLAUDE.md § Design system (v2) (the contact and invitation rules). The server seeds rows the user never created — one blank contact per client and vendor, one invitation per send-email contact, and a placeholder email address it typed itself — so `isNotEmpty` is never the question. Each rule names the per-row predicate that is.

## The server seeds one blank contact, so `isBlank` per row is the question

**The server seeds one all-blank contact per client and per vendor, so `contacts.isNotEmpty` is never the question — `isBlank` per row is.** A vendor the user gave no contact details rendered a Contacts card holding one row reading `(no name)` beside a blue primary star (invoiceninja/flutter#115). `Contact.isBlank` / `VendorContact.isBlank` (`lib/data/models/domain/contact.dart`, `vendor_contact.dart`) are the one predicate — first name, last name, email and phone all empty after `trim()` — replacing the two verbatim private `_isBlankContact` twins in the client and vendor edit VMs, which read it as "the user typed nothing" for the discard prompt. **The `trim()` is load-bearing, not defensive**, and only the server source says so: `ClientContactRepository::save` (`//always made sure we have one blank contact to maintain state`) writes `email = ' '` — a literal single space — and nothing between the wire and the domain model trims it, so an untrimmed predicate matches nothing on the client side. The vendor factory leaves `email` at `''`, which is why the identical row read `(no name)` on a vendor but painted an *invisible* title on a client. Each detail card filters its rows through it and exposes `static bool hasContent(List<…>)`; the grids gate the wide `Expanded` column **and** the stacked entry on that, the shape `ClientDetailShippingAddressCard.hasContent` already set. Three things are load-bearing. **`link` is deliberately out of the predicate** even though the client row builds portal buttons from it: the server mints a portal link for the blank contact too, so counting it would make the client card filter *nothing* and quietly reduce this to a vendor-only fix — React's `clients/show/components/Contacts.tsx` omits it from the identical test, and nothing is lost, since `ClientAction.clientPortal` / `VendorAction.vendorPortal` resolve the primary contact's portal from the actions menu independently of this card. **`customValue1..4` are out only because neither Flutter card renders them** — React's row does, which is why *its* predicate counts them — so a card that starts showing contact custom fields must widen its own `hasContent`, never `isBlank`, or the edit VMs stop offering to save work the user actually typed. And **the client card's `_inlineLimit` / "+N more" / bottom sheet must all count the *filtered* list** (the sheet re-filters on its own, being a separate route): an overflow button offering to reveal rows that paint nothing is the same bug wearing a hat. Note the row's own `name → email → no_name_fallback` title cascade stays — a contact with a phone and nothing else is not blank, still renders, and still needs a heading.

## An invitation is created when the document is saved, not when mail is sent

**An invitation is created when the DOCUMENT is saved, so `invitations.isNotEmpty` is never the question — `hasSendHistory` per row is.** `CreateInvitations.php` (plus `BaseRepository::alternativeSave`'s `count() == 0` fail-safe) seeds one invitation per send-email contact with `sent_date = null`, so a draft invoice always has N of them, and `BillingDocSendsTab` listed every one: a bold contact name, a grey email, and **nothing beneath**, under a heading reading "Email History". Testers read that as proof the contact had been emailed (invoiceninja/flutter#146, the seventh density/clarity report from the same Android tester). The predicate lives on the domain model beside `hasBeenSent`, and the tab has **six** mount sites, not five — the fifth billing detail screen plus `billing_doc_email_screen.dart`'s Send Email composer, where the History pane is only ever read *before* sending (the composer pops on send), so the new copy is exactly the pre-send reassurance someone wants with a finger over Send. Six things are load-bearing and most of them fail silently. **The predicate is a disjunction, never `hasBeenSent` alone**: `NinjaMailerJob` writes `email_error` with no `sent_date` on a failed send, and that is the row that most needs to survive. The delivery half of the predicate **delegates to `sendState`** rather than testing `emailStatus` / `emailError` itself, so the filter and the pill are one expression: spelled out separately they drift, and a status the pill could not map would have passed the filter as a bare row — #146 by construction. It is deliberately **not** gated on `messageId`, which is the precise "a real email left the building" discriminator (only `MailSentListener` writes it) and would also filter the marked-sent-but-never-emailed false positive — but that listener swallows its own exceptions and post-dates plenty of stored rows, so gating on it would *hide real history*; one extra `Sent:` line is the safe direction. **It has to be per row, not a whole-list gate**: `MarkSent` early-returns once the doc leaves `STATUS_DRAFT`, so a contact added to an already-sent invoice gets an invitation that never receives `sent_date`. (`markSent` / `markPaid` stamp `sent_date` on *every* invitation, so a marked-sent-but-never-emailed doc still reads `Sent:` — accepted, and `EmailController` calls `markSent()` *inside* its per-invitation loop while the loop's own `whereHas` excludes locked and trashed contacts — **not** addressless ones, since `whereNotNull('email')->orWhere('email','!=','')` is a disjunction that reduces to NOT NULL — so the first real send stamps contacts it skipped.) **The server writes exactly three `email_status` values** — `delivered`, `bounced`, `spam` (`ProcessPostmarkWebhook` and its Mailgun / SES / Brevo twins) — and never `'error'`, so `hasError`'s `== 'error'` arm is dead code. The pill was gated on `bounced || errored`, so on **SES** — the one ESP that writes no `email_error` — a spam complaint had been wholly invisible, and would have passed the new filter as a bare row. Hence `Invitation.sendState`, a precedence enum on the model carrying no `Color` (the `SystemLogTone` split, which keeps `lib/data` out of `lib/ui`) mapped to label + tooltip + tones at the call site. **The ordering turns on the fact that `email_error` is NOT a failure signal**: `ProcessPostmarkWebhook::handle()` assigns `email_error = $request['Details']` *before* its `RecordType` switch, and the file's own payload samples carry `Details` on **Delivery** as well as Bounce and SpamComplaint — on a delivered mail it is the remote MTA's success line (`smtp;250 2.0.0 OK …`). Mailgun and Brevo do the same with `delivery-status.message` / `reason`. So `email_status` **wins whenever it is set** and `errored` is reached only when no webhook has spoken; rank `errored` first instead — as this shipped for a day — and every successful send on the default hosted ESP paints a red "Error" pill over an SMTP success string, with Reactivate offered on mail that arrived, while the green arm becomes near-unreachable. The raw `emailError` text is suppressed on a `delivered` row for the same reason. That fact also re-pointed **`showReactivate`, which is now `sendState == bounced`** — Reactivate clears a Postmark *suppression*, and only a bounce makes one (spam carries `"CanActivate": false`, a delivered mail has nothing to clear, an MTA failure has no bounce record and no `message_id`); the old `hasBounced || hasError` had been offering the button on every delivered hosted row, where it could only 400. `email_status` is only ever written by a **webhook-capable** ESP, so a self-hosted SMTP install — or a *hosted* account on Gmail / Office365 — never sees a Delivered pill; `email_error = 'primed'` is a **VeriFactu sentinel** (four writers, cleared again by `SendToAeat`), so a Spanish company can see a red Error pill reading `primed` and, via `hasBouncedInvitation`, a bounce overlay on that invoice's list chip — pre-existing and app-wide, and transient except for contacts the submission skips. **The pill is capped, never wrapped in `Flexible`**: it is a non-flex child after an `Expanded`, so `StatusPill`'s inner ellipsis never binds — but a bare `Flexible` makes `totalFlex` 2 and `Expanded` is `FlexFit.tight`, pinning the identity column to exactly half the row with the remainder stranded, on *most* rows once `delivered` fires. `ConstrainedBox(maxWidth: 160)`, the constant and the argument `ClientListTile`'s money column already uses. **The empty state must yield to a queued send**, because the send rides the outbox (`MutationKind.emailEntity`) without dirtying the entity, so nothing else on screen shows it in flight; the watch therefore drops its `kind:` filter and partitions in Dart. `scheduleEmail` is excluded — it posts to `/api/v1/task_schedulers` and its handler applies nothing, so the row would appear and vanish, while "no emails have been sent" is simply *true* for a scheduled send; recurring "Send now" is a `MutationKind.update` carrying `send_now=true` (`sendNow` calls `save(extraQuery:)` — note `MutationKind.sendNow` exists, with a dispatcher case and **no enqueuer anywhere in `lib/`**, so it is dead wiring and not what that action produces), and `sendEInvoice` is a transmission, not an email. A **dead** send row is excluded by `watchPendingForEntity`, so the tab reverts to the truthful denial and the failure surfaces through the Outbox screen and the sync toast — the trade `OutboxDao` already documents, along with its general fix (`watchDeadForEntity`, worth building once for all five consumers). The drain applies its response *before* deleting the row, so there is no flash on success. **And the record's `isDirty` gates the assertive copy, which is not cosmetic**: `Invitation.toApiJson()` emits only `id` + the two contact ids, and `_domainToCompanion` stores that projection as the Drift payload with `_fromRow` reading the domain back out of it, so **any local edit-save strips every invitation's sent / viewed / opened / status / error from the local row** until the outbox `update` drains — unbounded offline, permanent if that row dies. Today that renders as bare contact rows, i.e. #146's symptom from a second cause; unguarded it would become a confident falsehood, so a dirty record falls back to `no_records_found`. `isDirty` is deliberately a **superset**: only `save()` / `create()` rewrite the payload, but `archive()` / `restore()` / `delete()` raise the flag too (they write the flag columns alone and leave `payload` intact), which only softens copy on a record with nothing to show. What it buys over watching the outbox is surviving a **dead** `update` row — exactly when the strip is permanent. It cannot cover every case: removing a contact soft-deletes its invitations and `includeInvitations` has no `withTrashed()`, so the history leaves the API with nothing local dirty, and the tab then reports no sends on a document that was emailed. **The root fix is still owed** and is cheap (`BaseRepository::alternativeSave` reads only `key`, `id`, `client_contact_id`, `can_sign` from a submitted invitation, so extra keys are ignored; the neighbouring `schedule:` column and `_forMutation`'s "stays in the *display* payload" are the idiom): it would also repair two live bugs — after a local save the invoice status chip reverts Viewed → Sent via `hasViewedInvitation` → `calculatedStatusId`, and the red bounce badge vanishes from list rows and detail headers. Everywhere **else** `invitations` means the *recipient set* and must stay unfiltered — `_hasDeliverable` → `_canSend` would disable Send on exactly the documents this fixes, `_recipientText()` / `noEmail` would blank the "To:" line, `hasInvitations:` feeds `emailPreviewBinding` and flipping a bound preview to the server's generic sample re-opens #31, and `BillingDocEditViewModel.hasInvitations` / `seedClientInvitationsIfEmpty` would re-seed contacts on already-sent docs; `_allBounced` is correct as written, since adding a never-emailed contact genuinely makes "resending just bounces again" false. Finally, the two Email History tabs are **different features under one name**: React's billing-doc one is `POST /api/v1/emails/entityHistory`, a `SystemLog` feed, and re-sourcing to it would cost every SMTP self-hoster the whole sent/opened/viewed lifecycle — so `email_history_empty` ("…only available when sending with Postmark/Mailgun") is *that* feed's string, right on the **client** tab and wrong here. That tab therefore states the neutral `no_records_found` and carries the caveat as a **subtitle** (`EmptyStateBody` gives the title no `textAlign`, so a 90-character sentence there wraps ragged-left) — on **both** account kinds. It briefly branched on `isHosted`, on the premise that hosted is always Postmark: it is not. `Email::MAIL_DRIVER_MAP` offers gmail / office365 / microsoft and the `client_*` methods and hosted free/trial routes to Mailgun, so a hosted account sending through Gmail gets no webhook, a permanently empty feed, and was told its mail had never been sent — #146 inverted. **`no_history` is unusable** — `fr.json` carries it as Greek ("Κανένα Ιστορικό") and `zh_CN` falls back to English, and `_app_pending.json` can only *add* a key, never override a present-but-wrong locale value; `in_flight` ("Syncing…") is English-only for the same reason, which is why the queued row leads with the fully-translated `email_queued` and demotes it to a grey sub-line, as `PendingCommentRow` does. Three things that look true and are not: **a recurring invoice's tab is permanently empty**, and correctly so — `SendEmailRequest::ENTITY_CLASSES` does map `recurring_invoice`, but `RecurringService` has no `markSent()` and `EmailController::send` calls it inside the per-invitation loop before dispatching, so that request fatals and the template's own invitations never receive a `sent_date` (BACKEND.md); the generated invoices carry the history. `invitation.link` is **not** unused (`purchase_order_actions.dart` resolves the vendor portal from it). And a vanishing tab would not shift an `initialIndex: 2` for the reason people assume — eleven entities pass 2 and `comments_surface_wiring_test.dart` enforces it; Client is simply the only screen whose tab *set* is module-gated, and the real mechanism is `EntityDetailTabs`' remembered-index guard.

## A contact's email can be one the server typed

**A contact's email can be one the *server* typed, and it is indistinguishable from the user's except by shape.** When a contact with no email of its own first reaches the client or vendor portal, the backend mints `Str::random(6|15) . '@example.com'` purely so Laravel's `contact` guard has a username — then **persists** it and returns it on every `GET` for ever after, so a contact the user left blank shows an address they never typed (invoiceninja/flutter#116). Fourteen mint sites: both `*Portal/InvitationController.php` (15 chars) and both `*ContactKeyLogin.php` middlewares (15 on the magic-link branch, 6 on the rest). The app's own **"View portal" button on the contacts card is one of the triggers**, and the server already hides these everywhere *except* the API — `HtmlEngine.php:568` blanks the address before rendering a PDF; `ClientContactTransformer.php:36` returns it raw. `isPortalPlaceholderEmail` (`lib/data/models/value/parsing.dart`, beside `kMaskedPassword`) is the one predicate, applied at the `Contact.fromApi` / `VendorContact.fromApi` seam so all ~15 render surfaces, `isBlank`, and the OS-address-book writer in `contacts_sync/contact_card_builder.dart` are covered at once. Four things are load-bearing. **The match is deliberately narrow** — 6 or 15 `[A-Za-z0-9]`, at least one **uppercase**, domain exactly `example.com` — because a blanket `@example.com` rule blanks the *entire* seeded demo dataset behind `tools/build_demo_web.sh`: measured live, all 96 demo contacts sit at `example.com`/`.net`/`.org`, and length alone also swallows three real ones (`shad30@`, `cboyle@`, `lucy17@`). Every Faker and hand-written fixture local part is lowercase, which is what the uppercase clause buys; the price is a ~3.8% miss on the 6-char variant, taken knowingly, because a miss shows one junk address while a false positive **hides a real one**. The raw value is then **carried on `portalPlaceholderEmail` and re-emitted by `toApiJson`, never cleared** — clearing it would be an unrequested write to the field the portal guard authenticates by, and it would never settle (the next portal visit mints a different address). The re-emit is gated on **`id.isNotEmpty`**, which is the clone guard, not a formality: `ClientAction.clone` / `VendorAction.clone` copy each contact with `id: ''` and keep every other field, so without it a clone POSTs a *new* contact carrying the **source** contact's minted address — invisible, because the form shows the email field blank (and `email` is the only field that reaches the server here: `contact_key`, `link` and `password` are not in `ClientContact::$fillable`). **Do not "just omit the key" instead**, however equivalent it looks on the wire: `_domainToCompanion` stores `toApiJson`'s output as the Drift `payload` and `_fromRow` re-reads the domain from it, so an omitted key round-trips to `''` and the *second* offline save clears the server value after all — invisible in review, reproducible only with two consecutive saves. And the scrub is needed **again** in `client_repository._primaryEmailOf` and `vendor_repository._displayNameFor`, because their API callers pass `ContactApi` / `VendorContactApi`, which never pass through `fromApi`: without it, `clients.email` (list search + the `contact_email` sort) and `vendors.display_name` (the picker) hold junk after a sync and `''` after a local save, for the same record. `Client.displayName` gets the same fallback, since `ClientPresenter::name()` derives it from the first contact's email for a nameless client — and that scrub is why **empty now means two different things, which the UI must keep apart**: the server never sends an empty `display_name` (that presenter bottoms out at `'No Contact Set'`), so `ClientNameLabel` folding `displayName.isEmpty` in with `client == null` started rendering its “deleted / no permission / still loading” em dash over a client that had loaded fine. A *label* now reads `(no name)` for resolved-but-nameless (`ClientNameLabel`, matching `ClientListTile._displayName`); a **picker** goes the other way and falls back to the record **id** in `Client`/`VendorRepository.watchActiveNames`, because that seam has no `BuildContext`, it is what `VendorNameLabel` / `_RecordMembershipFilterKey` / the line-item picker's `?? id` maps already do, and a repeated `(no name)` cannot tell two nameless rows apart in a list you must pick from — where a blank one is also sorted to the top, since those queries order by that same column.

## A row printing the same name twice is normal for an individual

**A row that prints the same name twice is the *normal* state for an individual, and the only usable tell is string equality against the title the row is already rendering.** `ClientPresenter::name()` keeps `client.name` only at `strlen() > 1` and otherwise returns the first email-bearing contact's `first_name . ' ' . last_name`, while `ClientContactPresenter::name()` does the exact reverse — whichever side is empty borrows the other — so `client.displayName` **is** the primary contact's name for every sole trader, and `clientDisplayNameOf` passes it through (it rejects only a minted placeholder *email*, #116). The narrow Clients row therefore stacked `Jane Smith` on `Jane Smith · New York` (invoiceninja/flutter#118), and `VendorListTile` did it without the server's help, since `VendorApi` carries no `display_name` at all and its `_displayName` runs the same cascade client-side. `contactSubtitleLabel` / `isSamePartyName` (`lib/domain/contact_label.dart`, which **imports nothing** — `Contact` and `VendorContact` share no supertype and the decision is pure string work, so each tile projects into `String`s; its sibling `phone_candidates.dart` needs a generic for the same split only because it walks a list) replace both tiles' `_contactLabel` twins: a contact name that reprints the title yields that contact's **email** instead, and when the title *is* that email — a nameless client whose `display_name` fell through to it — the existing `city → number → blank` cascade runs on, blank still meaning a *rendered* empty `Text` (#112, an invariant this makes reachable far more often, not less). Five things are load-bearing. **`classification == 'individual'` is not the gate** however much it looks like one: it is optional, usually blank, and has no display meaning server-side (every backend use is tax / Peppol / filtering, and `ClientPresenter` never reads it), so it would miss most of the collisions and catch none of the ones a business hits by naming its contact after itself. The comparison runs against the **`displayName` the tile's `build` already computed and passes down**, never `client.displayName` or `client.name` — a client named `A` is *titled* with its contact's name while `client.name` still says `A`, so comparing anything else dedupes against a string nobody can see. The fold is **trim + case + whitespace-run collapse and nothing else**: the server's concat is *not* trimmed, so a contact with only a first name arrives as `'Jane '` against the tile's `.trim()`ed `'Jane'` and a bare `==` misses the commonest shape there is (the same trim absorbs the literal `' '` `ClientContactRepository::save` writes into the seeded blank contact's email, #115 — `_contactLabel` already trimmed that, so the rewrite *preserves* it rather than fixing it: untrimmed it is `isNotEmpty` and would newly render a leading ` · `); Dart's `RegExp` is ECMA-262 so `\s` also catches the U+00A0 in a name pasted out of Word. Diacritics, punctuation, initials and any prefix/containment rule stay **out**, because the failure modes are asymmetric — a false positive hides the only place the narrow row shows that contact, a false negative merely leaves today's noise — and `Smith` ⊂ `Smith & Sons` is a company named after its owner. And it must stay **string** equality, never identity: `display_name` carries no contact id, and the two sides don't even pick the same contact (`contacts->whereNotNull('email')->first()` server-side, `isPrimary`-preferring in the tiles), so on a multi-contact client the two lines can legitimately name different people and the fold correctly declines. The client tile's `_displayName` also gained the **contact-name fallback its vendor twin and `clientPickerLabel` already had**: `ClientCreateDialog` accepts a client name *or* a contact name, so a client saved with only the latter has `name` and `display_name` both empty and the row titled it `(no name)` directly above that very contact — #118 inverted, and something the dedupe cannot catch because the two strings genuinely differ. It is convergent, not divergent: `ClientPresenter::name()` runs the identical fallback, so the optimistic local row now matches what the round-trip sends back instead of flipping on sync, and the avatar initials, the call button's `partyName` and the semantics label all read the same repaired string. Scope is the **narrow rows only** — the wide table's `contact_name` column is labelled and keeps its value, the same asymmetry #112 kept for its em dashes, and the detail screen deliberately repeats the name across its header and its captioned Contacts card.
