# What a row shows, and what its actions do

Companion to CLAUDE.md § Design system (v2) (the row and value rules). A narrow list row carries no labels, which changes what a tap means and what an empty value should render as. The main file carries one line per rule; this doc carries the evidence, including the three renderings a zero can legitimately take.

## A narrow list row has exactly one destination

**A narrow list row has exactly one destination, and a link's at-rest affordance is gated on the input device.** A cross-entity `*NameLabel(link: true)` belongs in a **labelled** wide-table cell (a column under a `Client` header) or on a detail surface where nothing else takes a tap — never in a tile's identity block. `linkOrText` builds a `LinkText` whose `GestureDetector` is `HitTestBehavior.opaque`, and it sits *inside* the row's own `InkWell`, so the innermost recognizer wins the arena and the row's "open this record" tap never fires. Nine tiles shipped that way: the client name was a 12 px `ink3` subtitle directly under the invoice number, so the row's most-scanned string was a live target to somewhere else, and an unpredictable share of row taps went to the client. That was invoiceninja/flutter#128 — testers read it as an intermittent bug, some went back to pen and paper, and one never opened an invoice at all during the beta. In **multi-select** it was worse: the row's tap becomes `onSelectTap` but the nested link still won, so the tap navigated away instead of toggling, and the `⋮` is hidden in that mode so there was no other route. The app already had the right shape in two places — `dashboard_mobile_rows.dart`'s `MobileInvoiceRow` takes a single `onTap` and renders the client as plain `Text` (and `dashboard_screen.dart` selects it on `Breakpoints.isPhone`, so a landscape phone gets it too), and `project_list_tile.dart` / `transaction_list_tile.dart` do the same while their wide columns link. `test/lint/no_list_tile_name_link_test.dart` pins it by allowlisting the *permitted* files rather than globbing the forbidden ones — scoping it to `*_list_tile.dart` would miss a `link: true` added to `kanban_card.dart`, `task_daily_entry_row.dart`, `weekly_grid.dart` or the mobile dashboard rows, all narrow surfaces with a whole-row tap; that way a new narrow surface is safe by default and the allowlist is the deliberate escape valve, which is why there is no comment opt-out. It strips `//` tails before scanning, or it fails on the very comment that explains it. Four things about the rest of the fix. **The at-rest cue is an underline, and the colour only rides along**: `linkNeedsAtRestCue` (`Env.isTouchPrimary`, the same gate as `InSizes.touchTarget` — a narrow desktop window still has a mouse) drives `LinkText.underlineAtRest`, because the hover underline that carries "link" on a pointer platform can never fire on touch, and **colour cannot carry it here** — `accent` is user-overridable per (company, user), `buildInTheme`'s `_deriveAccentInk` re-derives the whole family by shifting HSL lightness ±0.18, and the **second stock swatch** (`#1F2937`) clamps to near-black in light mode, so a colour-only affordance silently evaporates for that user while `#16A34A` / `#EF4444` would hand them client names that read `paid` / `overdue` (the same hazard the comment badge's tone paragraph already records). On the default palette the hue shift is nearly free of luminance signal anyway: `accent` against `ink3` is **1.09:1**. **The colour is `accentInk`, not `accent`**, because a selected row's fill is `accentSoft` and `accent` — the same mid blue in *both* brightnesses — lands ≈3.2:1 on the dark one, under the 4.5:1 floor; `client_picker_field.dart`, `tag_picker_field.dart` and `line_item_table_desktop.dart` had each already written that finding down. **`linkOrText` takes a `BuildContext` and the flag lives on `LinkText` as an opt-in**, so the pointer-only surfaces that deliberately stay quiet (`cellLink`'s Number cell, the dashboard tables, which build `LinkText` directly with no `onTap`) are untouched; a raw `LinkText` that *does* want the cue passes `linkAtRestColor(context)` + `linkNeedsAtRestCue` by hand, which the invoice header's "Recurring invoice" link must, or one header carries two links with only one of them visible. And **`Semantics(excludeSemantics: true)` must re-declare `onTap`** — excluding the subtree drops the descendant `GestureDetector`'s `SemanticsAction.tap` along with its text node, leaving a role with no `ACTION_CLICK` for TalkBack or switch access to invoke; `detail_info_row.dart` and `phone_number_value.dart` had the same latent bug. **That applies to `child: ExcludeSemantics(…)` exactly as it does to the property**, and the spelling is what decided where it was caught: the property form went wrong three times and was found each time, one issue apiece (`detail_info_row.dart` #109, `phone_number_value.dart` #128, the calendar cell #137), while the widget form — which no rule here named — had **all three of its role-bearing sites broken at once** (the other five widget-form excludes carry no role and need no action) and stayed that way until #143 went looking: `activity_feed_row.dart`, `kpi_card.dart` and `activity_record_row.dart`, each announcing a button nothing could activate, because `InkResponse` supplies the action from its own node and never sets `button`, so role and action come from two different places. `test/lint/semantics_excludes_need_ontap_test.dart` fails the build on either spelling now. The role is `link:`, not `button:` — for an inline text link; a whole row that navigates keeps `button:`, as `ActivityFeedRow` always has.

## A pure navigation action must never reach an edit screen

**A pure navigation action must never reach an edit screen.** `EntityActionItem.isNavigationOnly` exists because `EntityEditScaffold._onAction` treats any action with no `saveParamFor` entry as an *after-save* action: on a dirty form it runs `_runSave` **first**, and in create mode it creates the record outright and then races its own `saved` toast + detail redirect against the action's own navigation. So the "View client" / "View vendor" item that replaced #128's row link — one per party-bearing entity, sitting as a **sibling** immediately above `?copyLinkActionItem` (never inside the `if (can…Edit)` collection-`if`, which `entity_copy_link_coverage_test.dart` warns silently un-guards Archive) — is flagged, and `filterForEditScreen` drops it. `TaskAction.viewClient` predates the flag and had the bug latently; it is fixed too. Three more rules. The item is **permission-gated** on `me?.can('view_client')`, matching `EntityLinkCard`'s `permissionKey:` on the four detail grids — a labelled menu item makes a promise a bare table cell does not — and the read stays *inside* `itemsFor`, which runs per build, so it re-resolves on a company switch. Its slot is deliberately **low** in the menu: item order also drives the wide detail header, where `OverflowView.flexible` collapses from the end, so a slot right after Edit would promote it to a labelled button and push a money action into `⋮ More` on all five billing docs — the discoverable path is the detail header's now-cued client name, so the menu entry is an accelerator. Icons are `Icons.person_outline` / `Icons.storefront_outlined`, matching the detail grids rather than the registry's plural `people` / `store`. `test/lint/view_party_action_coverage_test.dart` pins the item, the dispatch case, the flag and the gate together, because only *half* of that is compiler-enforced — the exhaustive `dispatch` switch forces the `case`, but nothing forces the `itemsFor` entry, so an entity can ship a dead action with a green suite.

## An empty value is an em dash in a labelled slot, nothing in an unlabelled one

**An empty value is an em dash in a *labelled* slot and nothing at all in an unlabelled one.** `cellMoney` / `cellEmpty` (`lib/domain/columns/column_cells.dart`) render `—` for a zero because the wide table's column header says what the value is and a column of blanks reads as broken. A detail KPI strip is a *third* case with its own rules — see § A zero in a detail KPI cell has three possible renderings below. A **narrow list row carries no labels**, and the Clients tile stacked balance over paid-to-date dashing each independently — so an inactive client showed a `— / —` beside the `…` menu (invoiceninja/flutter#112). It now omits an absent line, and the whole block when both are absent. The predicate is `Formatter.money(..., zeroIsNull: true)` returning `''`, which keeps visibility to one source of truth and, as a consequence, makes a **negative** balance render (plain `ink`, not the bold `overdue` red) instead of hiding behind a dash the way `!(balance > 0)` used to hide it — the wide table always showed that same client's credit. Three things are load-bearing: the money block collapses but its **leading 12 px gap must not**, or a long ellipsized name ends up 4 px from the `…` icon on a row with no pill; `_SubtitleLine`'s fallback goes **blank, not absent** (`text = ''`), because an empty `Text` keeps its line box at any text scale while dropping the widget re-centres the name and zigzags the name column down a scrolled list — and a fixed-height `SizedBox` would clip descenders past ~1.14×; and row heights can't move either way — but **don't try to pin that with a height assertion**, because it can only ever pass: `EntityActionsPopupButton` sizes itself to `actionButtonSize()` (44 on touch, which `flutter test` always is) and floors the tile at 72 on its own, on top of the scaffold's `kEntityListRowHeight`, and the identity column outgrows the money block at every text scale anyway. Probe the *name's* `dy` instead — that is the only thing a collapsed subtitle actually moves. The Add-items picker's footer is an unlabelled slot too — in the ≥720 `Dialog` and the bottom sheet alike — and it shipped with a written rationale for the wrong answer: a comment claiming an empty slot "left the footer visually lopsided before any picks" justified a hardcoded muted `0` in the bottom-left of every billing doc's item picker. The premise was never reachable — the slot is an `Expanded` first in a `Row` whose other children are the Cancel / Add buttons, so a blank string leaves every position identical, and `git show 1deb9c72` shows that `Expanded` was already there in the commit that wrote the comment. What the `0` actually reads as is **money with the currency symbol missing**, because the same slot renders `3 · $45.00` the moment anything is picked — invoiceninja/flutter#132, which asked for it to be hidden because it is "distracting especially without a currency symbol". `lineItemPickerFooterText` (`line_item_picker_summary.dart`, a leaf: `decimal` + `formatting.dart`) is now the only source for that string, and the gate is the **count, never the total** — a picked free product prints a real `$0.00`, tier (1) of § A zero in a detail KPI cell has three possible renderings below. It is a pure function rather than a widget test because `_Footer` is private and pumping `LineItemPickerBody` needs a `noSuchMethod` `Services` stub plus four async loads, so the widget is impractical to pump and the decision is not (the trade `sidebarShowsUpsell` already makes). The sum also stopped wearing the company's `$` for a client who bills in something else: it passes `clientCurrencyId: _client?.currencyId` **and** `groupCurrencyId: _group?.currencyId`, both already loaded by `_loadRateContext`, and `Formatter._resolveCurrencyId` walks them client → group → company on its own. Pass **both** or neither — the client tier alone is a known bug with a written verdict: `billing_edit_totals.dart` resolves the same question through `watchEffectiveClientCurrency` (`client_settings_cascade.dart`) precisely because reading only the client's own override "rendered a grouped client's totals in the company currency, with the wrong symbol AND precision", and that totals strip is the surface the user lands on one tap after this footer, so the two disagreeing is visible within a second. A stream helper is the right tool where the party arrives asynchronously; here the cascade is two fields the state already holds. **The row prices are the gap that remains, and it is every doc type, not just purchase orders**: `_ProductsTab` / `_TasksTab` / `_ExpensesTab` all format with no currency id at all, so a EUR client sees rows in `$` under a footer in `€` — and with `convert_products` on the row also shows the *unconverted* catalogue price, so the fix is "show what will land", not a relabel (product × `crossCurrencyRate`, expense through `expenseInvoiceLineItem`, task through its rate cascade). A **purchase order** is the one doc with no tier to resolve — it passes `clientId: ''`, has no group, and its vendor is never threaded here, so its whole sheet stays company-scoped and at least self-consistent; giving it the vendor currency means adding a `vendorId` to `openLineItemPicker` → `showLineItemPickerSheet` → `LineItemPickerBody`, and then `PartyCurrencyBuilder` (`lib/ui/core/widgets/party_money_cell.dart`) is the resolver to reach for — don't hand-roll a second one.

## A zero in a detail KPI cell has three possible renderings

**A zero in a detail KPI cell has three possible renderings, and picking the wrong one is invisible in review.** (1) **Print the real `$0.00`** when the zero is itself informative — a free product's `price`, a payment's `applied` (zero applied is an unapplied payment, which is the point). (2) **Dash it** when the slot is labelled but the value is absent or simply not kept — the Client strip and `BillingDocKpiStrip` dash every zero, and Product's `cost` opts in via `moneyCell(..., dashIfZero: true)` so an unentered cost doesn't claim the product is free. Note Product deliberately splits the two: *"Price does not get the same treatment — a zero price is a real price."* (3) **Omit the cell entirely** when the zero is the overwhelming default *and* the label itself misleads. That is `Refunded`: virtually every payment has never been refunded, and people read the word on a payment they had just recorded and double-took before their eye reached the `0.00` (invoiceninja/flutter#113). Dimming to `—` does not fix that — the *word* is what is being read. `Refundable` leaves with `Refunded` rather than on its own test, because it is `amount - refunded` and so at zero it silently reprints `Amount` two cells away, on a payment the Refund action often won't offer anyway (gated on `canRefund` **and** `hasInvoiceAllocations`, `payment_actions.dart` — not on `canRefund` alone). Product's `in_stock` is the same tier (#91). The predicate for tier 3 is **`!= Decimal.zero`, never `> Decimal.zero`** — same lesson as #112: an anomalous negative is exactly the figure a user must see, not one to tidy away.

## A conditional KPI cell means the layout must be count-agnostic

**A conditional KPI cell means the layout must be count-agnostic — which is now a solved problem, so don't re-solve it.** `KpiStripLayout` (`lib/ui/core/detail/kpi_strip_layout.dart`) owns the whole responsive branch: the wide divided `Row` (1 × 36 hairline, `InSpacing.lg` padding) and the narrow two-per-row grid. Callers pass `cells`. The commonest cell — a caption over a pre-built `Widget` — is now `KpiCell` (`lib/ui/core/detail/kpi_cell.dart`), shared by six strips; the variants that take a `Decimal` + `Formatter` (Client, and Vendor's money cell) or a `String` with a `'—'` sentinel (Projects) genuinely differ and keep their own, which is why the layout and the plain cell are shared but the typed ones are not. Before this, the same two classes sat hand-copied in **eight** files and five of them indexed `cells[0..3]` outright, so the first strip to drop a cell got a `RangeError` — paid for twice (#91, #113) before it was shared. Two things the shared widget protects that a rewrite loses silently: an odd trailing cell keeps an **empty `Expanded` beside it** so it stays at half width instead of stretching out of line with the column above (that is why it isn't a `Wrap`); and `InSpacing.md`/`lg` read `MediaQuery.sizeOf(context).width` — the **window**, not the local constraints — so the gaps key off the screen while the branch keys off the box. Deliberately **not** merged with `BillingDocKpiStrip`, which branches on per-cell width (`maxWidth / cells.length >= 130`), falls back to a `Wrap`, and uses a 32 px divider; merging would silently move Invoice / Quote / Credit detail. Note also that a strip whose host caps its width — the payment detail body sits in `CenteredFormColumn` (820) — never reaches the 1100 branch at all, so a layout test that only sweeps wide widths proves nothing about what ships.
