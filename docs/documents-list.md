# The Documents list

Companion to CLAUDE.md § Sync — non-obvious rules. The main file carries the one rule about removing a row; this doc carries the evidence for it and for the other ways the company-wide Documents list (`/documents`, `DocumentRepository`, the `document_records` table) differs from every other list. Server gaps behind it are in BACKEND.md § Documents list.

admin-portal had this list in its menu; the web app's "Documents" is DocuNinja, a different product. A row is one uploaded file, whatever record it hangs off — an invoice, a client, an expense, the company itself.

## Where a row comes from

Four writers, all of them server copies:

1. **The list's own pages** — `GET /api/v1/documents`, page by page through `ensurePageLoadedTemplate`, like every list. An older server's response names no parent (below), so a page upsert leaves `parent_type` / `parent_id` **absent** in the companion, which keeps a link already stored; one with invoiceninja/invoiceninja#13365 names it on every document, and the page fills the link itself.
2. **The `/refresh` harvest** — `DocumentRepository.applyRefreshDelta`, a derived delta applier (`kDerivedDeltaApplierTypes`). Every record the delta carries brings its complete `documents` array (`BaseController` loads the relation whole), which gives each file its parent. It writes the whole server copy only when the file is new or strictly newer, and **only the link** when the link is the news: that copy can be older than the row stored, because the server built the response before an echo that has already landed — writing it whole reverted a just-saved rename. Unchanged files are not written at all, since the groups and the company's own files arrive on every tick. Files this session has seen removed are skipped (below). The prune's lookup is one batched query, not one per record: a delta after a long absence carries thousands of records, all inside the refresh transaction. It never touches the list's cursor — harvested rows can be old, and a user without `view_document` gets only their own files from `GET /documents` while the delta carries every file on the records they can see.
3. **A record tab's own change** — `documentMutationHandlers` (and the company dispatcher) tell the repository, as a `DocumentMirror`, about a delete or visibility change the server confirmed. An upload needs no mirror: the server touches the record, so the next delta files the new upload under it.
4. **The relink** — `DocumentDao.relinkFromParentTables`, one `UPDATE … FROM json_each(…)` per parent table, fills the link on rows that have none from the `documents` columns the records already cache. It runs when the list opens and after a full sweep. The `json_valid` guard is load-bearing: an older row can hold `''`, and `json_each` throws on anything that isn't JSON.

## A document row is removed only three ways

A delete is a hard `forceDelete` server-side (`DocumentRepository::delete`), so it leaves no tombstone and no `updated_at` delta can ever report it. Left alone, a file deleted on the web would sit in this list until the database was wiped. The three ways a row leaves:

- **A confirmed delete** — the outbox delete drains (`applyDeleteResponse`, a hard local delete, since this list has no Deleted view), a record tab's delete drains (`DocumentMirror.removeConfirmed`), or View / Download / the preview gets `NotFoundException` (`forgetMissing`).
- **A record that no longer lists it** — the harvest prunes rows linked to a record whose complete `documents` array no longer names them. Only for a prunable record (not the company's own files: that array is itself a delta), and only rows **older than the record**: a row newer than it was written after the server built the response, i.e. an upload confirmed while it was in flight.
- **A full Sync sweep that reached the end** — `refreshAll(full: true)` notes every id the list's pages (and any delta that arrives meanwhile) report during the sweep and, if `refreshAllTemplate` reports it walked to the end, removes the rest — **except a file a cached record still lists** (`DocumentDao.idsListedOnRecords`). That guard is what makes the sweep safe for anyone but an admin: `GET /documents` shows a user without `view_document` (which the permission grid cannot grant) only the files they uploaded or are assigned, while the harvest files every file on the records they can see — unguarded, each Sync deleted all of those. The record tables are fresh by then: the documents step runs last in the Sync pass, after each was re-downloaded with `include=documents`. A partial sweep never prunes: its page 1 is a delta and its later pages start at row 51.

Every path skips a **dirty** row — and `DocumentDao.deleteByIds` checks it in the DELETE itself, so a rename saved between a caller's read and the write can't lose its row. The two prunes also skip a row **an outbox row still names** — `OutboxDao.documentIdsInOutbox`, which also reads the `document_id` in a record tab's delete / visibility payload, since those are queued against the parent. Every state counts, `dead` included (§ A failed change is still unsynced work). The confirmed-delete paths deliberately don't check the outbox: the server has already said the file is gone. This is not the whole-database wipe `local_data_disposal_test` polices: a clean cache row the server no longer has is the same class as `applyPurgeResponse`.

Each removal is remembered for the session (`DocumentRepository._gone`), because no tombstone means a `/refresh` the server built just before the delete would put the file straight back; the harvest skips those ids, and the list's own pages — proof the file exists — take an id back out. Known residual: a delete on the server *during* a sweep shifts the offsets, so one row can be skipped and pruned. It is clean cache and comes back with its page.

## The list never sends a lifecycle status

The `documents` table has no `is_deleted` column, and `QueryFilters::status` reads it for `archived` / `deleted` (as do `is_deleted=` and `without_deleted_clients`). So `DocumentRepository.stateQueryParams` returns `{}` for every state — the one repository that overrides it — and the list never passes `excludeDeletedClients`. Nothing is lost: archive and restore are no-ops for a document, so every file is active. `{}` does also return a trashed one (`QueryFilters::apply` ends in `withTrashed()`), which only a company delete produces. That is also why the list has no State filter, no status tabs, no Archive / Restore, and a plain "Search Documents" hint (`search_hint_key_convention_test` exempts it).

## The server names no parent, so "Linked to" is learned

Before invoiceninja/invoiceninja#13365 `DocumentTransformer` sends no `documentable_type` / `documentable_id`, and the documents report's `record_type` is a class name with no id. admin-portal's "Linked to" filled in only for files it had also loaded through their record, and so does this one — from the four writers above. `DocumentApi` reads the two keys tolerantly and `_apiToCompanion` takes them whenever its caller names no parent, so a server with the PR — the snake_case model name (`Relation::getMorphedModel` first, so the morph-mapped `invoices` alias reads `invoice`) and the hashed id — fills the column from a list page or a PUT echo with no client change (`document_repository_test` › a server that names the parent). The four writers stay for older servers. A row with no link shows an em dash; one whose record isn't cached shows its type alone and still links.

## A change here is a change to the parent's copy too

A record's own Documents tab reads its `documents` JSON column, not this table. So a rename, a visibility change or a delete made from the Documents list also patches the parent's copy through `DocumentRepository.ownerFor` — every parent repository implements `EmbeddedDocumentsOwner`, the company's included — when the link is known. When it isn't, the server's `touch()` on the parent brings it back in the next delta with its new array.

`PUT /documents/{id}` validates only `name` and `is_public` (both `sometimes`), but runs `fill($request->all())` and `Document::$fillable` also lists `is_default` — so a save queues **only the fields it changed** (`DocumentRepository.save`). Never both by default: a rename that also sent the cached `is_public` would undo a "make private" queued on the record's own tab (which doesn't touch this table until it drains) or made on another device. A later save of the same file carries the keys of the pending one it supersedes, because `dedupPendingMutations` deletes that row. Delete is `DELETE /documents/{id}`, never `/bulk`: the bulk echo is the deleted rows (none) and its `ids` existence check rejects a batch with one already-gone id. Both authorize against the **document** (`EntityPolicy::edit` — admin, `edit_document`, uploader or assignee), not the parent, hence `canEditRecord('document', …)`; and attaching is an Enterprise feature on hosted, so the actions follow the record tab's read-only policy (`canAttachDocuments`). One rule, `documentEditable`, drives the row menu and the list's bulk Delete: `document` has no row in `kPermissionEntities`, so the scaffold's own bulk-permission gate lets anything through.

## No create screen

A file is uploaded on its record, so the module declares no `createBuilder`. The framework took three small extensions for that: `EntityHandlers.newRoute` is null for a routed entity with no create screen (no sidebar "+"), `buildEntityRouteBlock` routes `<root>/new` to a redirect to the list (otherwise it matches `:id` and hydrates a record called "new"), and `EntityListScreenScaffold.newRoute` / `newLabelKey` are nullable (no New button, no FAB, no FAB clearance, `N` inert). `entity_registry_completeness_test` (no "+" or create shortcut), `entity_links_test` (`/new` redirects) and `entity_list_fab_clearance_test` (no New button or FAB) pin the three.
